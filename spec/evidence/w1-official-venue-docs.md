# Official venue capability evidence (A7/provider input)

## Evidence boundary

- **Observed — https://docs.alpaca.markets/us/openapi/trading-api.json ; https://www.interactivebrokers.com/docs/openapi/api-reference.json**: These official machine-readable specifications were actually retrieved and parsed. Other URLs below were actually read as official HTML/Markdown unless marked Unknown.
- **Unknown**: Repository adapter exposure, current-engine/mock behavior, enabled account entitlements, and live provider behavior are not established by this document. This research made no repository edits, authenticated trading requests, or runtime-trading claims. Provider primitives must be joined to the separate adapter-method evidence, not substituted for it.
- **Unknown**: A pagination token, submission-time filter, returned sequence, and live WS feed do not by themselves establish a gap-free resumable order/account event log. Explicit distinctions are recorded below.
- **Unknown**: `functions.read` URL access was disabled. Actual successful document reads used `agent-browser --session w1docs read URL` (and `--raw` for JSON/full HTML). Binance remained unreadable through both fetch and rendered DOM attempts; search summaries are not treated as observed endpoint evidence.

## Alpaca — Trading API v2 and market-data streaming

- **Observed — https://docs.alpaca.markets/us/openapi/trading-api.json**: `POST /v2/orders` accepts `client_order_id`, described as a unique order identifier, automatically generated if omitted; maximum length 128. **Unknown**: duplicate submission response/rejection semantics, key retention duration, and same-key/different-payload behavior are not documented by the inspected field definition; do not claim exactly-once replay.
- **Observed — https://docs.alpaca.markets/us/reference/getorderbyclientorderid.md**: `GET /v2/orders:by_client_order_id` requires query `client_order_id` and retrieves that order.
- **Observed — https://docs.alpaca.markets/us/reference/getallorders-1.md**: order listing supports exclusive `after`/`until` **submission timestamps**, and exclusive `before_order_id`/`after_order_id`; ID cursors are mutually exclusive and must not be combined with `after`/`until`. **Unknown**: these do not establish an update-time change feed for previously submitted orders.
- **Observed — https://docs.alpaca.markets/us/docs/account-activities.md**: activity IDs serve as `page_token`; ascending pagination starts immediately after the supplied activity; descending ends before it. Fill activities expose quantities, prices, and order association.
- **Observed — https://docs.alpaca.markets/us/openapi/trading-api.json**: `/v2/account/activities` supports `order_id`, `after`, `until`, and activity pagination. `/v2beta1/events/activities` is **SSE**, explicitly streams historical events then new events, with `since`/`until` or `since_id`/`until_id`. Without `since`/`since_id`, no historic data is returned. Bounded `until`/`until_id` ends the stream. The spec warns generic OAS-generated clients may hang on SSE and slow-client comments may report dropped messages.
- **Observed — https://docs.alpaca.markets/us/docs/websocket-streaming.md**: authenticated `trade_updates` on `wss://api.alpaca.markets/stream` and paper equivalent covers fills, partial fills, cancellations, rejections and order/account changes.
- **Observed — https://docs.alpaca.markets/us/docs/streaming-market-data.md**: market-data WS at `wss://stream.data.alpaca.markets/{version}/{feed}`, with feed entitlements and symbol/channel subscriptions.
- **Unknown**: WS replay cursor and retention were not established. The separately documented activity SSE primitive must not be mislabeled as resumable WS or assumed exposed by the repository adapter.

## Longbridge — HTTP trading and quote/trading socket protocol

- **Observed — https://open.longbridge.com/docs/trade/order/submit**: `POST /v1/trade/order` accepts optional `client_request_id`, explicitly an idempotent request ID. Server caches it **10 minutes** and returns the original cached response on same-ID requests within that window without creating another order. Omitted/empty values skip protection, including for otherwise identical requests. `remark` is a separate optional 255-character remark, not this key.
- **Unknown**: key lookup after timeout/expiry and different-payload conflict behavior are not established by the submission contract.
- **Observed — https://open.longbridge.com/docs/trade/order/order_detail**: order detail accepts required broker `order_id` plus optional `is_attached`. **Unknown**: lookup by `client_request_id` is not established; the documented detail parameters are not a keyed-idempotency lookup.
- **Observed — https://open.longbridge.com/docs/trade/order/history_orders**: historical orders accept `start_at`/`end_at` seconds, defaulting to a 90-day interval when a boundary is absent. **Unknown**: no stable incremental change sequence was established from that endpoint.
- **Observed — https://open.longbridge.com/docs/trade/execution/all_executions**: `/v3/trade/execution/all` accepts `order_id`, `start_at`/`end_at`, and `page` starting at 1; at most 1000 records per query; `has_more` directs further paging; executions have `trade_id` and `trade_done_at`.
- **Observed — https://open.longbridge.com/docs/quote/subscribe/subscribe**: quote subscriptions use socket business command 6, symbols, `sub_type`, and `is_first_push`; immediate first push is not supported for trades.
- **Observed — https://open.longbridge.com/docs/socket/subscribe_trade**: private trading WS endpoint `wss://openapi-trade.longbridge.com`; subscribe topic `private`; notifications carry `order_changed_lb` with order ID, status, executed quantities/prices. Payload uses protobuf wrapping/base64 JSON.
- **Unknown**: market-data WS hostname and reconnect replay/gap cursor were not established by the quote-subscription page; do not infer replay from socket support or the ten-minute submission cache.

## IBKR — Client Portal / Web API, not TWS API

- **Observed — https://www.interactivebrokers.com/docs/openapi/api-reference.json**: order submission schema accepts `cOID`, a client-configurable identifier of at most 64 characters, unique for **24 hours**; it should not be set on bracket children. **Unknown**: this uniqueness requirement is not documented cached-response replay, and duplicate error/payload-conflict semantics remain unknown.
- **Observed — https://ibkrcampus.com/docs/web-api/v1/endpoints/orders/place-order.md**: placement can require a separate reply confirmation; order ID returned is used for tracking/modification/cancellation. Submission acceptance must not be treated as unconditional execution.
- **Observed — https://www.interactivebrokers.com/docs/openapi/api-reference.json ; https://ibkrcampus.com/docs/web-api/v1/endpoints/order-monitoring/order-status.md**: `GET /v1/api/iserver/account/order/status/{orderId}` uses broker order ID, only current brokerage-session information; prior-session/day executed orders may return 503. **Unknown**: a direct query parameter/path accepting `cOID` was not established.
- **Observed — https://ibkrcampus.com/docs/web-api/v1/endpoints/order-monitoring/live-orders.md**: live order output includes `order_ref` set from `cOID`; endpoint maximum is 1000 orders. Filtering can affect the WS `sor` stream until a `force=true` call clears cached behavior.
- **Observed — https://www.interactivebrokers.com/docs/openapi/api-reference.json**: trade history accepts `days`, described as at most 7 prior days; omission returns current day. **Observed — https://ibkrcampus.com/docs/web-api/v1/endpoints/order-monitoring/trades.md**: narrative page instead says current day and six previous days; it returns execution IDs and `order_ref`. **Unknown**: reconcile this documentation window discrepancy before depending on the precise boundary. Neither read establishes since-ID/time pagination for account events.
- **Observed — https://ibkrcampus.com/docs/web-api/v1/ws/market-data/market-data-request.md**: WS `smd` subscribes streaming top-of-book level-one market data by conid and fields.
- **Observed — https://ibkrcampus.com/docs/web-api/v1/ws/order-position-operations/request-live-order-updates.md ; https://www.interactivebrokers.com/docs/web-api/v1/ws/order-position-operations/request-trades-data**: `sor` live order updates; `str` trade stream supports `realtimeUpdatesOnly` and `days`, including `order_ref` from `cOID`.
- **Unknown**: durable WS resume sequence, complete historic order coverage, and provider replay retention beyond the stated cOID uniqueness span were not established.

## OKX — V5 general orders (not attached/algo-order equivalence)

- **Observed — https://www.okx.com/docs-v5/en/**: general order `clOrdId` must be unique among pending `live`/`partially_filled` orders in the account. Once `filled`, `canceled`, or `mmp_canceled`, it may be reused. Historic uniqueness is not enforced; this field is not forwarded to attached TP/SL algo orders.
- **Observed — https://www.okx.com/docs-v5/en/**: `GET /api/v5/trade/order` accepts `instId` and either `ordId` or `clOrdId`; `ordId` wins if both supplied; duplicate historical `clOrdId` values return only the latest match. **Unknown**: no perpetual idempotency retention or cached-response replay is established.
- **Observed — https://www.okx.com/docs-v5/en/**: order history has separate last-seven-days and last-three-months endpoints; `after` requests records earlier than an `ordId`, `before` newer. Transaction-detail endpoints have separate last-three-days and last-three-months scopes and use `billId`-based `after`/`before`.
- **Observed — https://www.okx.com/docs-v5/en/**: public WS channels include tickers, K-lines and order books without authentication; account/order/position channels require login. Orders-channel docs warn the same message may be delivered multiple times, potentially with different `uTime`; some options-expiry closing updates are not generated.
- **Unknown**: an order/account WS replay-from-sequence contract was not established. REST paging and public book sequencing must not be equated with complete private-event recovery.

## Bybit — V5 Spot, linear/inverse derivatives, options

- **Observed — https://bybit-exchange.github.io/docs/v5/order/create-order**: `orderLinkId` is client-defined, max 36 characters, “always unique”; optional for futures/perps/spot, required for options. Creation is asynchronous and docs say use WS to confirm order status.
- **Observed — https://bybit-exchange.github.io/docs/v5/error**: error table includes `110072` “OrderLinkedID is duplicate”, `10014` “Invalid duplicate request”, and separate WS `20006` duplicate `reqId`. **Unknown**: time retention and replaying an original successful response are not established; WS request IDs are not interchangeable with order IDs.
- **Observed — https://bybit-exchange.github.io/docs/v5/order/open-order**: `/v5/order/realtime` supports `orderLinkId`; lookup priority is `orderId > orderLinkId > symbol > baseCoin`; results sorted by created time newest first. Pagination uses `cursor` from `nextPageCursor`.
- **Observed — https://bybit-exchange.github.io/docs/v5/order/execution**: execution history accepts `orderLinkId`/`orderId`, `startTime`/`endTime` milliseconds and `cursor`/`nextPageCursor`; time windows must be at most seven days. Returned execution `seq` is not globally unique across symbols (`seq + symbol` is advised).
- **Observed — https://bybit-exchange.github.io/docs/v5/websocket/public/orderbook**: public orderbook stream provides snapshot/delta; a new snapshot resets local book, and `u=1` can signal service restart. `seq` compares orderbook generations across depths.
- **Observed — https://bybit-exchange.github.io/docs/v5/websocket/private/order**: `order` or categorized `order.spot`, `order.linear`, `order.inverse`, `order.option` streams provide live updates. Fill/cancel race may produce two `Filled` messages for the same order.
- **Unknown**: retention of uniqueness, durable private-stream resume cursor and gap-free replay were not established by these reads. Pagination and returned execution sequence alone are not such a contract.

## Bitget — distinguish Classic v2 from UTA v3

- **Observed — https://www.bitget.com/docs/catalog/classic-spot-trade/classic-spot-trade**: Classic Spot placement accepts `clientOid` (invalid for `tpsl` order type); `GET /api/v2/spot/trade/orderInfo` accepts `orderId` or `clientOid`. Batch-placement failure example contains `43118`, “clientOrderId duplicate”; cancel-replace warns idempotency duplication may cancel the old order while failing the new order. **Unknown**: do not expand a batch example into exact single-submit replay behavior or retention.
- **Observed — https://www.bitget.com/docs/catalog/classic-spot-trade/classic-spot-trade**: `/api/v2/spot/trade/fills` supports `startTime`/`endTime`, `orderId`, `idLessThan` using `tradeId` for older pages, maximum 100 results; only 90-day data is available there.
- **Observed — https://www.bitget.com/docs/catalog/classic-contract-trade/classic-contract-trade**: Classic futures accepts `clientOid`; `/api/v2/mix/order/detail` accepts either `orderId` or `clientOid` plus required symbol/product type (USDT-, COIN-, USDC-futures). `/api/v2/mix/order/fills` supports `idLessThan` trade ID and timestamp windows up to three months. Separate `/fill-history` documents one-week windows and `endId` paging. **Unknown**: these endpoints' differing windows must not be collapsed into one venue-wide retention promise.
- **Observed — https://www.bitget.com/docs/catalog/trading/order-management**: UTA `clientOid` format is 1–32 characters matching `^[\.A-Z\:/a-z0-9_-]{1,32}$`. After timeout/unknown errors, docs explicitly advise using it to query order details before deciding the operation outcome. `/api/v3/trade/order-info` supports `orderId` or `clientOid`, with order ID priority.
- **Observed — https://www.bitget.com/docs/catalog/trading/order-management**: UTA open-order cursor points to older orders; order history and fills use `cursor`, `startTime`/`endTime`, 90-day access window and at-most-30-day request interval. `/api/v3/trade/fills` is the UTA fills endpoint.
- **Observed — https://www.bitget.com/docs/uta/websocket/public/Tickers-Channel**: public ticker channel is documented with symbol and instrument type. **Observed — https://www.bitget.com/docs/uta/websocket/private/Order-Channel**: UTA private order channel pushes placement/fill/cancel updates but **no first-subscription snapshot**. **Observed — https://www.bitget.com/docs/uta/websocket/private/Account-Channel**: account channel does push initially and on subsequent account changes; snapshot/update action types are documented.
- **Unknown**: duplicate-key retention/cached-response replay for UTA or Classic futures, Classic WS specifics, and a resumable private WS event log were not established; UTA streaming cannot prove Classic adapter exposure.

## Hyperliquid — exchange/info endpoints and user-address subscriptions

- **Observed — https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint**: order action accepts optional `c`/`cloid`, a 128-bit hex client order ID. Cancel-by-cloid and modify-by-ID/cloid exist. **Unknown**: cloid duplicate behavior, historical reuse, and retention are not established by that field description.
- **Observed — https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/nonces-and-api-wallets**: separate signed-action replay protection stores the 100 highest nonces per signer; a new nonce must exceed the smallest stored nonce and never have been used. Timestamp window is `(T−2 days,T+1 day)`. API-wallet nonce state may be pruned, and previously signed actions can then become replayable. This is **nonce protection**, not documented idempotent cloid response replay.
- **Observed — https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/info-endpoint**: `orderStatus` accepts user address and `oid` as either numeric order ID or 16-byte hex client order ID. `userFillsByTime` accepts inclusive start/end milliseconds, returns at most 2000 fills, with only the latest 10000 fills available. Time-range pagination guidance says to reuse the last returned timestamp as the next `startTime`. Historical orders return at most 2000 latest orders.
- **Observed — https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions**: market subscriptions include `l2Book`, `trades`, `candle`, `allMids`; user-address feeds include `orderUpdates`, `userFills`, `userEvents`, clearinghouse/account state and ledger updates. Fills snapshots are tagged `isSnapshot: true` before streaming updates.
- **Unknown**: user-address feeds should not be described as exchange-style authenticated “private WS” without separate auth evidence; private/account data scope and authentication are distinct. No durable resume token or full-history guarantee was established.

## LeverUp — onchain protocol plus REST / 1CT intent relay

- **Observed — https://developer-docs.leverup.xyz/gasless/submit**: submit-intent body includes `nonce`, deadline, trader/action/actionData/signature; returned intent hash is `keccak256(abi.encode(trader, action, nonce, deadline, actionData))`, not the EIP-712 digest. Nonce admission is no older than two days/no more than five minutes ahead; NONCE skipped status includes non-increasing/out-of-window nonce. **Unknown**: a `clientOrderId` field or same-request cached replay/retention is not established.
- **Observed — https://developer-docs.leverup.xyz/gasless/submit**: `GET /v2/trading/{intent_hash}/status` reports submitted/executed/success/skipped and transaction hash; this is a keyed **intent-status** read, not evidence of lookup by a client order ID.
- **Observed — https://developer-docs.leverup.xyz/api/history**: user trade history is page/size pagination, with `transactionHash`, block number, transaction index, log index, operation type, and position/order linkage. **Unknown**: returned chain coordinates are not documented accepted REST since-block/log cursors.
- **Observed — https://developer-docs.leverup.xyz/api/positions**: positions support page/size plus `timestamp_after` and `close_time_after` seconds; docs explicitly say there is **no public per-user limit-order REST endpoint**, directing clients to onchain `getLimitOrders` and `getTraderDecreaseOrders`.
- **Observed — https://developer-docs.leverup.xyz/onchain/events**: protocol lifecycle events include pending market trades, opened/increased/closed positions, limit-order execution/rejection/cancel, and TP/SL decrease-order lifecycle. Source hashes link execution to originating order/trade hashes.
- **Unknown**: LeverUp-hosted market-data WS and account/private WS were not established. Onchain event watching is a different primitive and does not itself prove a conventional venue WS service, guaranteed RPC log retention, or repository event-adapter exposure.

## Cross-provider conclusions for the parent report

- **Observed — https://open.longbridge.com/docs/trade/order/submit**: this read establishes explicit timed idempotent-response replay (10 minutes), not merely client correlation.
- **Observed — https://docs.alpaca.markets/us/openapi/trading-api.json**: historical-plus-live activity SSE is explicitly documented and materially stronger evidence than a live-only WS claim; generated-client limitations are explicitly warned about.
- **Observed — https://www.okx.com/docs-v5/en/**: terminal-order key reuse plus latest-match lookup is an explicit hazard for treating client order IDs as forever-stable business identifiers.
- **Unknown**: every other missing duplicate/retention/reconnect guarantee stays unknown, not unsupported. No provider capability in this artifact establishes that the current repository adapter passes the field, exposes the lookup, persists a cursor, consumes a stream, or reconciles gaps.

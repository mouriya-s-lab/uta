# W1 — Ledger persistence, restart, and crash-window evidence

## Decision questions answered

1. **What is the current on-disk shape and what legacy variants must a new ledger understand?**  [observed: `services/uta/src/domain/trading/git-persistence.ts:14-39`; `packages/uta-protocol/src/types/git.ts:22-102,171-174`] The canonical file is `<OPENALICE_HOME>/data/trading/<accountId>/commit.json`, containing unversioned `GitExportState = { commits, head }`; three hard-coded legacy account mappings (two unique legacy paths) are read only as fallback. A commit contains operations, results, an inline post-operation `stateAfter`, and an optional `round`; the result can carry an opaque `raw` provider response. JSON output is pretty-printed with no final newline. Decimal values serialize as strings, while `OrderHelper.toWire` removes seven unset Decimal sentinels from projected orders. Rehydration accepts both string and legacy number forms for most known Decimal fields and fills an absent position multiplier with `'1'`.
2. **Where can the current push lose the relationship between upstream effects and the ledger?**  [observed: `services/uta/src/domain/trading/git/TradingGit.ts:119-184`; `services/uta/src/domain/trading/git-persistence.ts:42-48`] Broker writes run sequentially before `getGitState`, in-memory commit/head publication, and the awaited full-file `onCommit` write. There is no transaction boundary, durable intent/attempt/receipt, atomic replacement, fsync, or writer queue in this path. The exact outcome of a power loss is not experimentally established; the crash consequences in the table below are therefore explicitly marked inferred.
3. **What survives restart today?**  [observed: `services/uta/src/domain/trading/git/TradingGit.ts:61-68,565-576`; `services/uta/src/domain/trading/uta-manager.ts:61-77`] Only `commits` and `head` are loaded from disk. `stagingArea`, `pendingMessage`, `pendingHash`, and `inflightWrite` are process memory and are not in `GitExportState`; an approval token is therefore not recoverable after restart. The prior persisted-state report identifies this as issue [#1313](https://github.com/TraderAlice/OpenAlice/issues/1313), and its source/code map has no implementation or spec for it (`plans/uta-refactor/report/09-persisted-state-tests-docs-issues.md:144-156,620-623`).
4. **Can the existing migration framework migrate a ledger?**  [observed: `src/migrations/types.ts:4-27,30-47`; `src/migrations/runner.ts:102-160`; `src/migrations/registry.ts:9-30`] Yes, but a ledger migration must be a custom `up` body using `ctx.userDataHome()`: the default context read/write/remove helpers target `data/config/`, and the default pre-migration snapshot copies only `data/config/`. The next active migration number is `0044`; the runner records the migration only after `up` returns, so the body must be per-account idempotent and must survive partial completion. No existing registry migration touches `data/trading/`.
5. **Which durability and lock primitives are actually available?**  [observed: scoped Node probe] In the current environment (`darwin`, Node `v26.8.1`), `fs.promises.open()` returns `FileHandle.sync` and `datasync` functions, and opening/syncing the temporary directory returned `"ok"`. The repository requires Node `>=22.19.0` (`package.json:101-104`; `services/uta/package.json:32-34`), but exact Node 22 and Windows directory-sync behavior remain unverified. UTA ledger code does not use fsync or an OS advisory lock. Existing cross-platform application locking is a directory `mkdir` lock with owner metadata, heartbeat, stale-owner reclamation, and Windows rename retries (`packages/guardian-runtime/src/runtime-lock.ts:183-231,323-430`). The installer separately uses Darwin `lockf`/`shlock` and Linux `flock` (`install:411-432`); that shell lock is not used by UTA ledger writes.
6. **What should the new append-only contract guarantee?**  [inferred/recommendation] Use a per-account, single-writer append stream with explicit durable positions, full checksums/hash-chain, expected-position CAS, immutable intent/attempt/receipt/observation entries, provider-indexed opaque payloads, idempotency keys, and a recovery policy that makes torn tails and unknown kinds observable. Durable exposure must occur only after the agreed fsync/rename sequence; derived views must be rebuildable and must never become a second trading truth.

## Observed facts

### 1. Current ledger ownership, file shape, and read/write behavior

- [observed: `src/core/paths.ts:34-45`] `dataPath(...parts)` resolves under `OPENALICE_HOME` (default `~/.openalice`) and then `data/`. The account identifier is interpolated by `gitFilePath` into `data/trading/<accountId>/commit.json` (`services/uta/src/domain/trading/git-persistence.ts:14-16`).
- [observed: `services/uta/src/domain/trading/git-persistence.ts:18-39`] `loadGitState` first reads/parses the canonical path; any read or parse failure is swallowed. For `bybit-main`, `alpaca-paper`, and `alpaca-live` it then reads a hard-coded legacy path under `data/crypto-trading/` or `data/securities-trading/`; all fallback failures are also swallowed and return `undefined`. There is no version field or schema decoder in this loader.
- [observed: `services/uta/src/domain/trading/uta-manager.ts:61-79`; `services/uta/src/domain/trading/UnifiedTradingAccount.ts:201-209`] UTA boot loads once per account, passes `savedState` into the constructor, and constructs either `TradingGit.restore(savedState, ...)` or a fresh `TradingGit`. A malformed-but-parseable shape can therefore fail inside restore; the UTA service catches account-init errors and skips that account (`services/uta/src/main.ts:76-87`).
- [observed: `packages/uta-protocol/src/types/git.ts:22-54,60-102,171-174`] The persisted top-level union is:
  - `commits: GitCommit[]`, `head: CommitHash | null`;
  - `GitCommit`: `hash`, `parentHash`, `message`, `operations`, `results`, `stateAfter`, `timestamp`, optional `round`;
  - seven operation variants: `placeOrder`, `modifyOrder`, `closePosition`, `cancelOrder`, `syncOrders`, `observeExternalOrder`, and `reconcileBalance`;
  - `OperationResult`: `action`, `success`, `status`, optional order identifiers/state/execution, fill strings, error, bracket legs, symbol, and `raw?: unknown`;
  - `GitState`: four monetary strings, `positions`, and `pendingOrders`.
- [observed: `services/uta/src/domain/trading/git-persistence.ts:42-48`] Every successful `onCommit` callback performs `mkdir(dirname(filePath), {recursive:true})` and then `writeFile(filePath, JSON.stringify(state, null, 2))`. The serialized file has no trailing newline. The write is a full replacement of the prior file, not an append, and the function does not use a temporary path, rename, fsync, lock, or Promise queue.
- [observed: scoped command output] `node -e "const Decimal=require('decimal.js'); const d=new Decimal('1.23'); console.log(JSON.stringify({d,n:Number(d),s:d.toFixed()}))"` printed `{"d":"1.23","n":1.23,"s":"1.23"}`. Thus Decimal's JSON boundary is a string in this runtime; ordinary numbers and strings retain their JSON types.
- [observed: `services/uta/src/domain/trading/OrderHelper.ts:35-44,93-103`; `services/uta/src/domain/trading/git/TradingGit.ts:546-561`] Public projections and exported commits clone `placeOrder`/`observeExternalOrder` orders and `modifyOrder` changes through `OrderHelper.toWire`. It removes unset Decimal values for `totalQuantity`, `cashQty`, `lmtPrice`, `auxPrice`, `trailStopPrice`, `trailingPercent`, and `filledQuantity`; it does not normalize the rest of the enumerable IBKR object.
- [observed: `packages/ibkr/src/contract.ts:118-145`; `packages/ibkr/src/order.ts:37-75,194-224`] The embedded provider objects are broad enumerable `Contract`/`Order` instances. Contract fields include numeric `conId` and `strike`, strings such as `symbol`, `secType`, exchanges and currency, booleans, combo arrays, and a nullable delta-neutral contract. Order fields include identifiers, action/type, Decimal quantities/prices, strings, booleans, and numeric IBKR sentinels. The canonical file therefore stores a provider-shaped object graph rather than a small normalized order record.
- [observed: `services/uta/src/domain/trading/git/TradingGit.ts:929-967`] A raw provider result is copied into `OperationResult.raw` for both successful and explicitly unsuccessful object responses. A thrown `executeOperation` exception is converted to a rejected result without `raw` (`TradingGit.ts:143-154`). `raw` is not redacted or provider-normalized before `exportState`.
- [observed: `services/uta/src/domain/trading/git/TradingGit.ts:572-646`; `services/uta/src/domain/trading/git/TradingGit.spec.ts:670-745`] Restore wraps known order Decimal fields and `closePosition.quantity` through `new Decimal(String(x))`, wraps position quantities, and fills missing `Position.multiplier` with `'1'`. Tests intentionally rewrite `lmtPrice` as a bare legacy number and verify it rehydrates to Decimal; reconcile fields remain strings. The rehydration list does not wrap `filledQuantity`, although `OrderHelper.toWire` treats it as a sentinel field; a persisted non-null `filledQuantity` can therefore remain a plain string after restore (inferred from the two lists).
- [observed: `scripts/migrate-order-sentinels.ts:1-22,32-35,68-86`] The hand-run sentinel migration exists outside the registry. It removes legacy `Number.MAX_VALUE` values from five price-class fields (`lmtPrice`, `auxPrice`, `trailStopPrice`, `trailingPercent`, `cashQty`) and rewrites changed files through `.tmp` + rename. It is documented as idempotent, but it does not provide a ledger journal, fsync, or a backup in the shown implementation.

### 2. In-memory lifecycle and all current ledger writers

- [observed: `services/uta/src/domain/trading/git/TradingGit.ts:61-117`] `add` appends to `stagingArea` unless an in-flight write or pending approval exists. `commit` computes an eight-character SHA-256 prefix from message, operations, preparation timestamp, and current head, then stores only `pendingMessage` and `pendingHash` in memory. `commit` does not reject a second call while a pending hash exists; a second prepare can overwrite the approval token (observed source behavior).
- [observed: `services/uta/src/domain/trading/git/TradingGit.ts:119-184`] `push` checks the expected pending hash, sets the in-memory `inflightWrite` flag, executes each operation sequentially, snapshots broker state, appends a commit to the in-memory array, moves `head`, awaits `onCommit`, then clears staging and pending fields. `inflightWrite` is reset in `finally` even when any later step fails.
- [observed: `services/uta/src/domain/trading/git/TradingGit.ts:187-249`] `reject` does no broker write but does call `getGitState`, creates an all-`user-rejected` commit, awaits `onCommit`, then clears staging/pending. The same expected-hash and in-memory lock checks apply.
- [observed: `services/uta/src/domain/trading/git/TradingGit.ts:260-376,654-690`; `services/uta/src/domain/trading/UnifiedTradingAccount.ts:844-915,964-980,1026-1086`] `recordReconcile`, `recordObservedOrders`, and `sync` append directly to `commits` and call `onCommit` without checking `inflightWrite`. Their callers perform broker reads and can overlap a user push. Each path can independently move `head` and issue a full-file persistence callback.
- [observed: `services/uta/src/domain/trading/UnifiedTradingAccount.ts:158-177`] A push's post-operation state reads account, positions, and pending orders through the broker; pending orders are filtered to `Submitted` or `PreSubmitted`. This explains why `getGitState` can fail or return a state that is not transactionally tied to the preceding provider writes.
- [observed: `services/uta/src/domain/trading/UnifiedTradingAccount.ts:793-810`] The outer `push` rejects disabled/offline accounts before delegating to `git.push`, while `reject` delegates directly. Both fire post-operation hooks asynchronously after the ledger method; hook errors are swallowed by the outer wrapper.

### 3. Today's push crash-window table

The source has no power-loss harness. The **phase/order** below is observed; consequences after a process crash are marked `[inferred]` from that order and the absence/presence of durable writes.

| Phase | Observed operations and evidence | Remote effect / durable state if the process dies here |
|---|---|---|
| Stage | `[observed: TradingGit.ts:77-91]` `add` only mutates `stagingArea`; no persistence callback runs. | `[inferred]` No broker call and no ledger bytes are required; staged operations disappear on restart. |
| Prepare approval | `[observed: TradingGit.ts:94-117]` `commit` computes and stores `pendingMessage`/`pendingHash` only in memory. | `[inferred]` No broker call and no durable intent exist; a held approval hash cannot be resumed after restart. |
| Begin write | `[observed: TradingGit.ts:119-126,241-249]` expected hash is checked and `inflightWrite=true` is set. | `[inferred]` The flag is lost on restart; it is not a durable lease or execution record. |
| Broker operation loop | `[observed: TradingGit.ts:141-155]` each operation is awaited sequentially; a caught exception becomes `success:false,status:'rejected'`, and the loop continues. | `[inferred]` Earlier provider calls may already have changed the account while no ledger record exists. A crash makes the outcome of the current call unknown; restart has no attempt key to reconcile and a retry can repeat earlier effects. If the process stays alive, a transport exception and a provider rejection both become status `rejected`, distinguished only by error text. |
| After broker loop, before state read returns | `[observed: TradingGit.ts:157-159]` `getGitState` runs after all operation calls and before commit construction. | `[inferred]` Provider effects can exist with no in-memory commit and no `onCommit` call if the state read fails or the process dies. In a surviving process, `finally` clears only `inflightWrite`; staging/pending remain and can be retried. After restart, those fields are gone. |
| In-memory commit publication | `[observed: TradingGit.ts:160-174]` commit/head are updated before `await onCommit`. | `[inferred]` A crash before persistence leaves the disk at the previous head even though provider writes and the current process's memory saw a new head. A surviving process may report the commit until it restarts. |
| Full-file persistence | `[observed: git-persistence.ts:42-48]` `onCommit` directly rewrites `commit.json`; `[observed: TradingGit.ts:174-179]` staging is cleared only after the callback resolves. | `[inferred]` A write failure leaves the new in-memory commit and pending staging in the current process, and retrying can re-execute the same operations. A crash during direct replacement can leave old, truncated, or complete-new bytes; the loader conflates read/parse failure with no saved state and may start an empty ledger (`git-persistence.ts:27-39`). No real power-loss result is available. |
| Durable callback success, before clear | `[observed: TradingGit.ts:174-179]` the callback resolves before staging/pending are cleared. | `[inferred]` If the process dies in this narrow interval, the disk contains the commit while memory-only pending state is lost with the process; restart restores the commit and does not duplicate it from staging. |
| Clear and return | `[observed: TradingGit.ts:176-184]` staging and pending become empty, then result is returned. | `[inferred]` The normal durable outcome is a new commit/head on disk and clean in-memory proposal state. There is no post-return transactional acknowledgement beyond the callback resolution. |
| Post-push fan-out | `[observed: UnifiedTradingAccount.ts:801-803]` `onPostPush` is fire-and-forget and errors are swallowed. `[observed: snapshot/service.ts:46-75]` snapshot storage and activity events are separate. | `[inferred]` A crash after ledger durability can lose a post-push snapshot or its journal event without losing the ledger commit. These side effects must not be used as confirmation of the trade. |
| Synthetic writer overlap | `[observed: TradingGit.ts:260-376,654-690]` reconcile/observed/sync bypass `inflightWrite`; `[observed: git-persistence.ts:42-48]` each callback rewrites the whole file. | `[inferred]` A synthetic callback can race a push callback; last/full write wins or bytes can overlap, and a stale in-memory export can overwrite a newer commit. The current code has no writer serialization or expected-position check. |

### 4. Other persistence surfaces that must stay separate from the trading ledger

- [observed: `services/uta/src/domain/trading/snapshot/types.ts:12-80`] Snapshots are independent full-state observations. Financial values are strings; positions include selected contract metadata; `headCommit` and `pendingCommits` are references to the TradingGit view. The snapshot index is version `1` with chunk file/count/start/end metadata.
- [observed: `services/uta/src/domain/trading/snapshot/store.ts:1-16,18-86`] Snapshot storage uses `data/trading/<accountId>/snapshots/index.json` plus `chunk-0001.jsonl`-style files (the implementation starts at `chunk-0001` because `index.chunks.length + 1`). Each chunk holds at most 50 records. Appending writes the JSONL line first, then atomically replaces the index via `${pid}.tmp` + rename; neither step calls fsync. A Promise chain serializes writes only within one store instance, and the service caches one instance per account (`snapshot/service.ts:27-43`).
- [observed: `services/uta/src/domain/trading/snapshot/store.ts:43-49,141-167`] A missing or malformed snapshot index is treated as an empty index; malformed chunk lines throw from `readRange`. If a new-chunk append dies before index replacement, the line can remain in an unindexed file. This is a useful operational precedent for chunking, not a sufficient ledger recovery contract.
- [observed: `src/core/event-log.ts:1-30,48-91,106-163`] `data/event-log/events.jsonl` is a domain-neutral JSONL journal with `{seq,ts,type,payload,causedBy?}` records. It appends to disk before updating a 500-entry in-memory tail and has no domain validation; UTA uses it for `account.health` and snapshot activity, not for trading truth (`docs/event-system.md:18-31`).
- [observed: `src/core/event-log.ts:303-344`] Event-log recovery skips malformed lines and returns the last valid parsed row's `seq`; it does not truncate/quarantine a malformed tail. A scoped runtime probe wrote one valid line followed by a truncated JSON line and reopened the log; output was `{"lastSeq":1,"read":[{"seq":1,"ts":1,"type":"ok","payload":{"x":1}}],"recent":[{"seq":1,"ts":1,"type":"ok","payload":{"x":1}}]}`.
- [observed: scoped runtime output] Two `createEventLog` instances pointed at one path, then appended concurrently, produced two physical rows both with `seq:1` (for example `{"seq":1,..."type":"a"}` and `{"seq":1,..."type":"b"}`) and both instances reported `lastSeq:1`. This demonstrates why the new ledger cannot copy event-log's per-instance sequence recovery as its concurrency contract.
- [observed: `services/uta/src/domain/trading/uta-manager.ts:61-77`; `services/uta/src/main.ts:67-110`] `account.health` append is not awaited. Snapshot hooks are installed after all accounts are initialized: `initUTA` captures `onPostPush`/`onPostReject` at lines 64-77, while `setSnapshotHooks` occurs at lines 102-108. Existing accounts therefore receive `undefined` hooks unless another path replaces them (inferred from the one-time capture); this is a fan-out wiring issue, not a ledger durability guarantee.

### 6. Locking and durability primitives

- [observed: `packages/guardian-runtime/src/runtime-lock.ts:183-231`] `acquireRuntimeLock` creates a lock directory with atomic `mkdir`, writes owner metadata atomically, waits or returns a structured already-running error, and can reclaim dead owners after PID/start-time/token checks. - [observed: `install:411-432`; `docs/cli-installer.md:12-18`; `packages/cli/src/install.spec.mjs:246-273`] The shell installer requires `lockf` or `shlock` on macOS and `flock` on Linux; tests cover the macOS fallback. - [observed: scoped Node output] On this Darwin host, `FileHandle.sync` and `FileHandle.datasync` were functions, and opening/syncing `os.tmpdir()` returned `directorySync:"ok"` under Node `v26.8.1`. `[unavailable]` No Windows runtime or true power-loss test was run, so a Windows directory-sync policy is not established.

## Recommendations

### A. Candidate append-only ledger persistence contract

The following is a design candidate, not an observed implementation. It is intended to satisfy the already-approved ledger constraints (`plans/uta-refactor/design/00-core-contract.md:45-83`; `plans/uta-refactor/design/01-detail-constraints.md:54-102,235-258`).

- [inferred/recommendation] **Ownership and layout:** one UTA process owns one account stream; all ledger writes go through one per-account writer queue and one per-account lock. Use a layout such as:
  ```text
  data/trading/<accountId>/ledger/manifest.json
  data/trading/<accountId>/ledger/segments/segment-000001.jsonl
  data/trading/<accountId>/ledger/checkpoints/   # derived, source cursor/hash included
  data/trading/<accountId>/ledger/quarantine/    # preserved corrupt/torn bytes
  data/trading/<accountId>/ledger.lock/          # ephemeral owner/lease metadata
  ```
  Keep the old `commit.json` as an immutable migration archive until verification completes; do not dual-write it after cutover.
- [inferred/recommendation] **Storage envelope:** each physical line should contain a versioned envelope around a provider-indexed entry: `schemaVersion`, `streamId`, `position`, stable `entryId`, `occurredAt`, `recordedAt`, `source`, extensible `kind`, required structured `why`, required `idempotencyKey`, opaque provider/kind payload, `prevHash`, and a full-length `recordHash`. Preserve provider raw bytes/JSON at the translation boundary; do not normalize every provider into the old IBKR object graph.
- [inferred/recommendation] **Framing and integrity:** serialize a canonical body with sorted keys; store `byteLength` as UTF-8 byte count and `checksum = SHA-256(canonical body bytes)` in the outer frame. Include `prevHash` in the hashed body and use a full SHA-256 record hash rather than today's eight-hex commit prefix. The reader must validate UTF-8 length, JSON, position, checksum, and hash chain before exposing a record.
- [inferred/recommendation] **Batch commit boundary:** if an append contains more than one business entry, write immutable business frames followed by an immutable storage-level `batch.commit` marker containing the range and final hash. Consumers expose a batch only after its marker is durable. The marker is persistence metadata, not a provider fact or a substitute for `Intent`/`Attempt`/`Receipt`/`Observation`.
- [inferred/recommendation] **Append API and CAS:** `append(entries, expectedPosition)` must acquire the account lock, read the durable manifest tail, and return a structured `Conflict {expectedPosition, actualPosition, actualHash}` on mismatch. Never overwrite or reorder on a stale expected position. Allocate positions only under the lock and return a structured `DurabilityFailure` if the append cannot reach its durability acknowledgement.
- [inferred/recommendation] **Durability ordering:** write frames, call `FileHandle.sync()` on the segment, write/rename the manifest atomically, fsync the containing directory when supported, then resolve the append and publish consumer notifications. The current Darwin probe demonstrates the needed Node methods in this environment, but Windows needs an explicit tested fallback and acknowledgement policy. Notifications, snapshots, and activity events must follow durable ledger acknowledgement rather than precede it.
- [inferred/recommendation] **Torn-tail policy:** recovery scans only the contiguous valid prefix. A malformed, short, length-mismatched, checksum-invalid, or uncommitted final frame must produce an explicit `TornTail`/`UncommittedTail` recovery result, preserve the original bytes in quarantine, and never be silently treated as “no record.” Interior corruption or a broken hash chain must fail the account's ledger open with a structured corruption error; do not skip forward. A valid frame without a durable batch marker is not exposed until the recovery policy explicitly classifies/promotes it.
- [inferred/recommendation] **Single-writer lock:** reuse/adapt `acquireRuntimeLock`'s directory lock, owner token, heartbeat, process identity, stale reclamation, and Windows rename retry behavior for a per-account ledger lock. Do not rely on the global runtime lock as the ledger contract, and do not assume the installer’s `flock`/`lockf` shell path exists inside a packaged Node service. The in-process queue and cross-process lock are complementary: the queue orders local tasks; CAS protects stale writers.
- [inferred/recommendation] **Replay and views:** replay entries by persisted position, not local timestamp or directory order. Keep `Intent`, `Attempt`, `Receipt`, and `Observation` as distinct variants; a receipt is never an upstream fact. Unknown kinds remain in the stream and in an observable unconsumed set. Store materialized account/order views and checkpoints separately with `sourcePosition`/`sourceHash`; a view failure must leave the ledger untouched and trigger rebuild on restart.
- [inferred/recommendation] **Provider retry gate:** every provider write capability must declare idempotent placement and read-by-key support. A retry after an unknown provider outcome is automatic only when the declared capability makes it safe; otherwise the ledger records `Unknown` and waits for reconciliation/manual action. This is required by the design constraints (`plans/uta-refactor/design/01-detail-constraints.md:225-233`) and is not inferable from the old `success:boolean` result.

### B. Candidate crash matrix for `Intent → Attempt → Receipt → Observation`

The rows describe the recovery contract to implement; they are recommendations, not current behavior.

| Durable point at crash | Possible upstream effect | Restart action | Automatic retry rule |
|---|---|---|---|

### C. Migration cutover recommendation

- [inferred/recommendation] Add registry migration `0044_*` rather than reusing a retired ID. Use `ctx.userDataHome()` plus explicit `resolve(home, 'data', 'trading')` traversal; do not call `ctx.writeJson` for ledger bytes because it resolves under `data/config/`.
- [inferred/recommendation] Before converting an account, acquire its ledger/runtime ownership lock or require the UTA process to be stopped. Decode the old state strictly, write the new immutable segments and manifest through temp files plus fsync/rename, verify positions/hash/checksum, then write a per-account completion marker. Keep the old `commit.json` in an explicit archive until all verification is complete.
- [inferred/recommendation] Supply an explicit migration backup strategy for `data/trading/`; the runner's default backup omits it. A migration that touches all account directories must account for ephemeral accounts, whose pre-manager purge occurs after `loadConfig` migrations (`services/uta/src/main.ts:56-87`).
- [inferred/recommendation] On rerun, detect a verified completion marker and no-op; detect a partially written new ledger and resume or quarantine it; never append a second conversion of the same old commit. Only after all accounts pass verification should normal startup treat the new ledger as canonical. The migration journal is not a substitute for per-account progress because the runner writes one global ID only after `up` returns.

# Provider capability feasibility (A7 / OpenAPI projection)

## Decision questions answered

1. **Which current engine/venue combinations satisfy the new mandatory A7 pair (idempotent placement + read-by-key), and the observation requirement?**
   - **Observed — repository boundary:** `IBroker.placeOrder` has no caller-supplied idempotency key, `getOrder` accepts only an order ID plus optional symbol hint, and no `IBroker` method accepts or returns a resumable observation cursor (`packages/uta-protocol/src/types/broker.ts:528-531,569-577`; `:479-622`).
   - **Observed — adapter consequence:** no one of the six current adapters exposes caller-keyed placement through the `IBroker` contract. Alpaca, CCXT, IBKR, Longbridge, LeverUp, and Mock all generate or consume provider/process order IDs instead (`services/uta/src/domain/trading/brokers/alpaca/AlpacaBroker.ts:304-318`; `services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:524-530`; `services/uta/src/domain/trading/brokers/ibkr/IbkrBroker.ts:491-502`; `services/uta/src/domain/trading/brokers/longbridge/LongbridgeBroker.ts:271-304`; `services/uta/src/domain/trading/brokers/others/leverup/LeverupBroker.ts:245-305`; `services/uta/src/domain/trading/brokers/mock/MockBroker.ts:278-305`).
   - **Inferred — decision:** no current adapter should be declared A7-conforming for mandatory idempotent placement, keyed read, and resumable observation. Provider primitives below are migration evidence, not current adapter capabilities.
2. **Is one OpenAPI projection a viable provider input?**
   - **Observed — official specs:** a machine-readable Alpaca Trading API OAS 3.1.2 and IBKR Client Portal/Web API OAS 3.1.0 were retrieved and parsed (`https://docs.alpaca.markets/us/openapi/trading-api.json`; `https://www.interactivebrokers.com/docs/openapi/api-reference.json`).
   - **Observed — official non-OAS docs:** Longbridge, OKX, Bybit, Bitget, Hyperliquid, and LeverUp publish readable HTTP/WS or intent schemas, but an independently downloadable OAS/Swagger artifact was not established in this evidence pass (`local://w1-official-venue-docs.md:14-24`). Binance official pages returned empty content and remain an evidence gap (`local://w1-official-venue-docs.md:17-18,59-63`).
   - **Inferred — decision:** use OAS as a REST description where available, but do not make it the universal transport abstraction. Add a versioned provider description with explicit extensions for capability semantics, WS/session lifecycle, TCP callbacks, and on-chain events. Each projection may retain provider-specific schemas; only the A7 envelope and declared capability facts are common.
3. **What must be preserved at the pack boundary?**
   - **Observed:** packs are dynamically loaded JavaScript modules that return an `IBroker`, validated only by API version, engine name, `configSchema`, and `createBroker` (`services/uta/src/domain/trading/brokers/registry.ts:23-33,69-128`).
   - **Inferred:** the new capability declaration, provider-indexed operation/receipt/observation envelope, raw payload/error retention, and resource acquire/release semantics must become an explicit pack contract. `BROKER_PACK_API_VERSION=1` alone does not express those facts.

## Scope and evidence notation

- **Observed** means the cited repository path/line range or official URL was read. **Inferred** means a recommendation or conclusion derived from those observations. **Unknown** means the inspected evidence did not establish a fact; it is not a claim that a provider lacks the capability.
- The matrix separates **provider primitive** from **current adapter exposure**. A provider field, SDK declaration, REST page, or WS feed does not prove the current adapter forwards it.
- **Inferred cursor criterion:** for A7, an observation cursor needs a stable ordering/checkpoint, a way to resume after reconnect, and an explicit gap/backfill rule. The design requires a resumable cursor/checkpoint and end reason; a consumed page token, request ID, or timestamp used only for OHLCV bars is not sufficient (`plans/uta-refactor/design/01-detail-constraints.md:109-113`).
- Provider documents were read with `agent-browser` because direct URL reader access was unavailable. No authenticated order, live trade, or sandbox trade was issued in this investigation (`local://w1-official-venue-docs.md:3-8`).

### Matrix reading and first migration candidate

- **Inferred:** Alpaca is the strongest first migration candidate because one official OAS supplies keyed order lookup plus activity SSE replay and separate market/trade WS descriptions. The adapter still needs a caller key, client-key read, cursor persistence, raw-event retention, and gap handling before declaration.
- **Inferred:** Longbridge has the clearest timed idempotency contract (10-minute cached response), but no documented client-key lookup. A local key→order-ID record alone cannot guarantee recovery if the process fails before that record persists; it therefore does not satisfy mandatory keyed read without an explicit provider/read-back or durable intent/receipt strategy.
- **Inferred:** CCXT must be split by venue and account family. Bybit, OKX, Bitget, Hyperliquid, and Binance are not one capability tuple; the current overrides only repair selected REST namespace quirks and do not turn CCXT into a WS/cursor/idempotency adapter.
- **Inferred:** IBKR CP Web API evidence cannot be assigned to the current IBKR TWS engine. A future CP adapter and current TWS adapter need separate declarations.
- **Inferred:** LeverUp’s intent hash is a useful provider receipt/status key, but it is not evidence of caller-keyed placement or a resumable observation stream.

## Pack-loading facts

- **Observed:** Mock is the only built-in engine; installable engines are `ccxt`, `alpaca`, `ibkr`, `leverup`, and `longbridge` (`services/uta/src/domain/trading/brokers/registry.ts:1-6,44-50`; `src/core/broker-packs.ts:10-21`).
- **Observed:** `loadBrokerEngine` caches a load promise and deletes the cache entry on failure; Mock is constructed directly, while installable engines resolve an active release or an explicitly allowed workspace pack (`services/uta/src/domain/trading/brokers/registry.ts:52-114`).
- **Observed:** loaded module validation requires `BROKER_PACK_API_VERSION`, matching `BROKER_ENGINE`, `configSchema`, and `createBroker`; no capability manifest, transport description, operation identity, cursor, or raw-payload contract is validated (`services/uta/src/domain/trading/brokers/registry.ts:118-128`).
- **Observed:** release resolution validates active pointer schema/engine, realpath containment, manifest schema/API/version/content ID, package name/version identity, and entry containment (`src/core/broker-packs.ts:23-45,86-135,151-179`).
- **Observed:** wrappers are thin forwarding modules. For example, CCXT exports API version/engine/schema and calls `CcxtBroker.fromConfig`; analogous wrappers exist for Alpaca, IBKR, LeverUp, and Longbridge (`packages/uta-broker-ccxt/src/index.ts:1-9`; `packages/uta-broker-alpaca/src/index.ts:1-9`; `packages/uta-broker-ibkr/src/index.ts:1-9`; `packages/uta-broker-leverup/src/index.ts:1-9`; `packages/uta-broker-longbridge/src/index.ts:1-9`).
- **Observed:** factory maps persisted preset → engine config → pack and returns `IBroker`; only `setFxService` is duck-typed as an optional service (`services/uta/src/domain/trading/brokers/factory.ts:26-47`).
- **Observed:** Alpaca pack bundles all dependencies (`noExternal: [/.*/]`), while CCXT/IBKR/LeverUp/Longbridge externalize ordinary node modules and bundle selected workspace/protobuf patterns (`packages/uta-broker-alpaca/tsup.config.ts:1-10`; `packages/uta-broker-ccxt/tsup.config.ts:1-15`; analogous `tsup.config.ts:1-7` in the other packs).
- **Observed:** docs explicitly prohibit class-identity assumptions across pack dependency trees and recommend `Decimal.isDecimal` plus stable error codes instead of cross-package `instanceof` (`docs/broker-packs.md:67-77`). Every inspected adapter imports `Decimal` from `decimal.js`, and Longbridge also declares a native Decimal while the adapter casts decimal.js values at the SDK boundary (`services/uta/src/domain/trading/brokers/longbridge/LongbridgeBroker.ts:297-301`; `services/uta/node_modules/longbridge/index.d.ts:220-320`).
- **Inferred:** a new pack ABI must cross only serializable provider-indexed records (decimal strings, stable IDs, tagged errors, raw envelopes), not `Decimal`, `Contract`, SDK, or other class instances. This avoids duplicate dependency identity and permits a Rust process/FFI/WASM implementation later.
- **Inferred:** a Rust core cannot directly load these JavaScript dynamic wrappers. It needs a declared serialized process/IPC, FFI, or WASM boundary; an Effect-based TypeScript core can host them directly but should still isolate pack resources and errors behind a serializable boundary so the provider description remains transport-independent.

## Recommendations

All items in this section are **Inferred** from the observed constraints and matrix; they are not implementation changes in this report.

1. **Declare capability at the engine/venue/account tuple, not at a class or method.** The tuple should include provider identity/version, transport family, supported downstream channels/kinds, and explicit `supported`/`unsupported` witnesses for idempotent placement, read-by-key, observation cursor, market watch, and account/order watch. A method existing is not evidence of a capability (`plans/uta-refactor/design/00-core-contract.md:65-75`; `01-detail-constraints.md:220-225`).
2. **Make the two mandatory capabilities semantic, not merely field-shaped.** For placement, declare the key location, generation rule, duplicate behavior, same-key/different-payload behavior, retention, and whether the provider returns the original receipt. For keyed read, declare key kind, scope, lookup endpoint, terminal/history coverage, and symbol/account disambiguation. If any fact is unknown, declare the capability unavailable until verified rather than silently treating a provider ID as a client key.
3. **Treat observation as its own capability pair.** Declare channel (`order`, `fill`, `account`, `market`), provider event identity/order, checkpoint encoding, reconnect behavior, gap detection, REST backfill, retention, end reasons, and acquire/release. A REST page cursor or OHLCV timestamp is a provider pagination fact, not automatically a resumable event cursor.
4. **Use OAS as a source description for HTTP, not as the whole provider model.** Preserve the source OAS version/hash and operation IDs. Add a namespaced extension (for example, an `x-uta` capability block) for key semantics, duplicate policy, provider-indexed result/receipt types, cursor/replay facts, raw error fields, and lifecycle ownership. Do not force `clOrdId`, `orderLinkId`, `client_request_id`, `cOID`, `clientOid`, and `cloid` into one provider field type or imply equivalent retention.
5. **Add a separate stream/session description.** OpenAPI can describe REST request/response/error/pagination; an AsyncAPI-like or provider-specific stream manifest should describe WS topics, authentication, snapshots, deltas, event identity, reconnect, and gap/backfill. TWS TCP callbacks, Longbridge protobuf sockets, and LeverUp on-chain logs need transport plugins implementing the same capability witness, not fake REST operations.
6. **Handle SDK-only CCXT explicitly.** Treat each configured venue/account family as a separate provider projection. A CCXT `has` flag, override, or `extraParams` entry may be evidence for an adapter implementation but is not the official venue contract. `ccxt-custom` must remain unknown until its concrete exchange and version are resolved; never declare the generic engine's capabilities globally.
7. **Keep the current IBKR transport split visible.** The Client Portal/Web API OAS and cOID evidence can support a new CP adapter. The current TWS adapter uses numeric order IDs and framed TCP; assigning CP cOID semantics to it would be an architecture-by-accident error.
8. **Prefer Alpaca as the first end-to-end proof.** Its OAS, keyed order lookup, activity SSE replay, market WS, and trade-update WS give the clearest source material. The first proof must still exercise the adapter with a generated key, timeout/unknown outcome, client-key read, SSE checkpoint/reconnect, raw-event retention, and gap handling in paper/sandbox; no such runtime trade was performed here.
9. **Treat Longbridge’s 10-minute idempotency as time-bounded.** Persist the provider receipt and local intent relation before/alongside the attempt, and declare the post-expiry keyed-read limitation explicitly. Do not advertise permanent idempotency or client-key lookup from `remark` or from `order_id`.
10. **Make the pack ABI serializable and effect/resource explicit.** In TypeScript, an Effect layer can own acquire/release, retries, structured errors, and stream interruption. In Rust, expose the same records over IPC/FFI/WASM. In either runtime, cross the pack boundary with strings/records/tags, not `Decimal` or SDK/class identities; retain raw provider payloads for later reparse.
11. **Use explicit unsupported witnesses during migration.** Existing `getOpenOrders` empty-on-unsupported behavior and empty `close()` methods must not be reused to claim new capabilities. Until an adapter implements the declared witness, downstream composition should receive `Unsupported` (or a typed unavailable capability) and the ledger should distinguish not-written, rejected, transport-unknown, and observed states.

## Unavailable / contradictions

- **Unknown — Binance:** official Spot and USDⓈ-M pages returned empty content from the current environment; idempotency, keyed reads, cursor/replay, WS, and OAS availability were not established. This is an evidence-retrieval gap, not a claim that Binance lacks them (`local://w1-official-venue-docs.md:17-18,59-63`).
- **Unknown — runtime provider behavior:** no authenticated provider request, duplicate submission, reconnect, stream gap, or sandbox trade was run. Documentation fields and SDK declarations do not prove account entitlement, current server behavior, or current adapter wiring.
- **Observed contradiction:** the legacy `IBroker.getOpenOrders` comment says unsupported venues return an empty array and never throw (`packages/uta-protocol/src/types/broker.ts:579-586`), while the new detail constraints prohibit empty/no-op/undefined from masquerading as unsupported or complete (`plans/uta-refactor/design/01-detail-constraints.md:222,231-233`). CCXT concretely returns `[]` for non-strict open-order failures (`services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:1209-1219`).
- **Observed contradiction:** Longbridge config passes `quoteWsUrl`/`tradeWsUrl` into SDK construction (`LongbridgeBroker.ts:188-200`), and the SDK declares callback/subscription APIs, but the adapter only uses request/response methods and never registers a stream (`LongbridgeBroker.ts:193-207,631-653`). URL configuration is therefore not WS capability exposure.
- **Observed distinction:** Alpaca’s activity SSE explicitly replays historical then new activity, while its trade-update WS replay cursor was not established. These must not be collapsed into “Alpaca WS is resumable” (`https://docs.alpaca.markets/us/openapi/trading-api.json`; `https://docs.alpaca.markets/us/docs/websocket-streaming.md`).
- **Observed distinction:** OKX permits terminal `clOrdId` reuse and latest-match lookup, so a client key is not necessarily a forever-unique business identity (`https://www.okx.com/docs-v5/en/`).
- **Observed distinction:** Bybit, Bitget, Hyperliquid, Alpaca, Longbridge, IBKR, and OKX each expose different key, scope, retention, and stream semantics. No common field name should be treated as a common idempotency law.
- **Observed limitation:** the current pack loader validates module shape and API version, not provider capabilities or serialized ABI (`services/uta/src/domain/trading/brokers/registry.ts:23-33,118-128`). This report proposes that as a future contract; it does not claim it exists today.
- **Observed limitation:** pack dependency trees can have separate class identities; repository guidance explicitly directs callers to `Decimal.isDecimal` and stable error codes (`docs/broker-packs.md:67-77`). No runtime duplicate-Decimal experiment was run in this slice.

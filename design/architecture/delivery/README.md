# 订阅投递

负责持久订阅、各流的已确认位置与投递缺口；不负责记录怎样保存，也不负责消费方拿到记录后做什么。

## 依据

消费方的消费速度与核心的保留边界各自独立推进，慢消费方可能在确认之前就被压缩越过（来源：外部场所能力调查，证据见附录 `evidence/venue-facts.md`）。所以 ``Delivery`DeliveryGap`` 先于记录写在订阅上并随投递交出，直到 ``Delivery`Ack`` 确认越过它才消失；流本身不因此多出或少掉任何记录。

## 为什么

订阅表单独成子模块：它只用到父模块的 ``Observation`ReadFrom`` 与 ``Observation`RetentionOf``，父模块不需要知道有谁在消费、消费到哪里。不选让消费方自己记游标：断连重连后只有核心能按订阅续投，且投递缺口必须在跳过之前被持久写下。

## 语义

订阅的生命周期归核心所有，与下游会话的连接无关：会话断开时订阅与游标保留，重连后从已确认位置续投。程序作为核心内的消费方同样持有订阅，``Delivery`Ack`` 与程序检查点在同一次提交中生效。

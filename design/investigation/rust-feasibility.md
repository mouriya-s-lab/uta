# Rust ecosystem feasibility for the rewritten UTA

## 15-line summary
1. Scope: B1-B7 and D01-D08 require a parallel subscription/distribution core, isolated programs, durable effects, and a new streaming integration boundary ([problem](file://../01-problem.md#L132-L157)).
2. Runtime: Tokio 1.53.1 has a configurable multi-thread scheduler, but its documentation makes CPU-work bounds and benchmark adequacy application responsibilities ([runtime](https://docs.rs/tokio/1.53.1/tokio/runtime/struct.Builder.html#method.worker_threads)).
3. Cancellation: tokio-util 0.7.19 supplies hierarchical, cancel-safe cancellation requests; it does not force arbitrary task cleanup or persist state ([token](https://docs.rs/tokio-util/0.7.19/tokio_util/sync/struct.CancellationToken.html)).
4. Queues: Tokio bounded mpsc gives backpressure and one-consumer FIFO, while cancelled sends and non-durable acknowledgements must be handled explicitly ([mpsc](https://docs.rs/tokio/1.53.1/tokio/sync/mpsc/fn.channel.html)).
5. Fan-out: Tokio broadcast clones to active receivers but overwrites lagging values and returns `Lagged(n)`, so it is not the durable subscription bus ([broadcast](https://docs.rs/tokio/1.53.1/tokio/sync/broadcast/index.html#lagging)).
6. Sharding: DashMap 6.2.1 exposes configurable power-of-two shards, but no CPU affinity, per-instrument serialization, or business ordering ([DashMap](https://docs.rs/dashmap/6.2.1/dashmap/struct.DashMap.html#method.with_shard_amount)).
7. WASM limits: Wasmtime 48.0.2 provides deterministic fuel, resource limiters, import auditing, and component/WIT bindings ([fuel](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Config.html#method.consume_fuel)).
8. WASM state/effects: no documented arbitrary live `Store` checkpoint/restore was found; Wizer only snapshots initialization, and WIT describes contracts rather than behavior ([Wizer](https://docs.rs/wasmtime-wizer/48.0.2/wasmtime_wizer/struct.Wizer.html), [WIT](https://component-model.bytecodealliance.org/design/wit.html)).
9. RPC: tonic 0.14.6 plus prost 0.14.4 directly supports typed gRPC bidirectional streams and custom IO, satisfying the independent-binary boundary ([tonic](https://docs.rs/tonic/0.14.6/tonic/client/struct.Grpc.html#method.streaming), [prost](https://docs.rs/prost/0.14.4/prost/)).
10. UDS: native tonic/Tokio UDS is documented for Unix and tonic's Windows branch returns `uds connections are not allowed on windows`; use cfg adapters, named pipes, or loopback TCP ([source](https://docs.rs/tonic/0.14.6/src/tonic/transport/channel/uds_connector.rs.html)).
11. Log: okaywal 0.3.1 is the closest ready-made segmented CRC/fsync WAL but explicitly warns that its format is unstable and not production-ready ([warning](https://docs.rs/okaywal/0.3.1/okaywal/index.html)).
12. Durable fallback: a Rust-std `sync_all`/same-directory `rename` protocol plus crc32fast can be hand-rolled, but crash ordering and recovery remain UTA-owned ([sync_all](https://doc.rust-lang.org/std/fs/struct.File.html), [rename](https://doc.rust-lang.org/std/fs/fn.rename.html)).
13. Numbers: rust_decimal 1.43.0 is bounded fixed-scale with checked arithmetic; bigdecimal 0.4.10 is flexible but warns about complexity and huge-exponent resource failure ([rust_decimal](https://docs.rs/rust_decimal/1.43.0/rust_decimal/struct.Decimal.html), [bigdecimal](https://docs.rs/bigdecimal/0.4.10/bigdecimal/index.html)).
14. Analytics/lifecycle: ta/yata are incremental, RustQuant/black_scholes are value-in/value-out Greeks, and Tokio plus process-wrap/fs2 can form a supervisor only with a hand-written state machine ([ta](https://docs.rs/ta/0.5.0/ta/trait.Next.html), [process-wrap](https://docs.rs/process-wrap/10.0.0/process_wrap/)).
15. Verdict: no Rust-only infeasibility is proven; [INFERENCE] agents can write this stack with compiler/runtime evidence, but Rust-SWE-bench reports only 21.2% issue resolution for agents and is not UTA-semantic evidence ([paper](https://arxiv.org/abs/2602.22764)).

## Scope, provenance, and evidence method

This is an ecosystem-feasibility investigation for the **new** UTA design. It is not a claim that the current TypeScript UTA already has any of the Rust crate capabilities below. The new requirements are recorded verbatim in `../01-problem.md:132-138` (B1-B7), and the derived safety requirements are at `:149-157` (D01-D08). The constraints are a complete rewrite, an independent binary/process, serialized text or cross-language RPC, and Rust first at `:142-143`.

The current repository is used only where it exposes a relevant existing lifecycle fact. The Guardian comment says a Windows `ChildProcess` can point at a `cmd.exe` wrapper while the real `node`/`tsx` child keeps the port, and that `child.kill()` can orphan it (`scripts/guardian/shared.ts:268-279`). The restart path marks expected exit, sends `SIGTERM`, waits 8 seconds, escalates to `SIGKILL`, waits 5 seconds, respawns, and waits up to 15 seconds for health (`scripts/guardian/shared.ts:495-523`). Those are **observed existing behaviors**, not requirements that the rewrite must copy verbatim.

Release dates below are the `created_at` timestamps from the official crates.io version API. A row's exact metadata fragment is shown as `num` and `created_at`; `yanked=false` and download counts were also observed on the queried version endpoints. Download counts and docs coverage are maturity signals only; they do not prove correctness, performance, or semantic fit. Capability quotes come from pinned docs.rs, Rust standard-library, Bytecode Alliance, Microsoft, gRPC, protobuf, or RFC pages.

## 1. Async runtime, structured cancellation, and task supervision

### Chosen crates and direct capability

**Tokio 1.53.1** is the leading runtime. Its crate page describes it as “Tokio is an event-driven, non-blocking I/O platform for writing asynchronous applications with the Rust programming language” ([docs](https://docs.rs/tokio/1.53.1/tokio/index.html)). The multi-thread builder says “Sets the number of worker threads the Runtime will use,” with the default “the number of cores available to the system” ([worker_threads](https://docs.rs/tokio/1.53.1/tokio/runtime/struct.Builder.html#method.worker_threads)). This directly addresses B1's objection to a pure single-thread core, but it is only a mechanism; no quote promises UTA's target bars/sec or latency.

For CPU-heavy indicator work, Tokio explicitly warns: “issuing a blocking call or performing a lot of compute in a future without yielding is problematic,” and recommends a semaphore or other synchronization to limit concurrent CPU computations; it also names specialized CPU executors such as Rayon ([`spawn_blocking`](https://docs.rs/tokio/1.53.1/tokio/task/fn.spawn_blocking.html)). The same documentation says started `spawn_blocking` tasks “cannot be aborted” and continue normally. Therefore, [INFERENCE] indicator evaluation belongs in bounded dedicated workers, not arbitrary unbounded `spawn_blocking`; benchmark B1's real mix before selecting worker counts.

**tokio-util 0.7.19 `CancellationToken`** is the structured notification primitive. It is “a token which can be used to signal a cancellation request to one or more tasks”; `cancel()` “will wake up all tasks which are waiting for cancellation” ([overview/cancel](https://docs.rs/tokio-util/0.7.19/tokio_util/sync/struct.CancellationToken.html#method.cancel)). `child_token()` propagates parent-to-child while “cancelling a child token does not cancel the parent” ([child](https://docs.rs/tokio-util/0.7.19/tokio_util/sync/struct.CancellationToken.html#method.child_token)), and `cancelled()` is explicitly “cancel safe” ([cancelled](https://docs.rs/tokio-util/0.7.19/tokio_util/sync/struct.CancellationToken.html#method.cancelled)).

Known limitation: the docs warn “cancellation is not an atomic operation” while also guaranteeing that all child nodes are cancelled when `cancel()` returns. This is a request/wake protocol, not forced termination, durable state, or reconnect. A task blocked in a non-cooperative host call can remain alive. [INFERENCE] D04 therefore needs explicit `select!` cleanup and an acknowledgement/drain state above the token; D05/D06 recovery is outside it.

**Tokio 1.53.1 `JoinSet`** is a useful local supervisor: it is “a collection of tasks spawned on a Tokio runtime”; the set “is not ordered, and the tasks will be returned in the order they complete” ([docs](https://docs.rs/tokio/1.53.1/tokio/task/struct.JoinSet.html)). Dropping it immediately aborts all tasks. `abort_all()` “does not remove the tasks” and callers should join until empty ([`abort_all`](https://docs.rs/tokio/1.53.1/tokio/task/struct.JoinSet.html#method.abort_all)); `shutdown()` aborts and waits, but “ignores any panics in the tasks shutting down” ([`shutdown`](https://docs.rs/tokio/1.53.1/tokio/task/struct.JoinSet.html#method.shutdown)). `JoinError::is_panic()` and `is_cancelled()` distinguish those outcomes ([panic](https://docs.rs/tokio/1.53.1/tokio/task/struct.JoinError.html#method.is_panic), [cancel](https://docs.rs/tokio/1.53.1/tokio/task/struct.JoinError.html#method.is_cancelled)).

Concrete risks: completion order is intentionally nondeterministic, dropping a set can abort unrelated programs, and task-level panic classification is not a memory/process sandbox. A program that must not affect another program/account needs a WASM or child-process boundary, not merely `JoinSet`. Fallback: use `CancellationToken` in each scope, retain one supervisor-owned `JoinSet`, join every result, and record explicit expected/crash/timeout/unknown outcomes.

### Requirement judgment

- **B1/D04: feasible as assembled primitives.** Tokio supplies runtime and task lifecycle, but CPU bounds and high-rate adequacy remain unknown until a workload benchmark.
- **D05/D06: not supplied by the runtime.** Cancellation only controls local task lifetime; subscription identity, cursor persistence, replay, and gap events must be in the core/integration protocol.
- **D01: do not use task cancellation as evidence that a venue write did not happen.** The remote outcome is a separate ledger/integration state.

## 2. Bounded channels, backpressure, and fan-out

### Single-consumer queue

Tokio `mpsc::channel` 1.53.1 directly provides “a bounded mpsc channel for communicating between asynchronous tasks with backpressure”; it buffers up to the given number, and “Once the buffer is full, attempts to send new messages will wait until a message is received from the channel” ([channel](https://docs.rs/tokio/1.53.1/tokio/sync/mpsc/fn.channel.html)). It supports cloned senders but “Only one Receiver is supported.” The same docs promise “All data sent on Sender will become available on Receiver in the same order as it was sent.”

`Sender::send` says “a return value of Ok does not mean that the data will be received,” and cancellation of a pending send “makes you lose your place in the queue” ([sender](https://docs.rs/tokio/1.53.1/tokio/sync/mpsc/struct.Sender.html#method.send)). `Receiver::recv` is cancel-safe and guarantees that no message was received if its `select!` branch loses ([receiver](https://docs.rs/tokio/1.53.1/tokio/sync/mpsc/struct.Receiver.html#method.recv)). `try_send` returns immediately when full ([try_send](https://docs.rs/tokio/1.53.1/tokio/sync/mpsc/struct.Sender.html#method.try_send)).

Direct fit: one bounded queue per deterministic instrument owner gives B1 backpressure and B5 per-channel order. Limitation: FIFO is only the scope of that channel; it is not a global order across channels or a cross-channel timestamp alignment. [INFERENCE] Attach an explicit sequence/decision ID and use `reserve`/`Permit` where a cancelled send must not lose its place. Persist events separately for D05/D06.

### Multi-consumer broadcast

Tokio `broadcast` is “a multi-producer, multi-consumer broadcast queue. Each sent value is seen by all consumers”; values are stored once and cloned on demand ([module](https://docs.rs/tokio/1.53.1/tokio/sync/broadcast/index.html)). It is bounded: if full, “the oldest value currently held by the channel is overwritten,” and a lagging receiver gets `RecvError::Lagged`; “the error carries the number of messages that were dropped” ([lagging](https://docs.rs/tokio/1.53.1/tokio/sync/broadcast/index.html#lagging)). `send` returning `Ok` only means there is at least one active receiver; it does **not** mean every receiver will observe the value ([sender](https://docs.rs/tokio/1.53.1/tokio/sync/broadcast/struct.Sender.html#method.send)). Resubscribe starts at the current tail and does not replay queued values ([resubscribe](https://docs.rs/tokio/1.53.1/tokio/sync/broadcast/struct.Receiver.html#method.resubscribe)).

This is a good ephemeral live fan-out, not the durable subscription bus required by D05. Concrete risk: a slow UI, alert, or program subscriber can miss market data while the producer succeeds; ignoring `Lagged(n)` continues from an incomplete state. Fallback: treat `Lagged(n)` as a first-class gap; reload a durable snapshot/log from a cursor or force an explicit resync. Do not use broadcast alone for effects or ledger decisions.

## 3. Sharded per-instrument state across cores

**DashMap 6.2.1** is the leading off-the-shelf sharded map. Its docs call it “an implementation of a concurrent associative array/hashmap in Rust” and a direct replacement for `RwLock<HashMap<K, V>>`; all methods take `&self`, allowing an `Arc<DashMap<...>>` shared across threads ([overview](https://docs.rs/dashmap/6.2.1/dashmap/struct.DashMap.html)). `with_shard_amount` “creates a new DashMap with a specified shard amount”; the amount must be greater than zero and a power of two ([shard count](https://docs.rs/dashmap/6.2.1/dashmap/struct.DashMap.html#method.with_shard_amount)). Raw shard access requires the `raw-api` feature and the docs warn it should generally not be used unless the caller knows what it is doing ([shards](https://docs.rs/dashmap/6.2.1/dashmap/struct.DashMap.html#method.shards)).

Direct capability: concurrent lookup/update with configurable sharding. Known limitation: the docs do not promise CPU affinity, map-shard-to-core placement, serialization of updates to one key, or business/event order. A map guard is also a synchronous lock boundary; [INFERENCE] holding it across an async wait can block unrelated runtime work. The 37.7% docs coverage is a quality signal, not a correctness or throughput guarantee.

Recommended fallback for UTA state: deterministic hash(instrument identity) to one of N owner tasks, each with a bounded Tokio mpsc queue; only the owner mutates that instrument's state and indicator instances. This is [INFERENCE] derived from the one-consumer/backpressure contract above, not a claim made by DashMap. Use DashMap only for short-lived registries/lookup state where concurrent access is genuinely required. `parking_lot 0.12.5` is an optional lock primitive whose docs promise at most one writer and a fair policy ([RwLock](https://docs.rs/parking_lot/0.12.5/parking_lot/type.RwLock.html)), but it does not supply sharding or ordering.

Verdict: Rust can express the sharded state, but the deterministic owner-task arrangement is safer for B1/B5 than allowing concurrent writes to a shared map. Core-count tuning and hot-instrument behavior remain benchmark unknowns.

## 4. WASM hosting, limits, determinism, components, and state

### Wasmtime 48.0.2: limits and deterministic pure execution

Wasmtime's `Config::consume_fuel` “configures whether execution of WebAssembly will ‘consume fuel’,” and can “deterministically prevent infinitely-executing WebAssembly code”; “When fuel runs out a trap is raised” ([fuel](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Config.html#method.consume_fuel)). `Store::set_fuel` documents that a store starts with zero fuel and that most instructions consume one unit, while some consume zero ([fuel accounting](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Store.html#method.set_fuel)). A fixed fuel budget is therefore a deterministic instruction-cost bound, not a wall-clock or host-CPU bound.

Epoch interruption is the wrong primitive for reproducibility: Wasmtime says “The interruptions are not deterministic,” and its deadline trap is intended for “coarse-grained interruption, but not a deterministic deadline of a fixed, finite interval” ([epoch](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Config.html#method.epoch_interruption), [deadline](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Store.html#method.epoch_deadline_trap)). The docs also say “Epochs (and fuel) do not assist in handling WebAssembly code blocked in a call to the host.” Therefore, pure programs should have no blocking host calls; effectful calls require an external timeout/ledger policy.

Memory limits are direct. `StoreLimitsBuilder::memory_size` says “Growing a linear memory beyond this limit will fail,” but “This limit is applied to each linear memory individually” and linear memory is unlimited by default ([memory](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.StoreLimitsBuilder.html#method.memory_size)). `Store::limiter` only applies to future creation/growth and “does not retroactively attempt to apply limits to the Store” ([limiter](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Store.html#method.limiter)); shared memories are not covered by `ResourceLimiter::memory_growing` ([limitation](https://docs.rs/wasmtime/48.0.2/wasmtime/trait.ResourceLimiter.html#tymethod.memory_growing)). [INFERENCE] set memory/table/instance caps before instantiation and reject features not covered by the limiter. Do not call this a whole-process memory limit.

Wasmtime's deterministic-execution guide says: “Do not give Wasm programs access to non-deterministic host functions,” and recommends `wasi-virt` if WASI is used to virtualize clocks/filesystems ([determinism](https://docs.wasmtime.dev/examples-deterministic-wasm-execution.html#make-sure-all-imports-are-deterministic)). `cranelift_nan_canonicalization` is “useful for users requiring entirely deterministic WebAssembly computation” but is not enabled by default ([NaN](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Config.html#method.cranelift_nan_canonicalization)). Relaxed SIMD can differ on x86_64 versus AArch64; the docs provide `relaxed_simd_deterministic` to force deterministic behavior ([SIMD](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Config.html#method.wasm_relaxed_simd)). `Module::imports` says a module with no imports returns an empty list ([imports](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Module.html#method.imports)), and `Linker::instantiate` errors when an import is not defined ([fail closed](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Linker.html#method.instantiate)).

These facts make B3 pure functions feasible with a narrow contract: inspect imports and require none (or only reviewed deterministic functions), use fixed fuel, prebound memory/table growth, deterministic floating-point settings, and return typed values/traps. Wasmtime's support policy calls the Tier 1 Rust embedding API “suitable for production environments” ([tiers](https://docs.wasmtime.dev/stability-tiers.html)). The concrete risk is that a host import can still perform arbitrary side effects if UTA links it, so this is an authority boundary, not automatic effect safety.

### Component Model and WIT

The Wasmtime component module provides the Component Model embedding API and states that `bindgen!` “generates Rust bindings for a WIT world,” mapping WIT types and generating traits ([component API](https://docs.rs/wasmtime/48.0.2/wasmtime/component/index.html)). The Bytecode Alliance defines a world as a contract of imports and exports ([WIT worlds](https://component-model.bytecodealliance.org/design/wit.html#worlds)); it explicitly says “WIT isn’t a general-purpose programming language and doesn’t define behaviour; it defines only contracts between components” ([WIT limits](https://component-model.bytecodealliance.org/design/wit.html)).

That directly supports a typed, cross-language-ish component contract for B3, but WIT does not decide which effects are authorized, how an alert is routed, or how an effect is journaled. Component `Linker` supplies host functionality and errors if a required import is missing or wrongly typed ([linker](https://docs.rs/wasmtime/48.0.2/wasmtime/component/struct.Linker.html#method.instantiate)). The optional component async ABI is not a safe assumption: Wasmtime says support for this feature “is very incomplete” ([async component support](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Config.html#method.wasm_component_model_async)). For pure per-event calls, use synchronous component exports or core modules; do not make B3 depend on the incomplete async component ABI.

### State snapshot/restore: the material gap

A Wasmtime `Store` is “a collection of WebAssembly instances and host-defined state,” and a store is “intended to be a short-lived object” ([Store](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Store.html)). `Module::serialize` only “serializes this module to a vector of bytes” suitable for `Module::deserialize`, which returns a compiled `Module` “ready to be instantiated” ([serialize](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Module.html#method.serialize), [deserialize](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Module.html#method.deserialize)). Component serialization has the same compiled-artifact meaning ([component serialize](https://docs.rs/wasmtime/48.0.2/wasmtime/component/struct.Component.html#method.serialize)). These are not mutable instance-memory snapshots.

`wasmtime-wizer 48.0.2` is narrower: “Wizer instantiates your WebAssembly module, executes its initialization function, and then serializes the instance’s initialized state out into a new WebAssembly module” ([Wizer](https://docs.rs/wasmtime-wizer/48.0.2/wasmtime_wizer/struct.Wizer.html)). Its restrictions include “The initialization function may not call any imported functions,” imported globals/tables/memories are forbidden, and reference types are not supported ([Wizer restrictions](https://docs.rs/wasmtime-wizer/48.0.2/wasmtime_wizer/struct.Wizer.html)). A Wasm core dump is diagnostic; the docs warn that locals or operand-stack values “may be optimized away by the compiler or otherwise not recovered in the coredump” ([core dump](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.WasmCoreDump.html)).

The reviewed stable `Store` API exposes store data, fuel, epochs, limiters, and debug accessors, but no documented general snapshot/restore/checkpoint method ([Store API](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Store.html)). This is an **evidence gap**, not proof that no private or external mechanism exists. It means an opaque “pause arbitrary guest instruction and restore it later” requirement is not satisfied by Wasmtime, Wizer, module serialization, or core dumps. [INFERENCE] The feasible Rust design is an explicit guest/application state contract: export `save_state`/`load_state` or make logical state an explicit WIT record, persist it at quiescent boundaries, recreate the store, and replay deterministic inputs. If transparent continuation is mandatory, require a separate checkpoint technology or change the requirement; switching to TypeScript has no evidence-based advantage.

### Effects and isolation

Wasmtime's security guide says “All interaction with the outside world is done through imports and exports” and there is “no raw access to system calls or other forms of I/O” ([core security](https://docs.wasmtime.dev/security.html#webassembly-core)). WASI follows a capability model that restricts access to files/directories granted to the application ([WASI security](https://docs.wasmtime.dev/security.html#filesystem-access)). `Store<T>` can hold arbitrary host data accessible by host functions through `Caller` ([host state](https://docs.rs/wasmtime/48.0.2/wasmtime/index.html)). A guest trap “halts the execution of WebAssembly and cause[s] an error to be returned to the host” ([Trap](https://docs.rs/wasmtime/48.0.2/wasmtime/enum.Trap.html)); errors can indicate execution halted mid-way ([Func call](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Func.html#method.call)).

Therefore D04/B7 require the host effect design to be stricter than “WASM is sandboxed”: use no credentials or venue handles in guest data, provide only reviewed deterministic imports for pure programs, and keep venue calls/ledger/idempotency/readback in core/integration. A trap after an import is not rollback evidence. D05/D06 must be implemented by the outer subscription/log system, not by Wasmtime.

### Alternatives

- **Rhai 1.26.1** is a plausible Rust-native DSL fallback. Its safety guide says the operation count is “a very course-grained measurement” intended to impose a hard CPU upper limit, but “One operation can take an unspecified amount of time and real CPU cycles”; an external Rust function counts as one operation while consuming much more ([max operations](https://rhai.rs/book/safety/max-operations.html)). It also limits call depth to 64 by default ([call stack](https://rhai.rs/book/safety/max-call-stack.html)) and says “Rhai is sand-boxed so a script can never read from outside its own environment” ([sandbox](https://rhai.rs/book/safety/sandbox.html)). With `serde`, `Scope` can be serialized, but “Data in custom types are not serialized” ([scope](https://rhai.rs/book/engine/scope.html)). This is a DSL/state fallback, not a Component Model/WIT or live VM checkpoint. Concrete risk: coarse accounting and uncharged host work can violate D04 latency/resource bounds.
- **mlua/Lua 0.12.1** supports explicit safe libraries: `Lua::new_with` “will not allow to load unsafe standard libraries or C modules” ([safe state](https://docs.rs/mlua/0.12.1/mlua/struct.Lua.html#method.new_with)). It has `set_memory_limit`: allocations past the limit produce `Error::MemoryError` ([memory](https://docs.rs/mlua/0.12.1/mlua/struct.Lua.html#method.set_memory_limit)), and a hook can implement an instruction limit ([hook](https://docs.rs/mlua/0.12.1/mlua/struct.Lua.html#method.set_hook)). `Function::dump` only “dumps the function as a binary chunk” ([dump](https://docs.rs/mlua/0.12.1/mlua/struct.Function.html#method.dump)); explicit serde values are available, but no live-VM restore API was found in the reviewed docs. Use this only for Lua compatibility; persist application state explicitly.
- **Deno-in-Rust via deno_core 0.411.0** is a JS/TS compatibility last resort. `RuntimeOptions` says “Only ops registered by extensions will be initialized” and absent a module loader “runtime will error if code being executed tries to load modules” ([extensions](https://docs.rs/deno_core/0.411.0/deno_core/struct.RuntimeOptions.html)). V8 heap limits can end in `FatalProcessOutOfMemory` ([heap](https://docs.rs/v8/150.4.0/v8/struct.CreateParams.html#method.heap_limits)), and `IsolateHandle::terminate_execution` can force termination ([terminate](https://docs.rs/v8/150.4.0/v8/struct.IsolateHandle.html#method.terminate_execution)). Deno snapshots are startup optimization—“Create a snapshot of a JavaScript runtime, which may yield better startup time”—not documented arbitrary live restore ([snapshot](https://docs.rs/deno_core/0.411.0/deno_core/snapshot/fn.create_snapshot.html)). It has no reviewed Wasmtime-style deterministic fuel or WIT contract, and V8 fatal OOM makes a process boundary prudent for hostile code.

## 5. Protobuf/gRPC over UDS and bidirectional streaming

### Chosen stack

**tonic 0.14.6 + tonic-prost 0.14.6 + tonic-prost-build 0.14.6 + prost 0.14.4** is the leading Rust-first RPC stack. Tonic describes itself as “a gRPC over HTTP/2 implementation focused on high performance, interoperability, and flexibility” ([crate](https://docs.rs/tonic/0.14.6/tonic/)). Its low-level `Grpc::streaming` API is documented as “Send a bi-directional streaming gRPC request” with a stream in and `Streaming<M2>` out ([streaming](https://docs.rs/tonic/0.14.6/tonic/client/struct.Grpc.html#method.streaming)). `Streaming::message` exposes message, EOF, and `Status`; `Ok(None)` means “the stream was closed by the sender and no more messages will be delivered,” while `Err` means a gRPC error was sent ([terminal semantics](https://docs.rs/tonic/0.14.6/tonic/struct.Streaming.html)).

The client `Endpoint::connect_with_connector` accepts a `Service<Uri>` whose response implements Hyper `Read + Write + Send + Unpin`, and says “This allows you to build a Channel that uses a non-HTTP transport. See the uds example ... uses a Unix socket transport. The connect_timeout will still be applied” ([connector](https://docs.rs/tonic/0.14.6/tonic/transport/struct.Endpoint.html#method.connect_with_connector)). The server `serve_with_incoming` says “Serve the service on the provided incoming stream” and accepts `Stream<Item = Result<IO, IE>>` where IO implements `AsyncRead + AsyncWrite + Connected + Unpin + Send + 'static` ([server](https://docs.rs/tonic/0.14.6/tonic/transport/struct.Server.html#method.serve_with_incoming)). This is enough to put one API over Unix sockets, named pipes, or another custom local byte stream when the adapter implements the required traits.

`tonic-prost` documents “A Codec that implements application/grpc+proto via the prost library” and buffer settings that control memory allocation/growth per RPC ([codec](https://docs.rs/tonic-prost/0.14.6/tonic_prost/struct.ProstCodec.html)). `tonic-prost-build` supplies code generation for gRPC services from protobuf definitions ([build](https://docs.rs/tonic-prost-build/0.14.6/tonic_prost_build/)). Prost “generates simple, idiomatic Rust code from proto2 and proto3 files,” while not providing runtime reflection/descriptors by default ([prost](https://docs.rs/prost/0.14.4/prost/)). Its `Message` trait exposes length-delimited encode/decode ([framing helpers](https://docs.rs/prost/0.14.4/prost/trait.Message.html)).

### UDS portability decision

Tonic's pinned source recognizes `unix:`/`unix://` endpoints and selects `EndpointType::Uds` ([endpoint source](https://docs.rs/tonic/0.14.6/src/tonic/transport/channel/endpoint.rs.html)). The native connector imports Tokio's UnixStream under `cfg(not(target_os = "windows"))`; its Windows implementation returns the exact error `uds connections are not allowed on windows` ([connector source](https://docs.rs/tonic/0.14.6/src/tonic/transport/channel/uds_connector.rs.html)). Tokio's net module says UnixListener/UnixStream provide Unix-domain stream sockets “available on Unix only” and lists Windows named pipes separately ([Tokio net](https://docs.rs/tokio/1.53.1/tokio/net/index.html)). `tokio-stream 0.1.19` wraps a UnixListener and yields `Result<UnixStream, Error>` ([wrapper](https://docs.rs/tokio-stream/0.1.19/tokio_stream/wrappers/struct.UnixListenerStream.html)). On Unix, that is a direct tonic server pipeline.

Windows itself does have AF_UNIX: Microsoft says “Beginning in Windows Insider Build 17063, you can use the unix socket (AF_UNIX) address family on Windows to communicate between Win32 processes” ([Microsoft](https://learn.microsoft.com/en-us/windows/win32/ipc/interprocess-communications)). But Microsoft's AF_UNIX article says support is only `SOCK_STREAM`, connection-oriented one-to-one, with no ancillary data and no `socketpair` ([limitations](https://devblogs.microsoft.com/commandline/af_unix-comes-to-windows/)). OS support therefore does not imply stable Tokio integration. Tonic's own native branch is decisive for the selected stack.

Conclusion: C1/C2 are feasible as one **logical tonic service API** with target-specific transport. Native UDS can be used on macOS/Linux; Windows requires a custom AF_UNIX adapter such as `uds-compat 0.1.0`/`uds_windows 1.2.1`, a named-pipe transport, or loopback TCP. `uds-compat` advertises “Cross-platform async Unix domain socket compatibility types” ([docs](https://docs.rs/uds-compat/0.1.0/uds_compat/)), but it is new/low-usage and its docs do not prove a tonic `Connected` implementation; that adapter needs an actual Windows integration verification. The least risky uniform fallback is loopback TCP with local authorization. This is a selected-stack portability limitation, not evidence that Rust as a language is infeasible.

### Ordering and D01/D05/D06 semantics

gRPC's official concepts page says bidi streams operate independently and “The order of messages in each stream is preserved” ([gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/)). RFC 9113 similarly says streams are largely independent and recipients process frames in received order ([RFC 9113](https://www.rfc-editor.org/rfc/rfc9113.html)). This matches B5's consumer-controlled ordering: preserve per-stream sequence, expose explicit IDs/timestamps, and let the consuming program merge/await/window. No cross-channel alignment is supplied.

Tonic's `Status::deadline_exceeded` documentation explicitly warns that a state-changing operation may have completed successfully before the deadline error reached the client; insufficient information can become `Unknown` ([Status](https://docs.rs/tonic/0.14.6/tonic/struct.Status.html)). gRPC cancellation also warns that changes before cancellation are not rolled back ([core concepts](https://grpc.io/docs/what-is-grpc/core-concepts/)). Therefore D01/D02 cannot be implemented by retrying a failed RPC. Put operation identity, venue-declared idempotency/readback, and unknown-state transitions in the ledger/integration layer. `Request::set_timeout` supplies a wire deadline ([timeout](https://docs.rs/tonic/0.14.6/tonic/struct.Request.html#method.set_timeout)); it does not supply D03 identity/expiry semantics.

### Alternatives

- **Cap'n Proto 0.27.2 / capnp-rpc 0.27.0:** `capnp` has “standard stream framing” with a segment table before each message ([framing](https://docs.rs/capnp/0.27.2/capnp/serialize/)). `capnp-rpc` calls its transport “A two-way RPC connection” and has a `FlowController` that tracks an RPC stream ([connection](https://docs.rs/capnp-rpc/0.27.0/capnp_rpc/trait.Connection.html), [flow](https://docs.rs/capnp-rpc/0.27.0/capnp_rpc/trait.FlowController.html)). The concrete B1 risk is that `RpcSystem` is a “non-Sendable Future” needing an executor such as `tokio::task::spawn_local` ([RpcSystem](https://docs.rs/capnp-rpc/0.27.0/capnp_rpc/struct.RpcSystem.html)); it has no documented UDS helper. `auto_reconnect` only reconnects future calls; “The original request that got a Disconnected will still get that response. It is up to the caller to retry the call if relevant” ([reconnect](https://docs.rs/capnp-rpc/0.27.0/capnp_rpc/fn.auto_reconnect.html)). This is not D01-safe automatic retry.
- **Plain length-prefixed protobuf:** the official protobuf guide says “The Protocol Buffer wire format is not self-delimiting” and recommends writing each message's size before it ([protobuf framing](https://protobuf.dev/programming-guides/techniques/)). Prost's length-delimited helpers make this small and Rust-native, but framing limits, multiplexing, flow control, errors, auth, reconnect, cursors, and gap events become application code. This is the best fallback when both endpoints are controlled and HTTP/2 is unnecessary; use an explicit envelope with stream ID, sequence/cursor, operation ID, kind, payload, and gap/error variants.
- **JSON-RPC over UDS:** the standard is “stateless, light-weight” and transport agnostic, including sockets ([JSON-RPC](https://www.jsonrpc.org/specification)). Notifications are not confirmable: “The Server MUST NOT reply to a Notification” and a client would not know errors; batches may run concurrently/in any order and responses may return in any order ([notifications/batches](https://www.jsonrpc.org/specification)). jsonrpsee 0.26.0 exposes HTTP/WebSocket/WASM client transports but no first-class UDS transport ([crate](https://docs.rs/jsonrpsee/0.26.0/jsonrpsee/)); its server can convert to a Tower service for a custom connection loop ([service builder](https://docs.rs/jsonrpsee-server/0.26.0/jsonrpsee_server/struct.ServerBuilder.html#method.to_service_builder)). This is viable for HTTP-over-custom-IO compatibility, but dynamic JSON/type overhead and unconfirmable notifications are concrete risks for B1/D01. It does not define durable bidirectional streams.

## 6. Append-only segmented log, fsync, CRC, and atomic head

### Closest ready-made logs

**okaywal 0.3.1** is the closest documented fit. Its entry commit says: “Once this call returns, all data is atomically updated and synchronized to disk” ([commit](https://docs.rs/okaywal/0.3.1/okaywal/struct.EntryWriter.html)). Its overview says it streams data into “segments”; when a checkpoint threshold is reached it activates a new segment; before a commit returns the file is fsynced; file and directory fsync operations are batched ([overview](https://docs.rs/okaywal/0.3.1/okaywal/index.html)). Its chunk framing has a little-endian length, data, and “a four-byte crc32”; an incomplete ending means the entry is abandoned and chunks ignored ([CRC/tail](https://docs.rs/okaywal/0.3.1/okaywal/index.html)). Recovery explicitly returns `AbortedEntry` when an entry was being written during a crash and says the entire entry should be ignored ([aborted entry](https://docs.rs/okaywal/0.3.1/okaywal/enum.ReadChunkResult.html)).

The decisive maturity risk is the crate's own warning: “This crate is early in development. Please do not use in any production projects until this has been incorporated into Sediment and shipping as part of Nebari. The file format is currently considered unstable” ([warning](https://docs.rs/okaywal/0.3.1/okaywal/index.html)). It also leaves associated checkpoint state to the `LogManager`; the docs require all underlying storage changes to be synchronized before the checkpoint callback returns for ACID compliance ([checkpoint](https://docs.rs/okaywal/0.3.1/okaywal/trait.LogManager.html)). It documents unique entry IDs, but does not provide a separate external durable head/manifest protocol ([entry ID](https://docs.rs/okaywal/0.3.1/okaywal/struct.EntryWriter.html)).

**seglog 0.3.6** is a lower-level alternative: “a simple, high-performance segment log implementation” with “fixed-size segment files with built-in CRC-32 validation,” intended for event sourcing/WAL/append-only use ([overview](https://docs.rs/seglog/0.3.6/seglog/index.html)). It documents a single writer/multiple readers model and a `FlushedOffset` ([concurrency](https://docs.rs/seglog/0.3.6/seglog/index.html)). `append_batch` appends a commit marker, syncs once, and recovery retains the batch only if every record and marker validate ([batch](https://docs.rs/seglog/0.3.6/seglog/write/struct.Writer.html)). Rotation is caller-owned: “The caller must ensure the batch fits within the segment” ([rotation](https://docs.rs/seglog/0.3.6/seglog/write/struct.Writer.html)).

Its key concrete risk is a visibility/durability window. The docs say a follower sees only a valid prefix, but “It is not a durability oracle: a batch becomes visible when its commit marker reaches the page cache, which is just before the writer’s fsync returns, so a power loss in that window erases events a follower has already seen” ([follower warning](https://docs.rs/seglog/0.3.6/seglog/index.html)). `flush_writer` only writes to the OS and does not guarantee persistence, whereas `sync` persists to disk ([sync](https://docs.rs/seglog/0.3.6/seglog/write/struct.Writer.html)). With only 59 observed downloads, treat it as a prototype candidate, not an unreviewed ledger authority.

### Index/state stores are not the append log

**redb 4.2.0** is a strong durable index/state store: it describes itself as a portable ACID embedded key-value store, copy-on-write B+ trees, fully ACID transactions, and “Crash-safe by default” ([overview](https://docs.rs/redb/4.2.0/redb/)). `Durability::Immediate` is guaranteed persistent when `WriteTransaction::commit` returns ([durability](https://docs.rs/redb/4.2.0/redb/enum.Durability.html)). Its documented one-phase commit updates an inactive commit slot, flips the primary bit, calls fsync, and after a crash chooses the newest of two slots with a valid checksum ([commit slots](https://docs.rs/redb/4.2.0/redb/struct.WriteTransaction.html)).

redb's checksum is “xxhash, a fast, non-cryptographic hash function,” not the required CRC framing ([checksum](https://docs.rs/redb/4.2.0/redb/struct.WriteTransaction.html)). Its transaction commits an internal copy-on-write database, not an external append segment plus manifest atomically. A failed commit has exactly the D01 shape: changes are atomic but “may already have become durable, so they must not be assumed rolled back”; the database must be closed and reopened ([failed commit](https://docs.rs/redb/4.2.0/redb/struct.WriteTransaction.html)). Use redb for indexes, operation state, cursor metadata, or a complete ledger store if its model is accepted; do not call it a drop-in CRC segmented log.

**sled 0.34.7** is also a state store. Its docs promise thread safety and atomic operations, ACID transactions across trees, and a successful `flush` that calls fsync and guarantees previous writes recover after a crash ([overview/flush](https://docs.rs/sled/0.34.7/sled/)). Its public checksum is a CRC32 over all keys/values in the database ([CRC](https://docs.rs/sled/0.34.7/sled/struct.Db.html)), not per-record/torn-tail framing; `watch_prefix` is a blocking iterator over updates ([watch](https://docs.rs/sled/0.34.7/sled/index.html)), not a documented durable reconnect cursor. The stable release is from 2021, so use only after an explicit dependency decision.

**fjall 3.1.10** is an optional current LSM/BTreeMap-like key-value engine with atomic cross-keyspace batches ([overview](https://docs.rs/fjall/3.1.10/fjall/)). Its `PersistMode::SyncAll` flushes data and metadata with fsync; `Buffer` does not guarantee power-loss persistence ([persist](https://docs.rs/fjall/3.1.10/fjall/enum.PersistMode.html)). Its documented public role is a KV store, not a CRC append-log API, so it has the same separation as redb.

### Hand-rolled head replacement

Rust standard library primitives are sufficient to implement the missing protocol but do not constitute the protocol by themselves. `File::sync_all` “attempts to sync all OS-internal file content and metadata to disk” and attempts to ensure in-memory data reaches the filesystem before returning ([sync_all](https://doc.rust-lang.org/std/fs/struct.File.html)). `std::fs::rename` replaces an existing destination ([rename](https://doc.rust-lang.org/std/fs/fn.rename.html)), but both paths must be on one filesystem and platform crash semantics still need verification. `crc32fast 1.5.2` provides an incremental `Hasher::update`/`finalize` CRC32 API ([hasher](https://docs.rs/crc32fast/1.5.2/crc32fast/struct.Hasher.html)).

[INFERENCE] A UTA-specific durable ledger can therefore use: length/type/sequence/operation ID/payload/CRC records in immutable segments; an explicit commit marker for a multi-record effect; `sync_all` before acknowledging; a temp head/manifest in the same directory; file sync; atomic rename; parent-directory sync; startup validation and fallback to the last valid head; and a documented log/index ordering. The implementation must decide what an unknown fsync/rename error means and never silently retry an external effect. Neither std nor crc32fast promises this entire crash matrix.

Decision: do **not** adopt okaywal solely because its feature list matches; its warning is disqualifying for an unreviewed production ledger. Prototype against seglog and hand-rolled framing, then choose a format whose recovery and head protocol can be reviewed. If schedule favors an embedded store, redb is the stronger index candidate, but retain the exact D01 ambiguous-commit handling.

## 7. Exact decimal arithmetic

**rust_decimal 1.43.0** is the default for ledger money and venue quantities when domain scales fit its bounded representation. Its docs define `Decimal` as a 128-bit fixed-precision representation with values `m / 10^e`, `-2^96 < m < 2^96`, and `0 <= e <= 28` ([representation](https://docs.rs/rust_decimal/1.43.0/rust_decimal/struct.Decimal.html)). Checked addition/multiplication return `None` on overflow, and checked construction returns an error rather than panicking ([checked arithmetic](https://docs.rs/rust_decimal/1.43.0/rust_decimal/struct.Decimal.html)). Rounding follows “Bankers Rounding” by default and accepts an explicit `RoundingStrategy` ([rounding](https://docs.rs/rust_decimal/1.43.0/rust_decimal/struct.Decimal.html)).

For serialized cross-process values, use the string serde mode: it says “Serialize/deserialize Decimals as strings” and its example preserves `"123.400"` ([serde strings](https://docs.rs/rust_decimal/1.43.0/rust_decimal/serde/str/)). The float mode is a separate opt-in ([serde floats](https://docs.rs/rust_decimal/1.43.0/rust_decimal/serde/float/)); [INFERENCE] never use that mode for ledger values without an explicit precision contract. Concrete risk: a market venue may send a scale or magnitude outside the 96-bit bound; model this as a typed validation error, not a panic or silent round.

**bigdecimal 0.4.10** stores arbitrary-size integer digits plus a scale. Its docs say it can store real numbers “to arbitrary precision,” but also say the precision is limited by the 64-bit decimal-point position ([representation](https://docs.rs/bigdecimal/0.4.10/bigdecimal/index.html)). Lowering scale drops digits and `with_scale_round` performs explicit rounding ([scale](https://docs.rs/bigdecimal/0.4.10/bigdecimal/struct.BigDecimal.html)). The docs warn: “If the magnitude of the exponent is very large, this may cause out-of-memory errors, or overflowing panics” ([resource risk](https://docs.rs/bigdecimal/0.4.10/bigdecimal/struct.BigDecimal.html)), and warn that serializing through binary floats causes information loss ([serde](https://docs.rs/crate/bigdecimal/0.4.10/source/README.md)).

Choice: use rust_decimal for bounded, high-rate domain/ledger values and bigdecimal only where a model genuinely needs arbitrary exponent/precision. Keep f64 analytics at an explicit boundary; do not pretend converting Greeks to Decimal makes the calculation exact. If the venue's fixed scale exceeds rust_decimal's range, use a separately bounded integer/scale domain type rather than unbounded bigdecimal in the hot path.

## 8. Incremental indicators and Greeks

### Technical indicators

**ta 0.5.0** directly models incremental state. Its overview says every indicator is a data structure whose fields define “parameters and state,” and every indicator implements `Next` and `Reset`; most accept `f64` or `DataItem` ([overview](https://docs.rs/ta/0.5.0/ta/)). The central API is `pub trait Next<T> { type Output; fn next(&mut self, input: T) -> Self::Output; }` and “Consumes a data item of type T and returns Output” ([Next](https://docs.rs/ta/0.5.0/ta/trait.Next.html)). `Reset` “resets an indicator to the initial state” ([Reset](https://docs.rs/ta/0.5.0/ta/trait.Reset.html)). This is an actual streaming/update contract, not a batch-only facade.

**yata 0.7.0** is another direct streaming candidate. It says it implements common technical-analysis methods/indicators and provides an interface to create custom indicators ([overview](https://docs.rs/yata/0.7.0/yata/)). Its example initializes a configured indicator from a candle and calls `next` for each candle ([example](https://docs.rs/yata/0.7.0/yata/)); the public trait source describes `IndicatorInstance` as state and declares `fn next<T: OHLCV>(&mut self, candle: &T) -> IndicatorResult` ([trait source](https://docs.rs/crate/yata/0.7.0/source/src/core/indicator/instance.rs)).

Both satisfy incremental per-instrument computation. Neither docs page supplies transport, durable state snapshots, readiness, cross-channel ordering, or a multi-core scheduler. Their mutable `next` state means one instance must not be shared across unrelated symbols/timeframes. Concrete risk: after a D06 gap, blindly continuing a stateful indicator can produce a value based on missing observations. Fallback: persist the logical input cursor and indicator state (or replay inputs) at the outer UTA layer; reset/rebuild after a declared gap. For a user-program graph, keep each instance behind one owner task or inside the WASM guest.

### Greeks and option pricing

**RustQuant 0.3.1 / RustQuant_instruments 0.3.1** documents a generalized Black-Scholes-Merton European model with f64 fields and methods including `price`, `delta`, `gamma`, `vega`, `theta`, and `rho` ([model](https://docs.rs/RustQuant/0.3.1/RustQuant/instruments/struct.BlackScholesMerton.html)). Its instruments docs list analytic, Monte Carlo, finite-difference, lattice, and Greeks capabilities ([scope](https://docs.rs/RustQuant_instruments/0.3.1/RustQuant_instruments/)). The reviewed API is a model object with value-in/value-out methods; its listed methods contain no `next`, update, stream, or retained incremental state contract ([method list](https://docs.rs/RustQuant/0.3.1/RustQuant/instruments/struct.BlackScholesMerton.html)). Thus per-tick Greeks are an application loop that reconstructs or updates the model, not a documented streaming API.

**black_scholes 0.11.1** is a smaller function-oriented alternative. Its docs describe “A Black Scholes option pricing library” with European call/put pricing, a full Greeks set, implied volatility, multiple models, and caching ([overview](https://docs.rs/black_scholes/0.11.1/black_scholes/)). `compute_all(stock, strike, rate, sigma, maturity)` returns `PricesAndGreeks`; the docs say it “Returns call and put prices and Greeks” and caches repeated calculations for one input ([compute_all](https://docs.rs/black_scholes/0.11.1/black_scholes/fn.compute_all.html)). It is also value-in/value-out, with no documented incremental stream or state snapshot.

Choice: use yata (or ta if its older but simpler API is preferred) for incremental technical indicators and black_scholes for standard BSM Greeks; keep RustQuant optional for broader models. All cited Greeks APIs use f64, not `Decimal`, and no cited crate establishes formula correctness for UTA's venue conventions. [INFERENCE] Treat them as analytics, convert/round only at the typed domain boundary, and independently validate model conventions (rates, dividends/carry, time units, volatility) before allowing trading effects. This report ran no formula tests per the read-only constraint.

## 9. Child-process supervision, restart/backoff, singleton lock, and daemonization

### Child lifecycle and process trees

Tokio `process::Command` 1.53.1 supplies an awaitable child handle; Tokio's `Child::wait` “waits for the child to exit completely, returning the status that it exited with,” while `start_kill` “does not wait for the request to take effect” ([Child](https://docs.rs/tokio/1.53.1/tokio/process/struct.Child.html)). Dropping a child does not automatically terminate it unless `kill_on_drop(true)` is configured ([Command](https://docs.rs/tokio/1.53.1/tokio/process/struct.Command.html)). These are direct primitives, not a restart policy.

The current Guardian's repository evidence shows why direct-child kill is insufficient: on Windows the handle may point to a shell wrapper while a `node`/`tsx` grandchild keeps the port (`scripts/guardian/shared.ts:268-279`). **process-wrap 10.0.0** is the current successor to command-group and supplies platform wrappers; its docs expose Unix `ProcessGroup`/`ProcessSession` and Windows `JobObject` ([Tokio wrappers](https://docs.rs/process-wrap/10.0.0/process_wrap/tokio/), [platform types](https://docs.rs/process-wrap/10.0.0/process_wrap/)). [INFERENCE] Use one process group/Job Object handle per supervised child and await group/child reaping, not only `kill_on_drop`.

`command-group 5.0.1` is an older fallback whose docs say `group_spawn` “executes the command as a child process group” and on Windows “creates a job object instead of a POSIX process group”; its docs also say “The successor of command-group is process-wrap. No further work will be done on command-group” ([group](https://docs.rs/command-group/5.0.1/command_group/stdlib/trait.CommandGroup.html)). Do not start new UTA code on the deprecated crate unless process-wrap cannot be integrated.

The existing restart path (`scripts/guardian/shared.ts:495-523`) is a useful observed shape: mark expected exit, graceful signal, bounded wait, hard escalation, respawn, health readiness. Recreate it as an explicit ADT/state machine: `Running`, `ExpectedExit`, `GracefulStopping`, `HardStopping`, `Exited`, `Starting`, `Ready`, `Crashed`, and `UnknownOutcome`. This state model is [INFERENCE], not a claim supplied by Tokio.

### Backoff and unknown outcomes

**backoff 0.4.0** provides an exponential policy; its docs say `ExponentialBackoff` increases periods using a randomization function, and `Error::Permanent` versus `Error::Transient` separates no-retry from retry ([exponential](https://docs.rs/backoff/0.4.0/backoff/exponential/), [error](https://docs.rs/backoff/0.4.0/backoff/enum.Error.html)). Its async retry API says it retries according to the policy ([future retry](https://docs.rs/backoff/0.4.0/backoff/future/fn.retry.html)). The crate is old (last release 2021-12-14), and it cannot determine whether a child exit follows an external venue effect. Concrete D01 risk: converting every startup/error result to `Transient` can duplicate an order after a crash or timeout.

Fallback: hand-write the classification around Tokio/process-wrap and optionally use the backoff delay generator. Retry only a known pre-effect crash/transport startup failure, with a bounded jittered budget. Expected exit is not retried; deterministic config/program errors are quarantined; unknown outcome stops and demands venue readback/reconciliation. Keep operation identity/idempotency in the core/integration ledger. `backon 1.6.0` is a newer optional retry helper with caller predicates, but it likewise supplies no external-effect knowledge ([Retryable](https://docs.rs/backon/1.6.0/backon/trait.Retryable.html)).

### Singleton lock

**fs2 0.4.3** provides `FileExt::lock_exclusive` and `try_lock_exclusive`; its docs say “Locks the file for exclusive usage, blocking if the file is currently locked,” and warn “File locks may only be relied upon to be advisory” ([FileExt](https://docs.rs/fs2/0.4.3/fs2/trait.FileExt.html)). **fd-lock 4.0.4** is a newer alternative whose docs call it “Advisory reader-writer locks for files”; `RwLock::write` gives exclusive blocking access ([crate](https://docs.rs/fd-lock/4.0.4/fd_lock/), [write](https://docs.rs/fd-lock/4.0.4/fd_lock/struct.RwLock.html)).

Use a single `OpenOptions::create(true)` lock file, acquire the nonblocking exclusive lock, retain that exact open file handle for the process lifetime, then write diagnostic PID/start-time/token metadata. Never delete the file based on a stale PID guess: the lock is the handle, not the path. This is [INFERENCE] from advisory lock semantics and avoids two instances acquiring different inodes. A non-cooperating process can ignore advisory locks; if mandatory exclusion against arbitrary writers is required, use a platform-native named mutex/lock and record that as a separate portability decision.

### Daemonization and OS service ownership

**daemonize 0.5.0** is Unix-only. It calls itself a “Library to enable your code run as a daemon process on Unix-like systems” and says it will “Fork the process in the background, disassociate from its process group and the control terminal”; it can create and exclusively lock a PID file ([Daemonize](https://docs.rs/daemonize/0.5.0/daemonize/struct.Daemonize.html)). This directly conflicts with a Guardian that must own/reap the child. Do not call daemonize inside the supervised UTA path.

**service-manager 0.11.0** is the cross-platform installation/control alternative. Its API selects native managers (launchd, systemd/OpenRC, `sc.exe`/WinSW, and related backends) and exposes install/start/stop/uninstall plus restart policy ([trait](https://docs.rs/service-manager/0.11.0/service_manager/trait.ServiceManager.html), [policy](https://docs.rs/service-manager/0.11.0/service_manager/enum.RestartPolicy.html)). Its own API is an installer/control plane, not an in-process child supervisor; it warns when a backend approximates unsupported policy ([source](https://docs.rs/service-manager/0.11.0/src/service_manager/lib.rs.html)).

Choose one owner: (a) Guardian owns a foreground UTA child and process-wrap handles tree termination, or (b) the OS service manager owns UTA and Guardian only observes status. Mixing daemonize, an OS service manager, and a second Guardian creates ambiguous ownership, duplicate restarts, and unreaped children. The existing observed health/readiness sequence supports option (a) when UTA is launched by Alice; option (b) is appropriate for host-managed deployment.

### Requirement judgment

- D04 process isolation is feasible as a composition of Tokio Child + process-wrap + an explicit supervisor ADT, but no crate alone provides expected/crash/unknown classification.
- D01/D02 prohibit generic retry. Backoff is only a delay policy; no process crate can know venue-side effect outcome.
- D05/D06 are not supplied by child supervision. Persist subscriptions/cursors/gaps in UTA core and let restart reconnect through integration.
- D07 is a boundary decision: supervisor receives an opaque configuration reference, not credentials; child output and service definitions must not leak secret material.

## 10. AI coding-agent feasibility for this Rust shape

The strongest direct evidence found is Rust-specific rather than UTA-specific. Xiang et al.'s 2026 Rust-SWE-bench paper describes “Rust-SWE-bench, a benchmark comprising 500 real-world, repository-level software engineering tasks from 34 diverse and popular Rust repositories” and reports agents resolving “up to 21.2% of issues” ([arXiv](https://arxiv.org/abs/2602.22764)). The paper's abstract also states that Rust presents a “steep learning curve and significant coding challenges” ([abstract](https://arxiv.org/abs/2602.22764)).

Observed evidence supports only these limited conclusions: agents can be evaluated on real Rust repositories, and a majority of benchmark issues remain unresolved under the reported setup. It does **not** establish that an agent can correctly implement UTA's process-group teardown, lock ownership, crash/unknown classification, durable cursor recovery, or venue-safe effect semantics. The benchmark's issue tests are not proof of external side-effect correctness. [INFERENCE] An agent can plausibly implement local Rust slices when supplied pinned APIs and compile/runtime feedback, but every load-bearing UTA slice needs human review plus targeted runtime scenarios: kill descendants, crash at each log/fsync window, lag and recover a subscriber, trap a guest, and prove no blind retry after unknown status. No source found gives a supervisor-specific or trading-side-effect-specific agent success rate.

## Infeasibility decision: what would permit TypeScript?

**Genuinely infeasible in Rust: none proven by this investigation.** Stable Rust has direct or composable support for every named core category: async runtime/cancellation/channels, sharded state, WASM execution limits and typed components, protobuf/gRPC, Unix IPC on Unix targets, durable filesystem primitives, fixed/arbitrary decimal types, incremental indicators, Greeks calculations, child process handles, process groups/Job Objects, locks, and OS-service integration. The requirement-specific semantics that remain are application/integration protocols, not missing language features.

Two conditions are **not satisfied by the selected ready-made stack**, but neither is evidence for switching to TypeScript:

1. A single native Tokio/tonic UDS implementation across macOS, Linux, and native Windows is not available: Tokio documents Unix sockets as Unix-only and tonic's Windows connector returns `uds connections are not allowed on windows` ([Tokio](https://docs.rs/tokio/1.53.1/tokio/net/index.html), [tonic source](https://docs.rs/tonic/0.14.6/src/tonic/transport/channel/uds_connector.rs.html)). Keep the logical RPC API and select Unix UDS, a custom Windows adapter/named pipe, or loopback TCP per target.
2. Arbitrary opaque live Wasmtime Store continuation is not documented: Wizer snapshots initialization only, module serialization restores compiled artifacts, and core dumps are diagnostic ([Wizer](https://docs.rs/wasmtime-wizer/48.0.2/wasmtime_wizer/struct.Wizer.html), [Module](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.Module.html#method.serialize), [core dump](https://docs.rs/wasmtime/48.0.2/wasmtime/struct.WasmCoreDump.html)). Require explicit logical state serialization/replay or a separately selected checkpoint technology. This is a design requirement gap, not a TypeScript capability.

Rust's lack of a language-native effect-system keyword is not a demonstrated infeasibility condition here. B7 can be represented through WIT/trait/protobuf contracts, explicit effect ADTs, process/WASM boundaries, and an append-only ledger; the safety proof is a UTA design obligation, not a crate feature claim. This is an inference from the documented import/contract boundaries, not a claim that any crate automatically proves effect safety.

## Minimal crate set

The smallest recommended set for the design (with optional items separated) is:

- **Concurrency/core:** `tokio = 1.53.1` with runtime, net, sync, time, process; `tokio-util = 0.7.19` with `sync` for `CancellationToken`. Use owner tasks plus bounded `mpsc`; use `broadcast` only for ephemeral live fan-out.
- **Typed IPC:** `tonic = 0.14.6`, `tonic-prost = 0.14.6`, `tonic-prost-build = 0.14.6`, `prost = 0.14.4`; add `tokio-stream = 0.1.19` for the Unix listener wrapper. Use cfg-specific UDS/TCP transport; do not assume native Windows UDS.
- **Pure program runtime:** `wasmtime = 48.0.2` and `wit-bindgen = 0.62.0` when WIT components are used. Add `wasmtime-wasi = 48.0.2` only for reviewed capability-based WASI imports; it is not needed for pure no-import functions. Do not put credentials or irreversible effects in guest imports.
- **Durable effects:** Rust `std::fs` plus `crc32fast = 1.5.2` for the explicitly specified segmented ledger. Add `redb = 4.2.0` only if an embedded index/state store is desired. Do not make `okaywal` the production authority without resolving its unstable-format warning; do not use sled as a new default without accepting its stale stable line.
- **Numbers/analytics:** `rust_decimal = 1.43.0` for bounded ledger values; `yata = 0.7.0` for incremental indicators; `black_scholes = 0.11.1` for standard BSM Greeks. `ta = 0.5.0` is a viable simpler indicator alternative; `RustQuant = 0.3.1` is optional for broader models.
- **Lifecycle:** `process-wrap = 10.0.0` for POSIX process groups/Windows Job Objects, plus Tokio child handles. `fs2 = 0.4.3` (or newer `fd-lock = 4.0.4`) for a held advisory singleton lock. `backoff = 0.4.0` is optional only as a delay policy; the expected/crash/unknown retry ADT must be UTA code. `service-manager = 0.11.0` is optional when delegating ownership to launchd/systemd/Windows service managers; do not add `daemonize` to a directly supervised path.
- **Not minimal:** `dashmap = 6.2.1` is optional for concurrent registries; deterministic owner queues are preferred for per-instrument mutable state. `rhai`, `mlua`, and `deno_core` are compatibility fallbacks, not dependencies of the Wasmtime design.

## Unknowns / could not verify

1. No B1 workload benchmark was run; Tokio/indicator/log throughput, p99 latency, memory pressure, and worker/shard counts remain unknown.
2. No arbitrary live Wasmtime `Store` snapshot/restore API was documented in the reviewed stable pages. This is an evidence gap, not a proof of impossibility; an explicit-state prototype or external checkpoint experiment is required if the requirement remains.
3. A Windows `uds-compat`/AF_UNIX stream was not integrated with tonic's `Connected` server bound or exercised on native Windows; the documented fallback remains cfg-specific adapter, named pipe, or loopback TCP.
4. Native filesystem crash behavior for every target filesystem/device, including directory fsync and rename ordering, was not experimentally verified. The report records API contracts and application obligations only.
5. Venue-specific idempotency keys, readback, cursor, stream reconnect, rate limits, and unknown-outcome reconciliation were not investigated here; D02/D05/D06/D08 require each integration's official capability declaration.
6. No indicator or Greek formula correctness, venue convention, `Decimal` conversion, or state serialization test was run. The cited docs establish API shape, not numerical correctness.
7. `service-manager` backend restart/readiness semantics and `process-wrap` descendant behavior were not run on all three operating systems; only the official API/platform claims were reviewed.
8. AI-agent evidence is repository-level Rust issue resolution, not greenfield UTA or external trading-effect correctness; no source was found for a UTA-shaped success rate.
9. No formatter, linter, build, or test was run, as required by the read-only investigation assignment.

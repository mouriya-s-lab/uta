# Alice-side UTA consumer investigation

## Evidence method and scope

This is an observation report for the current repository. “Existing capability” below means behavior visible in current Alice code. “Consumer need” means an input, output, identity, timing, or safety property that a current consumer demonstrably relies on. It does not claim that the rewritten UTA already implements that property or prescribe a new design. Old files under `../reference/` were not used as facts, per the assignment. The repository was read without changing it; no formatter, linter, build, or test suite was run.

The source comments in `src/services/uta-client/UTAManagerSDK.ts:1-19` describe the SDK as an HTTP-backed adapter and state that formerly synchronous methods are asynchronous. The adapter therefore provides the strongest current evidence for the Alice-to-UTA boundary, while the tools and their consumers show how those calls are actually used.

## 1. AI trading tools and SDK boundary

### 1.1 SDK behavior consumed by Alice

`UTAManagerSDK` is deliberately a remote adapter. Setup hooks for snapshots, FX, CCXT registration, add, remove, and close-all are no-ops, because the comments say UTA owns those concerns (`src/services/uta-client/UTAManagerSDK.ts:52-79`). `initUTA` is explicitly unsupported in the SDK and tells callers to write accounts and trigger a restart (`src/services/uta-client/UTAManagerSDK.ts:52-79`). Reconnect and removal likewise trigger the supervised UTA restart path rather than changing a local object (`src/services/uta-client/UTAManagerSDK.ts:174-200`).

The manager lists UTA summaries with `GET /api/trading/uta`, resolves by exact source ID or provider prefix, and can restrict source-less resolution to trading-tier accounts (`src/services/uta-client/UTAManagerSDK.ts:81-129`). It discovers historical-bar sources from summary capabilities and, for a selected account, can refine quality by security type through contract details (`src/services/uta-client/UTAManagerSDK.ts:132-150`). Equity and FX are separate manager-level reads (`src/services/uta-client/UTAManagerSDK.ts:153-172`). Aggregated contract search is `GET /api/trading/contracts/search`, with an optional source filter (`src/services/uta-client/UTAManagerSDK.ts:203-228`).

The SDK account object is not a local venue implementation. Its comments say it is an HTTP-shaped adapter (`src/services/uta-client/UTAAccountSDK.ts:68-86`). Health is currently optimistic (`healthy`, readable, and trading in `getHealthInfo`), `waitForConnect` returns immediately, and `getCapabilities()` returns an empty object with a comment directing consumers to the authoritative UTA summary (`src/services/uta-client/UTAAccountSDK.ts:88-125`). Those current shortcuts matter because consumers use list-summary/readiness metadata rather than treating these account methods as a complete health protocol.

### 1.3 AI output contract

The compactor intentionally omits unset values and removes sentinel values, rather than serializing full internal objects (`src/tool/trading-compact.ts:1-15`, `src/tool/trading-compact.ts:18-60`). Contracts retain identity and instrument fields including `aliceId`, symbol/local symbol, security type, currency, exchange, expiry, strike, right, and multiplier; order fields retain action/type/quantity/cash/price/aux/trailing/time-in-force/date/outside-RTH/filled (`src/tool/trading-compact.ts:62-114`).

Operation results distinguish place/observe, close, modify, and cancel, and include status, top-level string order ID, fills, errors, legs, rejection, and warnings (`src/tool/trading-compact.ts:116-172`). Wallet status exposes staged state, awaiting-approval message/hash, head, and commit count; commit results carry metadata, operations, results, and state-after money/position/pending counts (`src/tool/trading-compact.ts:174-237`). Account compaction includes account identifiers/balances and contract details preserve contract identity/details (`src/tool/trading-compact.ts:239-268`).

A current consumer therefore needs compact, sparse, JSON-safe values; string-preserved order IDs; explicit operation/result status; and separate staged, awaiting-approval, committed, and pushed states. This is observed output consumption, not a claim about the rewritten protocol.

## 2. Market-data consumers

### 2.1 Bar-service source selection and UTA gateway

The bar layer is described as federated: `getBars` resolves to a single source and tags metadata, `searchBarSources` surfaces candidates, and broker candidates are considered only when their historical-bars capability is supported (`src/domain/market-data/bars/bar-service.ts:3-13`). It does not combine rows from multiple sources for one `getBars` response. A separate quant tool can receive explicit bars from different sources in one script; that composition is in the consuming program (`src/tool/quant.ts:4-9`, `src/tool/quant.ts:17-27`, `src/tool/quant.ts:29-95`).

The market-data identity is `{sourceId}|{nativeSymbol}`; UTA uses a contract `aliceId` as its bar ID, and the types explicitly say that the same asset from different sources produces separate bar IDs (`src/domain/market-data/bars/types.ts:6-15`). `UtaBarGateway` requires `getHistorical` and capability discovery (`src/domain/market-data/bars/types.ts:120-164`).

For UTA bars, Alice first resolves the account by source ID, reads `getBarCapabilities(barId)`, rejects an advertised-but-unsupported source, and only falls back to realtime quality when the capability API itself is unavailable (`src/domain/market-data/bars/bar-service.ts:262-308`). Count-only requests are converted to bounded start windows; the adapter receives `{contract: {aliceId: barId}, params}` through `getHistorical` (`src/domain/market-data/bars/bar-service.ts:262-308`). The bar layer bounds dates, inspects quality, filters incomplete rows, sorts ascending, caps at 5000 rows, and applies the requested count to the tail (`src/domain/market-data/bars/bar-service.ts:112-194`, `src/domain/market-data/bars/bar-service.ts:262-308`).

Source search combines vendor and UTA candidate lists for discovery, but deduplicates by `barId`; UTA candidates require an `aliceId`, skip absent/unsupported capability, skip malformed IDs, and carry an honest capability label (`src/domain/market-data/bars/bar-service.ts:310-402`). Bare symbols are sorted by non-derivative preference and freshness, while an explicit bar ID wins resolution (`src/domain/market-data/bars/source-resolve.ts:1-59`). Thus current consumers need source-qualified identity, capability metadata, deterministic single-source selection, and failure/quality metadata.

Bar quality is evaluated on the fetched window before truncation; missing/non-finite OHLC fields are excluded and the latest excluded fields are recorded (`src/domain/market-data/bars/quality.ts:1-21`). Freshness describes record age rather than feed latency; historical requests use a `historical_request` basis with unknown delay, delayed sources carry source classification, and empty data is `no_records` (`src/domain/market-data/bars/freshness.ts:1-45`).

### 2.2 AI and UI market-data entry points

The AI `getMarketBars` tool accepts either a bar ID or symbol plus asset class, then delegates to the bar service with interval/count/start/end (`src/tool/market-bars.ts:5-25`). The AI quant tool consumes explicit bars keyed by bar ID and reports data-source failure separately from script failure (`src/tool/quant.ts:17-95`). The snapshot tool resolves one freshest source, fetches a snapshot, and returns freshness warnings; its comment says it avoids lookahead with `asOf` (`src/tool/snapshot.ts:1-51`).

The UI K-line panel calls `/api/bars` using an explicit selected bar ID or symbol plus asset class, polling every 60 seconds for intraday and every 300 seconds for daily data (`ui/src/components/market/KlinePanel.tsx:234-278`). The UI market API exposes `/api/bars/search` and `/api/bars`, and its `BarMeta` mirrors source, capability, quality, and freshness fields (`ui/src/api/market.ts:141-229`). The UI quote header instead uses the legacy `marketApi.equity.quote`, polls every 60 seconds, and comments that bid/ask belong to the UTA execution layer (`ui/src/components/market/QuoteHeader.tsx:15-31`, `ui/src/components/market/QuoteHeader.tsx:88-89`). A tradeable-contracts panel searches `/api/trading/contracts/search` on demand without a source filter and displays source plus `aliceId` in each row (`ui/src/components/market/TradeableContractsPanel.tsx:16-48`).

## 3. Alice BFF, lifecycle, configuration, and policy consumers

### 3.1 BFF request path and gating

Alice's trading proxy is the browser-facing BFF. Its comments say it maps Alice `/api/trading/*` to UTA, forwards requests unchanged, relies on UTA loopback host trust rather than an inter-process auth layer, and has a 30-second request timeout (`src/webui/routes/trading-proxy.ts:1-19`). The `/status` route returns mode, environment lock, configuration presence, availability, reason/hint, start time, and UTA summaries; it probes `__uta/health` with a one-second timeout (`src/webui/routes/trading-proxy.ts:51-113`).

All other requests are forwarded with path and query intact, selected request headers/body, and fresh response headers (`src/webui/routes/trading-proxy.ts:115-188`). Lite mode returns 503, missing UTA configuration returns 503, and readonly mode returns 403 only when `isVenueMutation` matches. The matcher treats non-GET/HEAD requests containing `/wallet/push`, `/wallet/place-order`, `/wallet/close-position`, `/wallet/cancel-order`, `/simulate-price`, or starting `/api/simulator` or `/simulator` as venue mutations (`src/webui/routes/trading-proxy.ts:115-215`). The proxy is mounted for both `/api/trading` and `/api/simulator` (`src/webui/plugin.ts:254-266`).

This means current UI/API consumers need stable path-preserving forwarding, distinguishable not-configured/unavailable/readonly responses, and a gateway that does not silently turn mutation denial into a read result. It also shows that the current BFF mutation matcher is narrower/different from every wallet operation used by AI tools; the matcher evidence is limited to the literal paths above (`src/webui/routes/trading-proxy.ts:193-206`).

### 3.2 Configuration writes and restart behavior

Broker configuration is read from and written to Alice-managed configuration. GET config masks keys containing `key`, `secret`, `password`, or `token` recursively before returning them (`src/webui/routes/trading-config.ts:40-76`, `src/webui/routes/trading-config.ts:80-184`). POST and PUT validate presets/schema, preserve or unmask existing secrets as needed, write the config, notify the UTA restart supervisor, and make a best-effort SDK reconnect; enabled/disabled changes and credential rotation trigger reconnect (`src/webui/routes/trading-config.ts:188-310`). DELETE writes a filtered config, notifies restart, calls remove, and wipes ephemeral trading data (`src/webui/routes/trading-config.ts:312-337`). A test-connection route forwards to UTA and relays its status (`src/webui/routes/trading-config.ts:339-360`).

The durable account config is sealed with AES-256-GCM and written owner-only to `data/config/accounts.json`; reads seed/unseal/migrate/quarantine and writes validate the schema (`src/core/config.ts:704-787`). Alice therefore currently owns credential/config persistence and the transition that causes UTA to reload it. The SDK does not offer a local `initUTA` implementation (`src/services/uta-client/UTAManagerSDK.ts:52-79`), which is the direct reason the current consumer path is write-config-plus-restart rather than in-process setup.

The supervisor discovers the UTA URL from `OPENALICE_UTA_URL` or the configured/default loopback port, and disables the integration for lite mode or a truthy `UTA_DISABLED` (`src/services/uta-supervisor/url.ts:1-25`). It probes `/__uta/health`, requiring `{ok:true, startedAt, utas}` with a string or number start time (`src/services/uta-supervisor/health.ts:1-42`). A restart trigger atomically writes `data/control/restart-uta.flag`; Guardian watches/debounces it, sends SIGTERM, respawns, and polls health until `startedAt` changes (`src/services/uta-supervisor/restart-trigger.ts:1-82`). Main waits briefly for UTA readiness, logs ready/unavailable, and builds `UTAManagerSDK` with live unavailable/readonly reasons (`src/main.ts:124-160`).

Main registers trading tools with the live `config.agent.allowAiTrading` callback and starts the connector action bridge with the manager and current policy; snapshot scheduling is now on the UTA side (`src/main.ts:244-304`, `src/main.ts:320-322`). Trading mode is a finite `pro|readonly|lite` state derived from environment/config/auto policy; readonly reason and environment locking are exposed (`src/services/trading-mode.ts:5-72`).

## 4. Web UI consumers and polling cadences

The UI trading API is a typed HTTP client over Alice's BFF. ## 5. Connector review/action consumer

Alice starts a connector bridge with a default 1,500 ms interval and no overlapping ticks; it uses the connector client's claim/ack/release and present/fail calls, then starts an immediate tick (`src/services/connector-client/action-bridge.ts:46-146`). The UTA branch skips when disabled, claims if available otherwise drains, fulfills each request, acknowledges complete requests, and releases retryable requests (`src/services/connector-client/uta-review.ts:19-46`).

Review presentation is intentionally bounded. Alice lists UTA summaries, excludes data-tier accounts, fetches each account plus wallet status, caps visible accounts at eight, caps operations at eight, reports hidden operation count, and includes a readonly indicator (`src/services/connector-client/uta-review.ts:73-127`). An unavailable/lite state is represented as a no-account review rather than a thrown transport exception (`src/services/connector-client/uta-review.ts:73-127`).

Fulfillment checks action expiry, requires `utaId` and `pendingHash` for push/reject, re-reads status, rejects a missing pending commit as a review error, rejects too many operations, blocks readonly pushes, pushes or rejects by expected hash, and classifies hash conflicts, readonly, and delivery failures separately (`src/services/connector-client/uta-review.ts:129-219`). The connector protocol fixes the action TTL at 60,000 ms, max requests at 20, max presented accounts at 8, and max operations at 8; non-review actions require both UTA ID and pending hash (`packages/connector-protocol/src/types.ts:230-310`, `packages/connector-protocol/src/types.ts:317-362`). Failure variants include expired, unavailable, not found, conflict, readonly, and delivery failed (`packages/connector-protocol/src/types.ts:364-397`).

The Telegram adapter is the visible interactive consumer. It maps review/push/reject presentations to owner sessions, rejects non-owner transitions, renders account/detail/confirmation controls, and enqueues push/reject actions carrying `utaId` and `pendingHash` (`services/connector/src/adapters/telegram.ts:246-276`, `services/connector/src/adapters/telegram.ts:348-413`, `services/connector/src/adapters/telegram.ts:514-666`; `services/connector/src/adapters/telegram-uta.ts:15-50`, `services/connector/src/adapters/telegram-uta.ts:67-175`, `services/connector/src/adapters/telegram-uta.ts:177-314`).

The queue producer is in the connector service: `enqueueUtaRequest` validates the request, assigns an ID/time/connector ID, preserves optional UTA ID and pending hash, enqueues it, and records the action TTL (`services/connector/src/core/delivery-manager.ts:247-287`). Alice consumes those requests through connector protocol HTTP endpoints for claim/ack/release/present/fail (`services/connector/src/main.ts:112-132`, `packages/connector-protocol/src/client.ts:136-195`). Within the repository's production `src` tree, no additional `ConnectorUtaRequest` producer was found; Telegram is the observed producer path.

## 6. CLI consumer

The CLI command manifest maps the global `uta` export to `alice-uta` and covers account list/info/portfolio, contract search/details/quote/expand/option-contracts/option-chain/order-book, order list/history/trades/place/modify/cancel, position close, git status/log/show/commit/push/reject/sync, market clock, and simulation price-change (`src/server/cli-commands.ts:212-268`).

The platform shell wrappers select the managed Node binary and invoke `openalice-cli.cjs` (`src/workspaces/cli/bin/alice-uta:1-65`, `src/workspaces/cli/bin/alice-uta.cmd:1-8`). The Node launcher is a thin argv-to-JSON-to-HTTP forwarder. It obtains the gateway from `OPENALICE_TOOL_URL` or socket settings, requires workspace/project context, fetches the manifest, parses flags, and invokes the selected tool (`src/workspaces/cli/bin/openalice-cli.cjs:1-120`). JSON invocation can propagate `AQ_RUN_ID` as `x-openalice-run` and `AQ_SESSION_ID` as `x-openalice-session` when workspace context exists (`src/workspaces/cli/bin/openalice-cli.cjs:123-179`).

The Alice CLI server resolves workspace context, validates the mapped tool and CLI-group policy, resolves out-of-band origin from headers, strictly parses tool input, and wraps execution; trade-decision provenance is attached only when an authoritative session header is present (`src/server/cli.ts:285-376`). The CLI therefore currently needs JSON-compatible tool schemas, stable command-to-tool mapping, workspace policy enforcement, and optional run/session identity; it does not establish a separate UTA-native command protocol.

The packaged `alice-uta` skill documents safe reads separately from mutating commands and requires discovery/search-first source and `aliceId` quoting before contract/order operations (`default/skills/alice-uta/SKILL.md:1-20`, `default/skills/alice-uta/SKILL.md:22-67`, `default/skills/alice-uta/SKILL.md:69-117`). That is an operator-facing convention consumed by the CLI workflow, not evidence that UTA itself performs CLI parsing.

## 7. Consolidated consumer needs (evidence-backed)

The current consumers expose the following concrete needs for any UTA boundary they call:

1. **Source-qualified instrument identity.** AI tools parse `aliceId` with a source prefix; bars use `{sourceId}|{nativeSymbol}` and UTA `aliceId`; UI rows carry source and `aliceId`; CLI guidance asks users to quote source/ID (`src/tool/trading.ts:25-46`, `src/domain/market-data/bars/types.ts:6-15`, `ui/src/components/market/TradeableContractsPanel.tsx:16-48`, `default/skills/alice-uta/SKILL.md:22-67`).
2. **Explicit resolution semantics.** Exact source, provider prefix, source-less all-account fan-out, and trading-only filtering are distinct paths (`src/services/uta-client/UTAManagerSDK.ts:81-129`, `src/tool/trading.ts:108-113`, `src/tool/trading.ts:311-331`).
3. **Uniform but extensible reads.** The same account adapter carries account, positions, orders, quote, derivative discovery, order book, market clock, historical bars, contract search/details, wallet, and histories, with endpoint-specific structured bodies (`src/services/uta-client/UTAAccountSDK.ts:127-279`).
4. **Partial failure and lifecycle states.** AI tools use `Promise.allSettled`; UI preserves stale snapshots or renders degraded state; connector classifies unavailable/expired/not-found/conflict/delivery-failed separately (`src/tool/trading.ts:48-83`, `ui/src/live/account-health.ts:8-47`, `ui/src/pages/PortfolioPage.tsx:409-452`, `packages/connector-protocol/src/types.ts:364-397`).
5. **Capability and quality metadata for bars.** UTA bar reads are conditional on advertised historical support and return quality/freshness metadata; malformed or incomplete data is filtered (`src/domain/market-data/bars/bar-service.ts:262-308`, `src/domain/market-data/bars/quality.ts:1-21`, `src/domain/market-data/bars/freshness.ts:1-45`).
6. **No implicit cross-channel alignment.** Current bar resolution picks one source, while quant scripts receive explicit source-keyed bars and can compose them in the consumer (`src/domain/market-data/bars/bar-service.ts:3-13`, `src/tool/quant.ts:17-95`). No code here establishes a bus-level timestamp alignment rule.
7. **Ledger-aware effect progression.** Place/modify/close/cancel stage first, commit is separate, push/reject use status and pending hashes, and compact output preserves operation/result states (`src/tool/trading.ts:671-871`, `src/tool/trading-compact.ts:116-237`).
8. **Hash/conflict safety.** UI and connector requests include expected pending hashes; connector rejects conflicts and delivery uncertainty instead of automatically retrying an unknown push (`ui/src/api/trading.ts:132-167`, `src/services/connector-client/uta-review.ts:129-219`).
9. **Read-only and policy enforcement at multiple edges.** SDK guards mutations, BFF blocks matched mutations, UI fail-closes `canTrade`, connector blocks readonly pushes, and AI push checks `allowAiTrading` (`src/services/uta-client/UTAAccountSDK.ts:285-362`, `src/webui/routes/trading-proxy.ts:115-215`, `ui/src/hooks/useBrokerPackReadiness.ts:35-109`, `src/services/connector-client/uta-review.ts:129-219`, `src/tool/trading.ts:798-848`).
10. **Independent lifecycle/reload.** Config writes are followed by restart signaling; health includes a changed `startedAt`; SDK reconnect is a supervisor request (`src/webui/routes/trading-config.ts:188-337`, `src/services/uta-supervisor/restart-trigger.ts:1-82`, `src/services/uta-client/UTAManagerSDK.ts:174-200`).
11. **Bounded polling and request deadlines.** BFF requests time out at 30 seconds, health probes at one second, connector ticks at 1.5 seconds, and UI consumers use 3/5/15/30/60/300-second intervals depending on data and interaction (`src/webui/routes/trading-proxy.ts:20-34`, `src/webui/routes/trading-proxy.ts:51-113`, `src/services/connector-client/action-bridge.ts:46-146`, `ui/src/components/PushApprovalPanel.tsx:326-450`, `ui/src/live/account-health.ts:8-47`, `ui/src/live/trading-push.ts:31-74`, `ui/src/pages/PortfolioPage.tsx:139-238`, `ui/src/pages/UTADetailPage.tsx:34-172`, `ui/src/components/market/KlinePanel.tsx:234-278`).
12. **Cross-language serialized transport.** The only observed Alice-to-UTA boundary is HTTP JSON through the SDK/BFF, while CLI and connector also use JSON HTTP/protocol schemas (`src/services/uta-client/UTAManagerSDK.ts:1-19`, `src/webui/routes/trading-proxy.ts:1-19`, `src/workspaces/cli/bin/openalice-cli.cjs:1-23`, `packages/connector-protocol/src/types.ts:287-310`).

## 8. Existing Alice responsibilities and observed gaps

The following responsibilities currently remain in Alice code rather than being supplied by the SDK adapter or a visible UTA implementation:

- **Configuration and credential lifecycle:** Alice masks API responses, seals account configuration, writes owner-only files, preserves existing secrets on edits, and initiates restart/reconnect (`src/webui/routes/trading-config.ts:40-76`, `src/webui/routes/trading-config.ts:188-337`, `src/core/config.ts:704-787`).
- **Process supervision:** Alice chooses the UTA URL, probes health, signals restart by atomic file replacement, and waits for a changed process start time (`src/services/uta-supervisor/url.ts:1-25`, `src/services/uta-supervisor/health.ts:1-42`, `src/services/uta-supervisor/restart-trigger.ts:1-82`).
- **Policy and gateway enforcement:** Alice's main process supplies dynamic AI trading policy, the BFF applies mode/mutation gating, and the UI/connector apply additional readiness and owner gates (`src/main.ts:244-304`, `src/webui/routes/trading-proxy.ts:115-215`, `ui/src/hooks/useBrokerPackReadiness.ts:35-109`, `src/services/connector-client/uta-review.ts:129-219`).
- **Source federation and data hygiene:** Alice selects bar sources, discovers capabilities, filters incomplete bars, caps windows, and labels freshness/quality (`src/domain/market-data/bars/bar-service.ts:3-13`, `src/domain/market-data/bars/bar-service.ts:184-402`, `src/domain/market-data/bars/quality.ts:1-21`, `src/domain/market-data/bars/freshness.ts:1-45`).
- **Consumer-facing presentation:** Alice compacts trading objects for AI, computes FX-converted portfolio summaries, preserves partial failures, and renders connector/UI approval state (`src/tool/trading-compact.ts:1-268`, `src/tool/trading.ts:333-430`, `src/services/connector-client/uta-review.ts:73-260`).
- **Review/delivery orchestration:** Alice polls the connector queue, claims/acks/releases requests, checks expiry/hash/readiness, and presents or fails actions; Telegram owns the owner-facing interaction (`src/services/connector-client/action-bridge.ts:46-146`, `src/services/connector-client/uta-review.ts:19-219`, `services/connector/src/adapters/telegram-uta.ts:177-314`).
- **CLI transport and provenance:** Alice maps commands to tools, parses/validates input, enforces workspace CLI policy, and propagates optional run/session identity (`src/server/cli-commands.ts:212-268`, `src/server/cli.ts:285-376`, `src/workspaces/cli/bin/openalice-cli.cjs:123-179`).

The current SDK also exposes explicit gaps that affect these consumers:

- `UTAManagerSDK.initUTA` and manager-level `getContractDetails` are unsupported, so current config/search callers use restart and account-level routes instead (`src/services/uta-client/UTAManagerSDK.ts:52-79`, `src/services/uta-client/UTAManagerSDK.ts:203-228`; `src/services/uta-client/UTAAccountSDK.ts:225-237`).
- `UTAAccountSDK.getCapabilities` is empty, health methods are optimistic, and `getPendingOrderIds` is empty; summary/capability endpoints are therefore the authoritative paths currently used by Alice (`src/services/uta-client/UTAAccountSDK.ts:88-125`, `src/services/uta-client/UTAAccountSDK.ts:364-401`, `src/services/uta-client/UTAManagerSDK.ts:132-150`).
- `UTAAccountSDK.getHistorical` has a source comment warning that the route may 404 until the phase-one route/per-broker implementation exists; no runtime request was made in this investigation (`src/services/uta-client/UTAAccountSDK.ts:190-208`).
- `getState`, `exportGitState`, and `contractFromAliceId` are unsupported in the SDK, so their availability to current external consumers cannot be inferred from this adapter (`src/services/uta-client/UTAAccountSDK.ts:275-283`, `src/services/uta-client/UTAAccountSDK.ts:364-401`).
- The BFF's literal mutation matcher does not list every wallet endpoint used by the account adapter or AI tools (for example `/wallet/commit`, `/wallet/reject`, and `/wallet/stage-*` are absent from the matcher list); this is an observed code mismatch, not a runtime authorization result (`src/webui/routes/trading-proxy.ts:193-206`, `src/services/uta-client/UTAAccountSDK.ts:285-362`).

- The UTA server source and its actual HTTP route implementations were not present in the inspected Alice repository.

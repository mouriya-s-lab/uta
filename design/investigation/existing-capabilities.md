## Scope and evidence convention

This is a source investigation of the current TypeScript UTA implementation. It does not describe the rewrite design, and it does not treat comments in superseded documents as current behavior. `**Observed code**` means the cited executable path or type declaration says so. `**Inferred from code**` records a consequence of that path rather than a separately executed runtime observation. `**Unknown**` is reserved for behavior not established by the repository. No formatter, build, linter, or test was run, per the read-only investigation constraint.

## 1. Instrument identity

### Wire shape and UTA stamping

- **Observed code:** The protocol augments the IBKR `Contract` with optional `aliceId`; its documented wire form is `{utaId}|{nativeKey}`. The protocol explicitly says `localSymbol` is not a cross-broker uniqueness primitive and that each broker supplies its own native key (`packages/uta-protocol/src/types/contract-ext.ts:1-23`).
- **Observed code:** `UnifiedTradingAccount` stamps every position and order returned by its internal state read, then keeps only `Submitted`/`PreSubmitted` orders in `pendingOrders` (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:157-177`). The UTA also stamps returned positions, orders, quotes, search results, expansion leaves, and contract details (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:1026-1030,1126-1137,1164-1183,1198-1202`).
- **Observed code:** Stamping calls `broker.getNativeKey(contract)` and writes `${this.id}|${nativeKey}` (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:509-513`).

### Native-key rules by broker

- **Observed code:** IBKR uses a numeric `conId` when available; a bond without `conId` may use `issuer:{issuerId}` as a directory key; otherwise it falls back to the symbol. Numeric keys resolve as conIds, while nonnumeric keys are convenience STK symbols with SMART/USD defaults. Issuer keys deliberately throw because they are directories, not tradeable contracts (`services/uta/src/domain/trading/brokers/ibkr/IbkrBroker.ts:881-918`).
- **Observed code:** CCXT uses `localSymbol`, which is the unified wire/market-table symbol. Resolution first looks up that key and otherwise returns a skeletal contract whose `localSymbol` is the native key; market-dependent operations are expected to fail later if metadata is unavailable (`services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:1335-1355`). The conversion helper treats `localSymbol` and then `symbol` as CCXT market keys, and only falls back to a unique base/secType search (`services/uta/src/domain/trading/brokers/ccxt/ccxt-contracts.ts:113-143`).
- **Observed code:** Alpaca’s `resolveSymbol` uses an option’s `localSymbol`, rejects unsupported non-STK/non-CRYPTO types, and otherwise uses the upper-case ticker. Its native key delegates to that resolver or the contract symbol (`services/uta/src/domain/trading/brokers/alpaca/alpaca-contracts.ts:19-44; services/uta/src/domain/trading/brokers/alpaca/AlpacaBroker.ts:681-689`). The parser distinguishes OCC options, crypto pairs, and stocks (`services/uta/src/domain/trading/brokers/alpaca/alpaca-contracts.ts:19-38`).
- **Observed code:** Longbridge preserves suffixed symbols such as `700.HK` or `AAPL.US` as `localSymbol`; a bare ticker defaults to US, and a CNY/CNH fallback suffix is ambiguous because it chooses SH over SZ (`services/uta/src/domain/trading/brokers/longbridge/longbridge-contracts.ts:1-81`). The broker native key is the resolved suffixed symbol (`services/uta/src/domain/trading/brokers/longbridge/LongbridgeBroker.ts:683-692`).
- **Observed code:** LeverUp uses `localSymbol || symbol`, resolves known pairs from its network pair list, and otherwise emits a skeletal `CRYPTO_PERP` contract with exchange `LEVERUP` (`services/uta/src/domain/trading/brokers/others/leverup/LeverupBroker.ts:529-546`).
- **Observed code:** Mock uses `localSymbol || symbol`; its registry preserves previously seen derivative metadata, and unknown keys resolve to a skeletal STK contract (`services/uta/src/domain/trading/brokers/mock/MockBroker.ts:523-544`).

### Resolution and cross-account routing

- **Observed code:** `contractFromAliceId` parses the first `|`, checks that the embedded UTA id equals the current account id, calls that broker’s `resolveNativeKey`, and restores the supplied aliceId on the returned contract (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:515-544`). `expandContract` repeats the format and ownership checks before passing only the native key to the broker (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:1164-1177`).
- **Observed code:** Manager source routing is exact map lookup by UTA id; an absent source returns every registered UTA, and `resolveOne` errors when no exact id is found (`services/uta/src/domain/trading/uta-manager.ts:179-200`).
- **Observed code:** The flat tradeable-search path includes `source` on every hit, stamps contracts through each target UTA, and can target one exact source or every `asVendor !== false` account (`services/uta/src/domain/trading/contract-search.ts:27-64`). The manager’s grouped search independently filters to vendor accounts, skips unhealthy accounts, and returns only nonempty groups (`services/uta/src/domain/trading/uta-manager.ts:270-295`).

## 2. Contract search fan-out and ranking

### Shared normalization and fan-out

- **Observed code:** `normalizeBrokerSearchPattern` trims input. For `crypto` and `currency` it strips a known concatenated quote suffix (`USDT`, `USDC`, `BUSD`, `USD`, `EUR`, `JPY`, `GBP`, or `CNY`) only when the remaining base has at least two characters; equity, commodity, and unknown classes pass through unchanged (`packages/uta-protocol/src/brokers/search-rules.ts:14-54`).
- **Observed code:** `searchTradeableContracts` returns immediately for an empty normalized pattern, chooses one exact source or all vendor-participating UTAs, and calls their searches concurrently with `Promise.allSettled`. Rejected accounts are dropped; fulfilled descriptions become flat hits containing source, contract, derivative hints, and optional venue-provided asset class (`services/uta/src/domain/trading/contract-search.ts:27-64`).
- **Observed code:** The flat path appends hits in target/result order and performs no global sort or deduplication after fan-out (`services/uta/src/domain/trading/contract-search.ts:44-64`). This is an inference from the only post-fan-out loop: no ranking or deduplication operation occurs there.

### Shared cached-catalog ranking

- **Observed code:** The shared ranker scores exact symbol/base/name at 100; symbol/base prefix at 80; name word-boundary prefix at 70; whole-word name at 50; symbol/local/name substring at 30; exact quote currency at 20; and drops zero-score entries (`services/uta/src/domain/trading/brokers/fuzzy-rank.ts:36-73`).
- **Observed code:** It trims the query, computes scores once, stable-sorts by descending score and original index, defaults to 50 results, and copies each winning contract into a new `ContractDescription` (`services/uta/src/domain/trading/brokers/fuzzy-rank.ts:75-98`).

### Broker-specific search behavior

- **Observed code:** CCXT considers active markets with base and quote fields whose quote is USDT, USD, or USDC. It pre-sorts swap, future, spot, option, then USDT/USD/USDC, feeds candidates to the shared ranker, and skips markets that fail strict contract construction (`services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:434-488`). It then builds one derivative-type set from all ranked results and assigns the resulting array to every description (`services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:490-503`).
- **Observed code:** Alpaca refreshes active assets and removes `tradable === false` entries. Before the catalog exists, it echoes one upper-case guessed contract; after loading, it ranks catalog entries and marks each STK result as having an OPT derivative family (`services/uta/src/domain/trading/brokers/alpaca/AlpacaBroker.ts:223-265`).
- **Observed code:** IBKR sends `reqMatchingSymbols` after stripping a dot suffix from the request and retains the suffix as a currency filter for CASH expansion. CASH family rows without conId are expanded through contract details; other rows, including conId leaves and issuer hubs, pass through (`services/uta/src/domain/trading/brokers/ibkr/IbkrBroker.ts:239-285`).
- **Observed code:** Longbridge has no general fuzzy search endpoint in this adapter; it echoes the pattern as an exact-symbol guess (`services/uta/src/domain/trading/brokers/longbridge/LongbridgeBroker.ts:235-244`).
- **Observed code:** LeverUp filters its static pair list by case-insensitive substring of base or pair symbol and returns matches in pair-list order (`services/uta/src/domain/trading/brokers/others/leverup/LeverupBroker.ts:167-180`).
- **Observed code:** Mock records the query but always returns one default contract description, independent of the pattern (`services/uta/src/domain/trading/brokers/mock/MockBroker.ts:259-265`).

## 3. Expansion hub and leaf

- **Observed code:** The protocol models expansion as either concrete `contracts` or an `optionGrid`; filters include expiry, right, strike bounds, derivative family, and a limit capped at 200 with a default of 60 (`packages/uta-protocol/src/types/broker.ts:182-223`).
- **Observed code:** UTA refuses expansion with a `CONFIG` broker error when the adapter has no optional `expandContract`, validates the UTA-qualified aliceId, passes the native key and filters to the broker, and stamps every returned contract (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:1157-1177`).
- **Observed code:** IBKR accepts `issuer:` hubs and expands them into individual bonds, annotating missing description/maturity and sorting by maturity. It accepts a numeric conId for derivative expansion; `FUT` or any supplied expiry requests concrete leaves, filters strike/right, sorts by expiry/strike/right, and reports the pre-limit total. An option request without expiry calls `reqSecDefOptParams`, returns per-exchange grids with SMART first, and supplies a next-step hint (`services/uta/src/domain/trading/brokers/ibkr/IbkrBroker.ts:384-475`).
- **Observed code:** Alpaca expands only a stock into options, rejects a non-STK underlying or a non-OPT requested family, requires `YYYYMMDD`, drains paginated option contracts while rejecting repeated page tokens, applies right/strike filters at the API call, returns the full row count, caps returned rows at 200 (default 60), and marks the result read-only (`services/uta/src/domain/trading/brokers/alpaca/AlpacaBroker.ts:702-721`).
- **Inferred from code:** In the inspected adapters, there is no generic UTA-side expansion fallback for adapters that do not implement the optional method; those requests terminate at the explicit unsupported-capability error (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:1164-1167`).

## 4. Order-entry validation

### Stage/commit/push surface

- **Observed code:** `executeOneShotOrder` is a convenience wrapper around stage, synchronous commit, and asynchronous push. It labels failures by phase and returns a `PushResult` only when all phases complete (`services/uta/src/domain/trading/order-entry.ts:29-73`).
- **Observed code:** `stagePlaceOrder` rejects keyless accounts, applies the order-type gate, resolves the aliceId to a full contract, overlays an explicitly supplied symbol, resolves/stamps sub-account intent, converts supplied numeric strings to Decimal order fields, constructs optional TP/SL, and calls `git.add` (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:693-725`). Modify staging converts only fields supplied; cancel staging only stores the order id (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:727-771`).
- **Observed code:** UTA dispatch rejects all account mutations for `readOnly` accounts, which includes keyless accounts by default; its dispatcher sends place/modify/close/cancel operations to the broker and rechecks an explicit close quantity immediately before the broker call (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:180-199,549-563`).

### Quantity, cash notional, and order terms

- **Observed code:** Place staging treats a non-null/nonempty `totalQuantity` and `cashQty` as mutually exclusive. MKT requires one of them; non-MKT rejects `cashQty` and requires `totalQuantity`. LMT requires `lmtPrice`; STP requires `auxPrice`; STP LMT requires both; TRAIL and TRAIL LIMIT require exactly one of `auxPrice`/`trailingPercent`, with TRAIL LIMIT also requiring `lmtPrice` (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:597-638`).
- **Observed code:** Explicit close quantities are parsed as Decimal and must be finite and positive at stage time. Just before dispatch, UTA reads current positions, matches by broker native key, rejects a missing position, and rejects a quantity larger than the absolute available position (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:572-595,742-766`).
- **Observed code:** The place gate checks presence and exclusivity, not that a place `totalQuantity` or `cashQty` is numerically positive/finite; the individual adapter receives the Decimal after staging (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:603-616,708-713`).
- **Observed code:** A multi-sub-account connection must have an explicit selector, the selector must be known, and an adapter-declared instrument-to-sub-account mapping must agree with it. A single or not-yet-probed connection returns no selector requirement (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:657-688`). CCXT derives spot versus derivative routing from `CRYPTO_PERP`/`FUT`, lists override-defined wallets, and rejects unknown read selectors (`services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:743-777`).
- **Observed code:** Sub-account ids staged in a write are not fields in the operation; UTA appends a `[sub:...]` tag to the commit message and clears the transient tracker after `commit` (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:774-790`).

### Adapter-level acceptance and rejection

- **Observed code:** IBKR refuses any attached TP/SL before routing the order. Otherwise it resolves the routable contract, obtains a numeric order id, submits through the bridge, and returns the bridge’s `OrderState` (`services/uta/src/domain/trading/brokers/ibkr/IbkrBroker.ts:480-505`).
- **Observed code:** CCXT converts `cashQty` into size using an explicit limit price or ticker price; attached TP/SL is refused without a venue override; STP/STP LMT are represented as a base market/limit order plus `triggerPrice`; TRAIL/TRAIL LIMIT are refused without verified support (`services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:524-610`).
- **Observed code:** Alpaca permits stock and crypto order construction, restricts crypto to MKT/LMT/STP LMT and GTC/IOC, rejects crypto attached TP/SL or extended-hours flags, accepts either quantity or notional, and maps one TP/SL leg to OTO or two legs to bracket (`services/uta/src/domain/trading/brokers/alpaca/AlpacaBroker.ts:290-349`).
- **Observed code:** Longbridge requires a resolvable suffixed symbol, supported order type and time-in-force, and positive total quantity. The method accepts a TP/SL argument but names it `_tpsl` and does not translate it (`services/uta/src/domain/trading/brokers/longbridge/LongbridgeBroker.ts:271-312`).
- **Observed code:** LeverUp accepts only MKT orders with total quantity, computes 1x notional/margin from a Pyth price, and serializes supplied stop-loss/take-profit prices into its relayer `openData` (`services/uta/src/domain/trading/brokers/others/leverup/LeverupBroker.ts:213-256`).
- **Observed code:** Mock uses only `totalQuantity` when placing an order; market orders fill immediately at mark price or 100, while non-market orders are stored as Submitted (`services/uta/src/domain/trading/brokers/mock/MockBroker.ts:278-325`).

## 5. Order lifecycle statuses and venue mapping

### Ledger status vocabulary and push

- **Observed code:** The protocol status union is `submitted | filled | rejected | cancelled | user-rejected`; results may carry `orderId`, native `OrderState`, execution, fill quantity/price, bracket legs, symbol, and raw response (`packages/uta-protocol/src/types/git.ts:56-77`).
- **Observed code:** `TradingGit.executePush` executes staged operations sequentially. A thrown adapter error is converted into `{success:false,status:'rejected'}`; a successful response is parsed into a mapped status. After execution it reads state, appends one commit, calls `onCommit`, clears staging, and partitions results into `rejected` versus `submitted` solely by `success` (`services/uta/src/domain/trading/git/TradingGit.ts:129-185`).
- **Observed code:** Successful response parsing copies action, order id, mapped status, order state, optional legs, and raw response, but does not copy raw `execution`, `filledQty`, or `filledPrice` (`services/uta/src/domain/trading/git/TradingGit.ts:929-967`). Status mapping is Filled→filled, Cancelled→cancelled, Inactive→rejected, and every other status→submitted (`services/uta/src/domain/trading/git/TradingGit.ts:969-977`).

### Venue status mappings

- **Observed code:** IBKR returns native bridge `OrderState` for place/modify and explicitly returns Cancelled for cancel. The request bridge collects `openOrder`, caches fill quantity/average price from `orderStatus`, and resolves a pending cancel when status is Cancelled (`services/uta/src/domain/trading/brokers/ibkr/IbkrBroker.ts:491-555; services/uta/src/domain/trading/brokers/ibkr/request-bridge.ts:738-777`).
- **Observed code:** CCXT maps `closed`→Filled, `open`→Submitted, `canceled/cancelled`→Cancelled, `expired/rejected`→Inactive, and unknown status→Submitted (`services/uta/src/domain/trading/brokers/ccxt/ccxt-contracts.ts:36-52`). Its order conversion preserves string order id, average, filled quantity, and TP/SL prices (`services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:1127-1183`).
- **Observed code:** Alpaca maps `filled`→Filled; new/accepted/pending-new/accepted-for-bidding→Submitted; canceled/expired/replaced→Cancelled; partially-filled→Submitted; done-for-day/suspended/rejected→Inactive; unknown→Submitted (`services/uta/src/domain/trading/brokers/alpaca/alpaca-contracts.ts:46-76`). Its open-order mapping preserves string id, filled quantity, average fill, and bracket-derived TP/SL (`services/uta/src/domain/trading/brokers/alpaca/AlpacaBroker.ts:758-803`).
- **Observed code:** Longbridge maps numeric status 5→Filled, 14/16→Inactive, 15/17→Cancelled, partial-filled and pending/replacement/cancel variants→Submitted, and unknown→Submitted (`services/uta/src/domain/trading/brokers/longbridge/longbridge-contracts.ts:109-143`).
- **Observed code:** LeverUp starts a submitted relayer order, checks its status on each `getOrder` while still submitted, and changes it to Filled when executed successfully or Inactive when executed unsuccessfully (`services/uta/src/domain/trading/brokers/others/leverup/LeverupBroker.ts:460-491`). A separate helper can poll every 1.5 seconds for up to 30 seconds, but the broker’s `getOrder` path performs only one status request (`services/uta/src/domain/trading/brokers/others/leverup/relayer-client.ts:74-93; services/uta/src/domain/trading/brokers/others/leverup/LeverupBroker.ts:465-477`).
- **Observed code:** Mock market orders become Filled immediately; limit/stop orders become Submitted; manual fills accumulate quantity and weighted-average price, retaining Submitted status for a partial fill and changing to Filled at completion; pending cancellation becomes Cancelled (`services/uta/src/domain/trading/brokers/mock/MockBroker.ts:278-325,357-366,580-621`).

### Bracket and pending identity

- **Observed code:** Alpaca place responses extract child TP/SL ids and return them as `legs`, because its held stop leg may not appear in open-order listing. The protocol and `TradingGit.getPendingOrderIds` treat those legs as separately pending order ids (`services/uta/src/domain/trading/brokers/alpaca/AlpacaBroker.ts:351-367; packages/uta-protocol/src/types/broker.ts:157-180; services/uta/src/domain/trading/git/TradingGit.ts:692-745`).
- **Observed code:** The protocol’s `OpenOrder.orderId` is a broker-native string, while `order.orderId` remains an IBKR-shaped number; this distinction exists because large CCXT ids can exceed safe numeric precision (`packages/uta-protocol/src/types/broker.ts:226-246`).

## 6. Order-sync poller lanes and reconcile/observed synthesis

### UTA sync strategies

- **Observed code:** With `getOpenOrders`, UTA makes one listing call, treats listed pending ids as alive, and calls `getOrder` only for pending ids absent from the listing. Without a listing capability, it selects candidates through in-memory age backoff (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:827-865`).
- **Observed code:** Candidate orders are fetched one by one. Submitted/PreSubmitted results produce no update; every other status becomes Filled, Cancelled, or rejected, with filled quantity taken from `order.filledQuantity` and price from `avgFillPrice`. Filled without either field emits a warning but still advances the status update (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:868-915`).
- **Observed code:** Per-order backoff is eager for orders younger than two minutes, once per minute until one hour, and once per five minutes thereafter. Its first-seen/last-polled map is process-local and resets after restart (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:931-950`).

### External-order observation

- **Observed code:** `observeExternalOrders` requires an open-order listing capability, diffs listed ids against every order id in the ledger, stamps unknown contracts, obtains a state snapshot, and records all unknown orders in one squashed `[observed]` commit with submitted results (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:953-980; services/uta/src/domain/trading/git/TradingGit.ts:330-376`).
- **Observed code:** Once recorded, observed order ids participate in ordinary pending-id scanning and sync. Brokers without enumeration return zero without additional calls (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:953-980`).

### Poller cadence and isolation

- **Observed code:** The poller defaults to a 10-second fast lane and a 15-minute observation lane. The observation lane fires on the first tick and then every rounded interval count; nonpositive observation intervals disable it (`services/uta/src/domain/trading/order-sync-poller.ts:20-61`).
- **Observed code:** Each tick has a re-entry guard. It skips keyless or non-healthy accounts, performs slow observation first when due, then checks for pending ids before invoking sync. Observation and sync failures are logged per account and do not stop other accounts (`services/uta/src/domain/trading/order-sync-poller.ts:53-95`). Main configures the lanes from `observeExternalOrdersEvery`, with malformed durations falling back to 15 minutes (`services/uta/src/main.ts:116-128; src/core/config.ts:395-410`).

### Reconciliation synthesis

- **Observed code:** For positions marked `avgCostSource: 'wallet'`, UTA reconstructs projected quantity from the commit log, computes actual-minus-projected drift, suppresses reconcile recording while an order for that aliceId is pending, and otherwise records a `reconcileBalance` at broker average cost when positive or market price as fallback (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:1040-1087`).
- **Observed code:** Reconcile result quantity is absolute drift and result price is the mark; nonnegative drift is described as observed/buy and negative drift as released/sell (`services/uta/src/domain/trading/git/TradingGit.ts:272-327`). UTA then recomputes WAC and mutates avg cost and multiplier-aware unrealized PnL on the returned position (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:1089-1105`).
- **Observed code:** The synthetic reconcile state has zeroed monetary fields and no pending orders while reusing the supplied positions (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:1108-1123`).

## 7. Projections: order history, trade history, and cost basis

### Shared position arithmetic

- **Observed code:** Position math treats quantity, avg cost, and market price as per-unit; multiplier defaults to one; market value is `quantity × marketPrice × multiplier`; unrealized PnL applies a positive sign for long and negative sign for short (`services/uta/src/domain/trading/position-math.ts:1-79`). Account aggregation adds cash plus signed market values, subtracting short notional (`services/uta/src/domain/trading/position-math.ts:81-118`).
- **Observed code:** `buildContract` validates universal fields and derivative-specific fields; OPT/FOP require expiry, strike, right, and multiplier, while FUT requires expiry and multiplier. `buildPosition` always emits a multiplier, rejects OPT/FOP multiplier one/empty, and either passes through both precomputed monetary fields or derives both (`services/uta/src/domain/trading/contract-discipline.ts:30-61,68-110; services/uta/src/domain/trading/brokers/contract-builder.ts:49-73,102-160`).

### Order-history projection

- **Observed code:** Contract projection preserves aliceId, symbol/localSymbol, secType, currency, exchange, expiry, positive non-sentinel strike, normalized C/P right, and multiplier. Decimal order fields are emitted as strings with sentinel values omitted (`services/uta/src/domain/trading/order-history.ts:24-68`).
- **Observed code:** `projectOrderHistory` creates one row for place, observed external, and close operations. Close is represented as SELL/MKT; other rows use the stored order fields. Status defaults to rejected, fills and errors are copied, and source is `external` only for observed orders. Rows with an order id are indexed by id; pre-submit rows without one are kept anonymously (`services/uta/src/domain/trading/order-history.ts:70-98`).
- **Observed code:** A successful cancel resolves an existing row and marks it cancelled; unknown cancels create no projected row. Sync results update matching rows with status, resolvedAt, and fill fields. Rows sort newest first, and a truthy limit is applied (`services/uta/src/domain/trading/order-history.ts:101-131`).

### Trade-history projection

- **Observed code:** `projectTradeHistory` first maps order ids to originating operation contract, side, and multiplier. It emits only successful filled place/close/observed results, later sync fills, and successful reconcile fills; duplicate origin/sync fills are suppressed by order id (`services/uta/src/domain/trading/order-history.ts:133-245`).
- **Observed code:** Trade value is Decimal quantity × price × multiplier. Source is `order`, `external`, or `reconcile`; reconcile uses a synthetic contract containing only aliceId and side from the quantity delta. Results sort newest first and use truthy-limit semantics (`services/uta/src/domain/trading/order-history.ts:158-250`).

### Wallet WAC cost basis

- **Observed code:** Cost-basis replay scans place, close, observed, and reconcile fills. Buys update weighted average; sells reduce quantity without changing average until quantity reaches zero/negative, when avg and qty reset to zero. Sync fills are attributed through an order-id metadata pre-pass and counted once (`services/uta/src/domain/trading/cost-basis.ts:38-133`).
- **Observed code:** Direction is BUY unless a place/observed order action is SELL, always SELL for close, and determined by the sign of reconcile quantity delta. No relevant fill returns null (`services/uta/src/domain/trading/cost-basis.ts:132-166`).
- **Observed code:** The source comments and implementation describe WAC only, long-only spot-style behavior, no FIFO/splits/rebases/short modeling, and first-observation pricing for pre-Alice deposits (`services/uta/src/domain/trading/cost-basis.ts:1-24`).
- **Observed code:** UTA only replaces account-level unrealized PnL with the sum of position PnLs when every position currency equals the account base currency (or is omitted); mixed-currency accounts retain broker-reported PnL (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:993-1023`).

## 8. Guards: inputs, thresholds, and failures

- **Observed code:** A configured guard pipeline reads positions and account info concurrently from the broker, constructs a context, checks guards in configured order, returns the first rejection as `{success:false,error:'[guard:name] ...'}`, and otherwise invokes the dispatcher (`services/uta/src/domain/trading/guards/guard-pipeline.ts:13-36`). UTA wires this pipeline around its broker dispatcher before giving it to TradingGit (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:180-205`).
- **Observed code:** `max-position-size` applies only to placeOrder, matches an existing position by `contract.symbol`, estimates added value from positive cashQty or quantity × existing market price, defaults to 25% of equity, and rejects only when projected percentage is greater than the configured limit. It allows an unestimated new-symbol quantity (`services/uta/src/domain/trading/guards/max-position-size.ts:5-48`).
- **Observed code:** `cooldown` applies only to placeOrder, keys by `getOperationSymbol`, defaults to a 60-second interval, returns remaining whole seconds while active, and records the current timestamp as soon as the check passes (`services/uta/src/domain/trading/guards/cooldown.ts:4-32`).
- **Observed code:** `symbol-whitelist` requires a nonempty configured array, allows operations whose symbol resolves to `unknown`, and rejects any known operation symbol absent from its set (`services/uta/src/domain/trading/guards/symbol-whitelist.ts:4-24`).
- **Observed code:** The registry supports the three built-ins and custom registrations. An unknown configured guard logs a warning and is skipped; options default to an empty record (`services/uta/src/domain/trading/guards/registry.ts:6-34`).

## 9. Snapshots: capture, timing, and storage

### Captured shape and triggers

- **Observed code:** Snapshot triggers are `scheduled`, `post-push`, `post-reject`, and `manual`. A snapshot stores account strings, position identity/financial fields plus derivative metadata, pending open-order fields, health, head commit, and pending commit hashes (`services/uta/src/domain/trading/snapshot/types.ts:10-80`).
- **Observed code:** `buildSnapshot` returns null only up front for disabled/offline UTA health, runs `uta.sync()` best-effort, then reads account, positions, and ledger-pending orders. It filters captured orders to Submitted/PreSubmitted and stores UTA health as disabled or the current health (`services/uta/src/domain/trading/snapshot/builder.ts:13-31,35-84`).
- **Observed code:** Main wires post-push and post-reject hooks to per-account snapshot calls and starts the configured scheduler (`services/uta/src/main.ts:102-114`). The scheduler uses a private interval pump and directly calls `takeAllSnapshots('scheduled')`, without an event-log timer event (`services/uta/src/domain/trading/snapshot/scheduler.ts:1-56`).

### Service retry and persistence

- **Observed code:** The service caches one store per account, skips null builds with `snapshot.skipped`, appends successful snapshots and emits `snapshot.taken`, emits `snapshot.error` on exceptions, and retries all null accounts once after 3 seconds in `takeAllSnapshots` (`services/uta/src/domain/trading/snapshot/service.ts:18-109`).
- **Observed code:** The default layout is `data/trading/{accountId}/snapshots/index.json` plus `chunk-0001.jsonl` onward. Each chunk holds at most 50 snapshots; appends are serialized per store, the index is written through a same-directory temporary file and rename, and reads walk chunks/lines newest first with optional time bounds/limit (`services/uta/src/domain/trading/snapshot/store.ts:1-16,23-85,127-169`).
- **Observed code:** The snapshot config defaults to enabled and every 15 minutes, and rejects a configured interval that `parseDuration` cannot parse (`src/core/config.ts:373-382`).

## 13. Health, tier, reach, and recovery timing

- **Observed code:** Reach is a capability ladder: `down` means transport unavailable, `connected` means broker/public data is reachable, and `readable` means private account reads work. Tiers are `data`, `account`, and `trading`; both funded tiers target readable, while data targets connected. Writing is not probed as a reach level (`packages/uta-protocol/src/types/broker.ts:366-390`).
- **Observed code:** UTA marks disabled or down accounts offline; three consecutive failures make a reachable account degraded, six make it offline, and a reachable-but-below-target funded account is degraded (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:99-109,231-282`).
- **Observed code:** Initial connect is asynchronous and starts with optimistic target reach. Reads wait up to 1.5 seconds for the initial connect, then return a transient CONNECTING error while the background connect continues. The initial probe calls `broker.init`, and for funded accounts calls `getAccount` to distinguish connected from readable (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:141-151,211-228,285-310,395-437`).
- **Observed code:** Permanent structured BrokerErrors disable the UTA. Ordinary call failures increment counters; offline accounts enter recovery with delays `min(5000 × 2^attempt, 60000)`; a successful target probe resets counters and recovery state (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:313-328,440-505`). Explicit broker connection-dead events force down/offline and restored events nudge recovery (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:330-352`).
- **Observed code:** Manager aggregation and grouped search do not use unhealthy accounts for data; they nudge recovery and return null/empty account results for that pass (`services/uta/src/domain/trading/uta-manager.ts:205-220,272-295`).

## Observed defects and implementation risks

These are findings about the current source, not rewrite requirements.

1. **Observed control-flow gap:** A read contract containing both an aliceId and a populated `symbol`/`localSymbol` bypasses `_expandAliceIdIfNeeded` and therefore bypasses `contractFromAliceId`’s UTA ownership check. `getQuote` and `getContractDetails` use that helper, which returns the caller’s object whenever native fields are present (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:1132-1135,1198-1213`). The direct resolver does enforce ownership (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:534-544`).
2. **Observed validation gap:** Place staging validates field presence and exclusivity but does not reject zero, negative, NaN, or infinite place quantities/notionals before constructing the operation (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:603-616,693-713`). Adapter-level checks differ; for example Longbridge explicitly checks positive total quantity (`services/uta/src/domain/trading/brokers/longbridge/LongbridgeBroker.ts:287-289`).
3. **Observed race window:** `_resolveWriteSubAccount` treats a null cache as an empty/single-sub-account connection, while the constructor starts asynchronous connection and only later warms the sub-account cache. A write staged in that interval can avoid the multi-wallet selector requirement (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:130-139,211-222,367-371,642-668`).
4. **Observed stale contract/comment:** `executeOneShotOrder` says a commit failure rolls the staging area back, but its commit catch only returns a phase error; it does not call `reject` or clear staging (`services/uta/src/domain/trading/order-entry.ts:35-43,56-64`).
5. **Observed failure classification risk:** Any exception from an operation is persisted as `success:false,status:'rejected'`, and the status union has no unknown/indeterminate value. If a venue accepted an order but the response/transport failed, the source therefore records rejection; the possible duplicate-retry consequence is an inference from this classification (`services/uta/src/domain/trading/git/TradingGit.ts:141-155; packages/uta-protocol/src/types/git.ts:56-71`).
6. **Observed post-side-effect persistence window:** `executePush` calls broker operations, then `getGitState`, appends the commit, calls `onCommit`, and only then clears staging/pending state. A failure in state read or persistence after venue side effects leaves the prepared batch uncleared; retry/duplicate effects are an inferred consequence (`services/uta/src/domain/trading/git/TradingGit.ts:157-184`).
7. **Observed fill-data loss:** Successful place/modify/close responses may carry `execution`, `filledQty`, and `filledPrice` in the protocol, but `parseOperationResult` omits those fields and copies only order state, id, legs, and raw. The projections consume `filledQty`/`filledPrice`, so immediate-fill execution data can be absent from the ledger result (`packages/uta-protocol/src/types/git.ts:60-77; services/uta/src/domain/trading/git/TradingGit.ts:929-967; services/uta/src/domain/trading/order-history.ts:80-95`).
8. **Observed sync status collapse:** UTA’s sync maps every non-Submitted/PreSubmitted result other than exact Filled and Cancelled to rejected. Venue adapters can expose partial/other statuses, while the protocol has no partial status, so such statuses can be falsely terminal-rejected (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:874-905; packages/uta-protocol/src/types/git.ts:56-69`).
9. **Inferred observed-order state mismatch:** `observeExternalOrders` computes `stateAfter` with `_getState` before calling `recordObservedOrders`; `_getState` derives pending ids from the ledger before the new external ids exist. Thus the observed commit’s `stateAfter.pendingOrders` does not include the newly recorded orders, even though later pending-id scans do (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:953-978,157-177`).
10. **Observed helper inconsistency:** Cost-basis replay includes `observeExternalOrder` in its originating metadata and direction handling, but `isCostBasisRelevant` excludes that action. No caller of the helper was established in this investigation; the two executable definitions remain inconsistent (`services/uta/src/domain/trading/cost-basis.ts:52-67,136-173`).
11. **Observed CCXT search metadata issue:** CCXT accumulates derivative types globally across ranked results and assigns the same `derivativeSecTypes` array to every description, rather than deriving the family per hit (`services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:493-501`).
12. **Observed Mock parity gaps:** UTA accepts MKT `cashQty` and passes TP/SL to Mock, but Mock computes quantity only from `order.totalQuantity` and only records the TP/SL argument in its call log; its internal order/result structures have no TP/SL fields. A cash-notional order can therefore reach Mock with zero quantity, and attached protection is not simulated (`services/uta/src/domain/trading/UnifiedTradingAccount.ts:603-616,708-722; services/uta/src/domain/trading/brokers/mock/MockBroker.ts:65-75,278-324`).
13. **Observed Longbridge identity loss:** `mapOpenOrder` sets `order.orderId = 0` and returns no `OpenOrder.orderId`, despite the protocol distinguishing the required broker-native string id from the numeric IBKR-shaped field. The comment says the string is preserved through placement, but the open-order mapping itself does not preserve it (`services/uta/src/domain/trading/brokers/longbridge/LongbridgeBroker.ts:696-713; packages/uta-protocol/src/types/broker.ts:226-243`).
14. **Observed LeverUp data loss:** LeverUp `getOrder` returns contract, action/type/quantity, and status but no `OpenOrder.orderId`, average fill, or filled quantity/price. This leaves the UTA sync path without execution data for a relayer order (`services/uta/src/domain/trading/brokers/others/leverup/LeverupBroker.ts:479-491; services/uta/src/domain/trading/UnifiedTradingAccount.ts:870-905`).
15. **Observed initialization-order risk:** Main creates and initializes UTAs before constructing the FxService and calling `utaManager.setFxService`; the factory injects FX only at broker creation, and Longbridge’s setter stores it on the broker. Existing Longbridge instances therefore take the no-FX balance branch until a later broker recreation; that effect is an inference from the ordering and setter paths (`services/uta/src/main.ts:63-100; services/uta/src/domain/trading/brokers/factory.ts:27-47; services/uta/src/domain/trading/brokers/longbridge/LongbridgeBroker.ts:160-171,393-409; services/uta/src/domain/trading/uta-manager.ts:55-57`).
16. **Observed keyless snapshot mismatch:** Snapshot building checks disabled/offline but not `uta.keyless`; the scheduler asks the service to snapshot every manager account, while keyless CCXT account/positions are intentionally zero/empty. A scheduled or manual snapshot can therefore persist a zero-valued keyless snapshot (`services/uta/src/domain/trading/snapshot/builder.ts:13-31; services/uta/src/domain/trading/snapshot/service.ts:78-101; services/uta/src/domain/trading/brokers/ccxt/CcxtBroker.ts:947-952,1047-1049`).
17. **Observed legacy-path collision:** Both `alpaca-paper` and `alpaca-live` legacy ids fall back to the same `data/securities-trading/commit.json`, so an old shared file can be considered for either account when its new per-account file is absent (`services/uta/src/domain/trading/git-persistence.ts:18-39`).
18. **Observed guard bypass of UTA health accounting:** The guard pipeline reads positions/account directly from `IBroker`, whereas ordinary UTA reads are wrapped by `_callBroker` for failure counting, health transitions, and BrokerError conversion. Guard-read failures therefore do not follow the normal UTA call wrapper (`services/uta/src/domain/trading/guards/guard-pipeline.ts:20-24; services/uta/src/domain/trading/UnifiedTradingAccount.ts:409-437`).
19. **Observed guard protection gaps:** Max-position-size matches only symbols and allows an unestimated new-symbol quantity; cooldown records a timestamp before broker dispatch; and unknown guard types are silently skipped after a warning (`services/uta/src/domain/trading/guards/max-position-size.ts:15-45; services/uta/src/domain/trading/guards/cooldown.ts:15-31; services/uta/src/domain/trading/guards/registry.ts:21-34`).
20. **Observed recovery-state loss:** `TradingGit.restore` rehydrates committed history and head but does not restore `currentRound`, staging, or a pending approval hash/message. A restart therefore loses an in-progress prepared batch and round context (`services/uta/src/domain/trading/git/TradingGit.ts:61-69,572-576,648-650`).

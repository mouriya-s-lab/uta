# Venue capability investigation — summary (1/15)
2/15 **Observed routing:** The preset catalog exposes Binance, OKX, Bybit, Hyperliquid, Bitget, Alpaca, IBKR, Longbridge, LeverUp, and Mock; the five crypto presets all use the CCXT engine (`packages/uta-protocol/src/brokers/preset-catalog.ts:108-292`).
3/15 **Observed official Alpaca capability:** Trading and market-data WebSockets expose `trade_updates`, trades, quotes, bars, updated bars, daily bars, and crypto order books; REST provides `client_order_id` lookup and paginated bars ([Alpaca streaming](https://docs.alpaca.markets/us/docs/websocket-streaming), [crypto stream](https://docs.alpaca.markets/us/docs/real-time-crypto-pricing-data), [client lookup](https://docs.alpaca.markets/us/reference/getorderbyclientorderid)).
4/15 **Observed official IBKR capability:** TWS API offers continuous `reqMktData`, tick-by-tick trades/bid-ask, five-second realtime bars, Level-II depth, account callbacks, and order callbacks; small historical bars have explicit pacing ([market data](https://interactivebrokers.github.io/tws-api/historical_bars.html), [depth](https://interactivebrokers.github.io/tws-api/market_depth.html), [pacing](https://www.interactivebrokers.com/docs/tws-api/doc/market-data-historical/historical-data-limitations/pacing-violations-for-small-bars-30-secs-or-less)).
5/15 **Observed official Longbridge capability:** Quote and trade are separate binary/protobuf WebSockets; quote subscriptions include quote/depth/trade pushes and are capped at 500 symbols, while private trade notifications use topic `private` and command `18` ([quote](https://open.longbridge.com/docs/socket/subscribe_quote), [trade](https://open.longbridge.com/docs/socket/subscribe_trade)).
6/15 **Observed official crypto capability:** Binance, Bybit, OKX, Bitget, and Hyperliquid each document public market streams and private order/account streams, but their stream protocols, limits, identifiers, and recovery semantics differ ([Binance](https://developers.binance.com/docs/binance-spot-api-docs/web-socket-streams), [Bybit](https://bybit-exchange.github.io/docs/v5/ws/connect), [OKX](https://app.okx.com/docs-v5/en/), [Bitget](https://www.bitget.com/docs/classic/rest-api), [Hyperliquid](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket)).
7/15 **Observed idempotency:** Alpaca `client_order_id`, Longbridge `client_request_id`, Binance `newClientOrderId`, Bybit `orderLinkId`, OKX `clOrdId`, Bitget `clientOid`, and Hyperliquid `cloid` are documented fields, but only Longbridge, Alpaca, and Bitget sources explicitly describe duplicate/retry behavior; other duplicate semantics remain unknown ([Longbridge](https://open.longbridge.com/docs/trade/order/submit), [Bitget](https://www.bitget.com/docs/uta/error-code/restapi)).
8/15 **Observed current adapter gap:** No inspected adapter forwards a client-order-id field; the shared protocol exposes only broker-generated `orderId` in `PlaceOrderResult` (`packages/uta-protocol/src/types/broker.ts:170-180`; repository grep for `client_order_id|clientOrderId|clientOid|orderLinkId|clOrdId|newClientOrderId|orderRef` returned no matches).
9/15 **Observed current market-data gap:** Alpaca uses REST snapshots/bars/orderbooks (`services/uta/src/domain/trading/brokers/alpaca/AlpacaBroker.ts:549-650,724-753`), IBKR uses account subscription plus one-shot `reqMktData(..., snapshot=true)` (`IbkrBroker.ts:213-218,800-838`), and CCXT uses REST ticker/OHLCV/book calls (`CcxtBroker.ts:1222-1308,1384-1404`); none of these paths opens a market WebSocket.
10/15 **Observed current order/account gap:** Current adapters poll or request order/account state; Longbridge configures SDK WS URLs but calls `TradeContext`/`QuoteContext` request methods only (`LongbridgeBroker.ts:180-207,303-368,613-655`), LeverUp uses relayer status polling and REST/RPC readers (`LeverupBroker.ts:460-514; relayer-client.ts:54-71; reader-client.ts:78-100`), and Mock is in-memory.
11/15 **Observed current history gap:** Alpaca and CCXT implement historical bars; Mock synthesizes deterministic bars; IBKR, Longbridge, and LeverUp do not implement `getHistorical` in their adapter classes (`AlpacaBroker.ts:591-650,733-753; CcxtBroker.ts:1254-1308; MockBroker.ts:492-512; broker.ts:590-597`).
12/15 **Observed resume facts:** The cited venue documents describe reconnect/resubscribe or snapshot/delta/reset behavior, but no venue cited here provides a universal durable replay cursor for all requested streams; where the docs do not explicitly promise replay, this report marks resume as no or unknown rather than inferring it.
13/15 **Observed rate-limit facts:** Limits are product/account/mode-specific: Alpaca market-data plans, IBKR message/line/pacing limits, Longbridge API/subscription limits, and exchange-specific REST/WebSocket limits are recorded below with source quotes.
14/15 **Strict separation:** “Current adapter” cells describe only executable code in this checkout; “official capability” cells describe venue documentation and are not claims about what UTA currently consumes.
15/15 **Unknowns:** Direct URL reads were attempted but disabled by the tool settings; official evidence below is therefore quoted from `web_search` extracts with their primary-source URLs, and unresolved retention, duplicate, replay, SDK, and LeverUp limits are listed explicitly at the end.

## Scope and evidence convention

This is a read-only source investigation. It covers the venue APIs named in the task, with each CCXT preset treated as its own venue because the venue-native streams, order identifiers, limits, and recovery rules are not interchangeable. `**Observed official**` means the cited primary documentation explicitly names the field, endpoint, stream, or limit. `**Observed code**` means the cited path and line range shows the current adapter call. `**Unknown**` means the inspected official material or repository does not establish the requested fact; it is not an inference from a similar endpoint. Superseded design documents are not used as venue evidence.

The official web pages were located with `web_search`; `read` of those URLs returned `URL reads are disabled by settings`. No formatter, linter, build, test, authenticated experiment, or rate-limit probe was run.

## Final cross-venue matrix

`Streams` means at least one documented real-time market or account/order stream for the venue/product, not that the current adapter consumes it. `Idempotency key` is **yes only where a caller field is documented as a usable client-order identity**; it does not silently upgrade a merely unique reference (`orderRef`) or a field with unknown duplicate semantics into a proven deduplication guarantee. `Read by key` means an official endpoint accepts that client key, not merely the venue-generated order ID. `Resume cursor` means an explicitly documented durable replay/resume cursor; snapshot/update IDs alone do not count.

## Unknowns / could not verify

- Direct `read` calls for official URLs were blocked by the environment setting (`URL reads are disabled by settings`); the report preserves primary URLs and quotes returned by `web_search`, but a future investigator should re-open each source directly before implementation.
- Alpaca’s cited pages do not establish the exact crypto symbol/order-book subscription count, Trading API numeric order rate limit, client-order-id retention window, or a replay cursor.
- IBKR `orderRef` duplicate behavior/retention and any query-by-`orderRef` operation are not documented in the cited TWS API pages; `permId`/`orderId` retrieval is not equivalent to client-key lookup. Account-specific market-data-line allocation may exceed the default values.
- Longbridge’s `client_request_id` uniqueness scope after the documented 10-minute cache and exact post-expiry duplicate behavior are not stated; quote/trade push sequence fields and replay cursors are not documented in the cited pages.
- Binance’s cited Spot docs establish open-order uniqueness for `newClientOrderId` but not a permanent retention window or exact duplicate error behavior; derivatives-product differences were not exhaustively compared with the repo’s CCXT configuration.
- Bybit’s cited docs establish a unique `orderLinkId` requirement and read filters but not retention or the exact duplicate response; product/category differences can change endpoint limits and stream topics.
- OKX’s cited guide establishes pending-order uniqueness, terminal reuse, and latest-match behavior for historical duplicates, but the exact duplicate error payload and all regional API-domain differences remain unverified.
- Bitget has separate Classic and UTA v3 contracts. This report uses Classic because the preset says Classic; UTA v3 fields/limits are not current-adapter facts. Exact Classic stream sequence/replay semantics and clientOid retention are not established.
- Hyperliquid’s cited docs establish `cloid` format and lookup but do not guarantee duplicate-cloid idempotency or retention. The `userFills` initial snapshot is not a durable replay cursor.
- LeverUp’s official pages located here do not document native trades/quotes/bars/book streams, order/account streams, client-key deduplication, historical bars, or relayer/reader rate limits. Pyth Hermes is a separate oracle service; its current authentication requirement and the repo’s unauthenticated call should be checked before relying on it.
- Mock has no venue semantics by design; its synthetic history/quotes and generated IDs must not be used as evidence for a real venue protocol.
- No runtime or authenticated venue experiment was run, by assignment constraint; this report therefore does not claim that a documented endpoint is enabled for a particular account, region, subscription tier, or sandbox mode.

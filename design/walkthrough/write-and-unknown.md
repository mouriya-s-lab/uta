# 写与结果不明走查（Q1–Q10）

## 走查范围与判定方法

本文件只依据 `../uta-design.md`，按 §5（`uta-design.md:325-327`）推演 Q1–Q10。没有读取契约或旧设计，也不以它们补充本文空白。

每条走查都按同一顺序记录：前置 → 刺激 → 步骤（模块、主文档行号与关键短语、追加的帐票）→ 客户端可观察结果 → 禁止的动作 → 结论。`调用许可`是安全边界，不等于 broker 已经被调用：许可落盘后即进入结果不明边界；许可未落盘且没有确认时，按 R1 可证明未递。结论只有在整条路径能由主文档闭合时才写“通过”；需要选择未定义的优先级、时序、帐票类型或恢复动作时写“卡点”。

## T01 — Q1 正常下单：受理、部分成交、成交

- **前置**：客户端已通过会话与权限检查；账户可交易；指令的批准前置条件已满足。流订阅者已订阅该账户的交易帐票。
- **刺激**：客户端在账户 X 提交一笔委托。
- **步骤**：
  1. **客户端端 → 会话与权限 → 指令与帐票**。依据 `uta-design.md:41`“核心校验权限与参数、保留指令”、`:60-61`“读写权限在核心判定”，核心接收委托并校验账户范围与参数。追加帐票：`指令（委托）`；其引用规则见 `:176`。
  2. **指令与帐票 → 存储**。依据 `uta-design.md:178`“递送进度（已交集成 / 调用许可 / 结果不明 / 未递）”和 `:202`“指令与‘已交集成’在集成收到之前落盘”，把指令交给对应集成并落盘已交集成进度。追加帐票：`递送进度（已交集成）`，引用该指令。
  3. **集成端 → 指令与帐票 → 存储**。依据 `uta-design.md:202`“向核心请求调用许可；核心落盘许可……后回确认”，核心将指令 id、尝试号、账户、集成会话、请求摘要绑定到调用许可并写入确认。追加帐票：`递送进度（调用许可）`。
  4. **集成端**。依据 `uta-design.md:202`“收到确认才调用，且同一许可只调用一次”，集成收到确认后调用 broker。追加帐票：调用动作本身不在 `:174-183` 的帐票种类中；不另造帐票。
  5. **集成端 → 指令与帐票**。依据 `uta-design.md:41`“broker 返回受理 / 成交 / 状态 → 集成转成回票”以及 `:179`“回票（受理 / 部分成交 / 成交……）”，按顺序收到受理、部分成交、成交并逐张保留。追加帐票：三张`回票`，每张保留 broker 原生订单 id 与成交字段。
  6. **指令与帐票 → 流与订阅 → 客户端端**。依据 `uta-design.md:41`“转发给订阅者”和 `:228`“账户变动流（回票……）按账户选择”，关联同一指令后分发三张回票。追加帐票：无新增帐票，分发使用已追加回票。
- **客户端可观察结果**：订阅者依次收到受理、部分成交、成交三张回票；每张有 broker 原生订单 id 与成交字段；指令视图最终为成交。依据 `uta-design.md:130`。
- **禁止的动作**：不得把三张回票压成一个结果；不得丢 broker 原生订单 id 或成交字段；不得在同一许可之外再发一张许可（`uta-design.md:202、205-206`）。
- **结论**：通过。

## T02 — Q2 变体一：确认进入 socket 缓冲但集成没有记录

- **前置**：调用许可已经落盘；确认已进入传输的 socket 缓冲，但集成端没有确认日志；核心在收到回票前被终止。该许可绑定指令 id、尝试号、账户、集成会话和请求摘要。
- **刺激**：核心重启，集成按“没有可证明的确认记录”恢复。
- **步骤**：
  1. **存储 → 指令与帐票**。依据 `uta-design.md:131`“调用许可已落盘”与 `:197`“调用许可已落盘，无回票……结果不明”，重放已有帐票。追加帐票：已有`递送进度（调用许可）`；重放本身不追加新种类。
  2. **集成端**。依据 `uta-design.md:202`“收到确认才调用”“没收到确认不调用”，集成不能仅凭 socket 缓冲中曾有数据就把没有确认记录解释为已确认。追加帐票：无；主文档没有把确认事件列为帐票。
  3. **指令与帐票**。依据 `uta-design.md:43`“许可已落盘且无确定回票 = 结果不明”和 `:251`“调用许可已落盘、无回票 → 结果不明 → 2.4，不再许可”，把指令保持为结果不明。追加帐票：状态由已有帐票函数得出；重启时是否另写一张“结果不明”进度帐票未规定，不新增假想帐票。
  4. **指令与帐票 → 集成端**。依据 `uta-design.md:212-215`“按能力声明……查询渠道”及“渠道用尽仍无结论……转人工”，进入查询或人工路径；但 socket 缓冲中的确认在核心重启后是否仍可交集成、是否作废，主文档没有规定。追加帐票：查询得到结果前无新增帐票被主文档指定。
- **客户端可观察结果**：重启后可确定看到该指令为结果不明、有调用许可记录、没有第二条许可，并进入查询路径；Q2 的 broker 调用记录上限为一。缓冲确认是否能在重连后改变集成可观察结果未定义。依据 `uta-design.md:131`。
- **禁止的动作**：不得因为集成日志缺少确认就断言“未递”；不得发放同一尝试号的新许可；不得让 SDK 或 HTTP 客户端自动重试写请求（`uta-design.md:202`）；不得自行规定缓冲确认的重放或丢弃。
- **结论**：卡点：结果不明与“不再许可”已闭合，但核心重启后 socket 缓冲确认的归属与处置未定义。

## T03 — Q2 变体二：集成拿到确认后、调用 broker 前崩溃

- **前置**：调用许可已落盘，集成已收到确认；集成尚未调用 broker 即崩溃；核心没有回票。
- **刺激**：核心重启，集成会话重新建立。
- **步骤**：
  1. **存储 → 指令与帐票**。依据 `uta-design.md:197`“调用许可已落盘，无回票……结果不明”，重放调用许可。追加帐票：已有`递送进度（调用许可）`。
  2. **指令与帐票 → 会话与权限 / 集成端**。依据 `uta-design.md:251`“调用许可已落盘、无回票 → 结果不明 → 2.4，不再许可”，旧集成会话不能使该尝试获得第二张许可。追加帐票：无新增帐票；禁止重复许可是规则，不是新帐票。
  3. **指令与帐票 → 集成端**。依据 `uta-design.md:212-216`，按已声明的查询渠道确认 broker 事实，查到才补回票，查不到且不能证明未递则转人工。追加帐票：查到时为`对账响应（回读结果）`及其补`回票`；无结论时等待`人工凭证`。
- **客户端可观察结果**：即使实际调用为零，客户端仍先看到结果不明；不能看到一个“未递”结论，除非查询渠道证明未递或人工凭证给出该结论。依据 `uta-design.md:43、214-216`。
- **禁止的动作**：不得把“已收到确认”改写成“已调用事实”；不得再发放许可；不得把自动重放当作普通重试（`uta-design.md:202、204`）。
- **结论**：通过。

## T04 — Q2 变体三：集成调用 broker 后、核心收到回票前崩溃

- **前置**：调用许可已落盘，集成收到确认并调用 broker；broker 可能已受理或尚未产生可见回票；核心在收回票前被终止。
- **刺激**：核心重启。
- **步骤**：
  1. **存储 → 指令与帐票**。依据 `uta-design.md:131`“许可后崩溃”和 `:197`，重放调用许可且发现没有确定回票。追加帐票：已有`递送进度（调用许可）`。
  2. **指令与帐票**。依据 `uta-design.md:43`“许可已落盘且无确定回票 = 结果不明”，把状态定为结果不明。追加帐票：无新增种类被主文档指定；状态由已有帐票函数得出。
  3. **指令与帐票 → 集成端**。依据 `uta-design.md:212-215`进入 client key 回读、未成交列表、成交/持仓对账或人工路径。追加帐票：查询命中时追加`对账响应（回读结果）`和补`回票`；无法证明时追加`人工凭证`（由 Human 签发）。
- **客户端可观察结果**：结果不明；调用记录最多一条；没有第二条许可；后续由查询或人工收敛。依据 `uta-design.md:131、210-216`。
- **禁止的动作**：不得按“调用可能已发生”再创建新的 broker 尝试；不得将无回票压成被拒；不得自动写请求重试（`uta-design.md:202、204、206`）。
- **结论**：通过。

## T05 — Q3：client key 回读得到结果

- **前置**：指令处于结果不明；集成能力声明明确支持 client key 回读，且该能力的可信结论已声明。
- **刺激**：核心按能力顺序请求回读，集成返回与该 client key 对应的 broker 结果。
- **步骤**：
  1. **指令与帐票 → 集成端**。依据 `uta-design.md:212`“client key 回读”，核心选择第一查询渠道，不新增调用许可。追加帐票：无新增帐票；查询动作不是新 broker 尝试。
  2. **集成端 → 指令与帐票**。依据 `uta-design.md:180`“对账响应（……回读结果）”和 `:213`“查到 → 补回票，关联到指令”，保留回读结果并生成关联回票。追加帐票：`对账响应（回读结果）`、至少一张与指令关联的`回票`；具体回票状态以查询结果为准，不在此补写。
  3. **指令与帐票 → 流与订阅 → 客户端端**。依据 `uta-design.md:41、228`，将补回票转发到账户变动流。追加帐票：无新增帐票。
- **客户端可观察结果**：看到回读结果对应的补回票，结果不明被已知 broker 结果收敛；不会看到第二条调用许可。依据 `uta-design.md:132、213`。
- **禁止的动作**：不得因为回读得到结果就创建新的 broker 尝试；不得丢 broker 原生订单 id、状态原值或成交字段（`uta-design.md:202、204、206`）。
- **结论**：通过。

## T06 — Q3：未成交列表查到结果

- **前置**：指令处于结果不明；client key 回读不可用或无结论；能力声明可信地支持按 broker 原生 id 或指令特征查询未成交列表。
- **刺激**：核心按下一渠道查询，列表返回该指令对应的未成交项。
- **步骤**：
  1. **指令与帐票 → 集成端**。依据 `uta-design.md:212`“未成交列表（按 broker 原生 id 或指令特征）”，使用已声明渠道。追加帐票：无新增帐票。
  2. **集成端 → 指令与帐票**。依据 `uta-design.md:213`“查到 → 补回票，关联到指令”，把列表结果保存为`对账响应（订单列表）`并补回票。追加帐票：`对账响应（订单列表）`、关联的`回票`。
  3. **指令与帐票 → 流与订阅**。依据 `uta-design.md:228`，把关联回票放入账户变动流并通知订阅者。追加帐票：无新增帐票。
- **客户端可观察结果**：得到关联到原指令的补回票，看到不明收敛后的状态；无第二条许可。依据 `uta-design.md:132、213`。
- **禁止的动作**：不得把未成交列表查询当成新的 broker 调用；不得因列表结果缺少某字段而自行改写为被拒（`uta-design.md:204、206`）。
- **结论**：通过。

## T07 — Q3：没有可信渠道，转人工凭证

- **前置**：指令处于结果不明；能力声明没有可信查询渠道，或所有已声明渠道用尽仍无结论。
- **刺激**：核心进入人工处理；Human 随后提交一张说明结论与依据的人工凭证。
- **步骤**：
  1. **指令与帐票 → 会话与权限**。依据 `uta-design.md:215`“转人工：告警 + 等待人工凭证”，发出告警并保持等待。追加帐票：告警的帐票种类未单列；不创造新种类。
  2. **Human → 指令与帐票 → 存储**。依据 `uta-design.md:182`“人工凭证……结论 = 已递(id, 状态) / 未递”和 `:216`“只能由 Human 身份签发，说明结论与依据”，保存带身份的人工凭证。追加帐票：`人工凭证`。
  3. **指令与帐票**。依据 `uta-design.md:199`“已递则按其给的状态继续接回票；未递则终态”，按凭证结论继续接回票或结束。追加帐票：已递分支后续收到回票时追加`回票`；未递分支不自动新建 broker 尝试。
- **客户端可观察结果**：先看到结果不明与人工等待，之后看到带 Human 身份、结论和依据的人工凭证；凭证为已递时继续接收回票，为未递时看到未递终态。依据 `uta-design.md:132、182、199、215-216`。
- **禁止的动作**：不得由集成或 Client 签发人工凭证；不得在人工凭证前自行决定已递或未递；不得自动新建 broker 尝试（`uta-design.md:204、216`）。
- **结论**：通过。

## T08 — Q4：请求许可但核心未落盘时崩溃

- **前置**：指令已保留并已交集成；集成请求调用许可；核心在许可落盘前被终止，集成没有收到确认。
- **刺激**：核心重启，旧集成会话失效。
- **步骤**：
  1. **集成端 → 指令与帐票**。依据 `uta-design.md:202`“集成……向核心请求调用许可”，接收请求但尚未形成许可。追加帐票：没有`递送进度（调用许可）`；本步未越过落盘边界。
  2. **集成端**。依据 `uta-design.md:202`“没收到确认不调用”，不调用 broker。追加帐票：无。
  3. **存储 → 指令与帐票**。依据 `uta-design.md:133`“核心未落盘”“无许可记录”和 `:251`“已交集成无调用许可 → 未递”，重放后判定可证明未递。追加帐票：`递送进度（未递）`；若按 `:196` 回到待递，状态由已有帐票函数计算。
  4. **指令与帐票**。依据 `uta-design.md:196`“可证明未递 → 回待递，重新派发同一指令”和 `:133`“回到待递或按策略过期”，按现有策略选择待递或过期。追加帐票：过期分支追加`决定（过期）`；待递分支不新建指令。
- **客户端可观察结果**：broker 调用记录为零、无调用许可记录；指令不是结果不明，回到待递或按策略过期。依据 `uta-design.md:133`。
- **禁止的动作**：不得把许可未落盘解释成结果不明；不得调用 broker；不得创建第二条指令或自动换成新的 broker 尝试。重派只能是同一指令的 R1/R2 路径。
- **结论**：通过。

## T09 — Q5：部分成交到成交的保真路径

- **前置**：一笔已批准委托已有调用许可；集成获得受理、部分成交与成交结果。
- **刺激**：fixture broker 依次返回 `partially_filled(3/10)` 与 `filled`。
- **步骤**：
  1. **集成端 → 指令与帐票**。依据 `uta-design.md:134`“partially_filled(3/10) → filled”和 `:179`“回票（……部分成交 / 成交）”，按返回顺序保存两类回票；若另有受理回票也按同一规则保存。追加帐票：对应`回票`，保留 broker 原生订单 id、状态原值、成交字段、原始负载摘要。
  2. **指令与帐票**。依据 `uta-design.md:205`“同一指令的回票按 broker 状态偏序折叠”，把成交状态单调折叠，不让迟到旧状态覆盖。追加帐票：无新增帐票，折叠是状态函数。
  3. **流与订阅 → 客户端端**。依据 `uta-design.md:130`“订阅者收到三张回票”和 `:41`“转发给订阅者”，发送受理、部分成交、成交三张回票。追加帐票：无新增帐票。
- **客户端可观察结果**：三张回票均可见；指令视图成交量等于回票累计，最终为成交。依据 `uta-design.md:130、134、205-206`。
- **禁止的动作**：不得把部分成交直接改写成成交；不得把异常改写成被拒；不得丢成交字段或 broker 原生订单 id。
- **结论**：通过。

## T10 — Q5：broker 专有状态保留为非终态

- **前置**：指令已有调用许可；broker 返回一项主文档未列为通用状态、但集成能力声明的映射表中有专有状态。
- **刺激**：集成提交专有状态回票。
- **步骤**：
  1. **集成端 → 指令与帐票**。依据 `uta-design.md:134`“专有状态映射为非终态并保留原值”和 `:206`“映射表按 broker 版本化”，保存状态原值及原始负载摘要。追加帐票：`回票（专有状态）`。
  2. **指令与帐票**。依据 `uta-design.md:198`“回票……按 broker 状态单调折叠”，将专有状态作为非终态保留，不提前结束指令。追加帐票：无新增帐票。
  3. **流与订阅 → 客户端端**。依据 `uta-design.md:41、179`，向账户变动流转发该回票。追加帐票：无新增帐票。
- **客户端可观察结果**：看到专有状态原值，能区分其非终态；不会被静默改写成被拒。依据 `uta-design.md:134、206`。
- **禁止的动作**：不得删去原始状态；不得将专有状态折叠为被拒或其他未声明状态；不得凭状态名称补造映射。
- **结论**：通过。

## T11 — Q5：表外状态标不明并告警

- **前置**：broker 返回状态不在集成版本化映射表中。
- **刺激**：集成收到并转发该状态。
- **步骤**：

- **步骤**：
  1. **集成端 / 指令与帐票**。依据 `uta-design.md:202`“收到确认才调用”，若回票声称来自当前尝试，则在当前尝试尚未获确认时没有合法的调用前置，场景前提与 R1 的因果顺序冲突。追加帐票：不能据此追加当前指令的`回票`，因为归属尚未确定。
  2. **指令与帐票**。依据 `uta-design.md:41、179`，只有能用 broker 原生订单 id 或 client key 关联时才可把回票关联到指令；依据 `:220`，无匹配时应追加`外部变动`。追加帐票：若确实无匹配，追加`外部变动`；若匹配到当前未获确认指令，正文没有说明应关联还是仍作外部变动。
  3. **流与订阅**。依据 `uta-design.md:228`，已确定为外部变动时才能按账户变动流转发；确认与回票跨路径的先后处理、缓存或重排未定义。追加帐票：取决于上一步的未定义裁决，不能虚构。
- **客户端可观察结果**：当前尝试的回票归属与客户端先后次序无法由主文档确定；至多能在无匹配时观察到外部变动。依据 `uta-design.md:41、179、202、220`。
- **禁止的动作**：不得把回票先到解释为集成已在确认前调用；不得自行设计缓存、重排或补确认；不得在无法关联时归因到当前指令。
- **结论**：卡点：同一尝试的回票接收方、确认接收方、归属证明与跨路径先后处理未定义，且当前尝试的因果前提可能违反 R1。

## T24 — 额外 (c)：人工凭证说已递，后来 broker 回票状态不同

- **前置**：指令处于结果不明；Human 提交人工凭证，结论为“已递(id, 状态 A)”；随后集成提交同一 broker 原生 id 的回票，状态为 B，且 A 与 B 不同。
- **刺激**：人工凭证先落盘，后来的 broker 回票再到达核心。
- **步骤**：
  1. **Human → 指令与帐票 → 存储**。依据 `uta-design.md:182、216`，验证 Human 身份、保存结论与依据。追加帐票：`人工凭证`，结论为已递(id, 状态 A)。
  2. **指令与帐票**。依据 `uta-design.md:199`“已递则按其给的状态继续接回票”，继续接收后续回票。追加帐票：此步骤不改写人工凭证。
  3. **集成端 → 指令与帐票**。依据 `uta-design.md:179`，以 broker 原生 id 关联回票 B。追加帐票：`回票`，保留状态 B、原始负载摘要及 broker 原生 id。
  4. **指令与帐票**。依据 `uta-design.md:205`“同一指令的回票按 broker 状态偏序折叠”，只能确定回票之间的单调折叠；该行没有规定人工凭证与回票状态 A/B 的跨种类优先级。追加帐票：无新增帐票；人工凭证不可变。
- **客户端可观察结果**：客户端能看到人工凭证和后来回票，但最终应显示 A、B 哪一个，或如何同时表达二者，主文档未定义。
- **禁止的动作**：不得覆盖或删除人工凭证；不得无依据让人工结论覆盖回票，也不得让回票覆盖人工结论；不得把两者静默合成一个状态。
- **结论**：卡点：人工凭证与后来回票的冲突裁决、客户端最终状态和是否继续查询均未定义。

## T25 — 额外 (d)：改单目标指令处于结果不明

- **前置**：目标指令已存在，手里有调用许可但没有确定回票，状态为结果不明；客户端提交一条改单指令，引用该目标指令。
- **刺激**：核心收到改单请求。
- **步骤**：
  1. **客户端端 → 指令与帐票**。依据 `uta-design.md:176`“改单 / 撤单引用目标指令或 broker 原生 id”，确认引用对象存在并保留改单指令。追加帐票：新的`指令（改单）`；目标指令已有帐票不可变。
  2. **会话与权限 → 指令与帐票**。依据 `uta-design.md:41`“核心校验权限与参数、保留指令”，执行一般权限和参数校验。追加帐票：决定是否能创建改单指令、以及校验失败时的拒绝记录，主文档未给出额外类型。
  3. **指令与帐票**。依据 `uta-design.md:204`“结果不明期间不创建新的 broker 尝试”，可确定不能把目标指令直接改成新的 broker 尝试；但正文没有规定改单是等待目标收敛、立即拒绝、还是保留为待决定。追加帐票：上述三种分支的追加帐票均未定义，不能擅自选择。
- **客户端可观察结果**：只能确定目标指令仍为结果不明且不得自动发放新的调用许可；改单指令的最终结果、等待方式和客户端返回未定义。
- **禁止的动作**：不得把改单当成目标指令的状态覆盖；不得在目标不明期间自动取得新的调用许可；不得擅自选择等待、拒绝或改用 broker 原生 id 的规则。
- **结论**：卡点：结果不明目标能否承接改单、改单指令的决定与递送前置、以及客户端结果均未定义。

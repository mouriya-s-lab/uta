# Q11–Q21：流、读、恢复与会话走查

## 范围与方法

本文只依据 `uta-design.md` 的 §1.4、§2.6–§2.10、§3.3 推演。每条 trace 使用同一格式：覆盖项、依据、刺激、步骤、预期、可观察证据、结论。`结论` 只取“已定义”或“卡点”；主文档没有给出的行为不补写。

## Traces

### Trace 01：Q11 初次订阅建立流

- **覆盖项**：Q11
- **依据**：`uta-design.md:140`、`uta-design.md:224-228`
- **刺激**：客户端以已认证身份订阅 200 个 instrument 的 tick；集成已声明支持该流种类。
- **步骤**：核心按选择器建立订阅；集成产生行情记录；核心按来源内顺序编号并转发。
- **预期**：订阅记录包含客户端身份、选择器和每流游标；每条行情记录带同一代数内连续的 `seq`；行情流按 instrument 选择，账户变动流不混入。
- **可观察证据**：客户端收到该选择器对应的行情记录；订阅表有每流游标；记录可按 `(Generation, seq)` 重建顺序。
- **结论**：已定义。

### Trace 02：Q11 断线且无续传游标

- **覆盖项**：Q11
- **依据**：`uta-design.md:140`、`uta-design.md:224`
- **刺激**：行情流已发送到前一代的最后 `seq`；集成断线 30 秒后重连，broker 没有可信续传游标。
- **步骤**：集成在重连时报告不能续接；核心结束前一代，创建新代数；新代数首条记录是来源缺口。
- **预期**：来源缺口包含前一代数、前一代最后 `seq` 和原因；断线前后的记录各自在自己的代数内连续；核心不静默跳过缺失区间。
- **可观察证据**：订阅者先收到缺口，再收到新代数记录；缺口字段能指出前一段最后 `seq` 与断线原因；不存在跨代数伪造的连续序号。
- **结论**：已定义。

### Trace 03：Q11 重连有可信续传游标

- **覆盖项**：Q11
- **依据**：`uta-design.md:224`
- **刺激**：行情流断线；集成重连时报告 broker 给出可信续传游标。
- **步骤**：核心校验集成的续接声明；集成从可信游标继续送行情记录。
- **预期**：流继续使用原代数；不因可证明的连续性而新建来源缺口。
- **可观察证据**：后续记录的 `Generation` 不变，`seq` 在前一记录之后继续；订阅者没有收到无理由的来源缺口。
- **结论**：已定义。

### Trace 04：Q12 一个慢消费者填满缓冲

- **覆盖项**：Q12
- **依据**：`uta-design.md:141`、`uta-design.md:226`
- **刺激**：三个订阅者消费同一行情流，其中一个不 ack，直到该订阅者的缓冲满。
- **步骤**：核心记录该订阅者尚未确认的范围；生成投递缺口；停止向该订阅者投递该流，等待其确认缺口。
- **预期**：慢订阅者收到投递缺口，缺口包含 `from` / `to seq`；停投只作用于该订阅者的该流；不能把它写成来源缺口。
- **可观察证据**：慢订阅者收到缺口记录并看到该流停投；订阅表保存待确认缺口；其它订阅者仍收到各自的行情记录。
- **结论**：已定义。

### Trace 05：Q12 快消费者不受慢消费者影响

- **覆盖项**：Q12
- **依据**：`uta-design.md:141`、`uta-design.md:226`
- **刺激**：两个订阅者持续 ack，第三个订阅者不 ack 并触发投递缺口。
- **步骤**：核心为第三个订阅者停投；继续按流内顺序向两个快订阅者投递。
- **预期**：慢订阅者的缺口和停投不改变两个快订阅者的顺序与可见延迟；跨订阅者不互相阻塞。
- **可观察证据**：两个快订阅者的 `(流, seq)` 记录持续递增；只有第三个订阅者的订阅记录有待确认缺口。
- **结论**：已定义。

### Trace 06：Q12 缺口确认前后

- **覆盖项**：Q12
- **依据**：`uta-design.md:226`
- **刺激**：慢订阅者已经收到投递缺口，但尚未 ack。
- **步骤**：先观察未 ack 期间，再提交该缺口的 ack。
- **预期**：未 ack 前该流继续停投；只有确认缺口后才满足继续投递的前置条件。
- **可观察证据**：未 ack 阶段没有该流的新投递；ack 记录引用同一缺口的 `from` / `to seq`。
- **结论**：已定义停投条件；ack 后的具体首条 `seq`、重送范围和缓冲清理形状未定义，列入卡点表。

### Trace 07：Q13 订阅在配额内

- **覆盖项**：Q13

### Trace 08：Q13 第二次订阅超出配额

- **覆盖项**：Q13
- **依据**：`uta-design.md:142`、`uta-design.md:225`、`uta-design.md:238`
- **刺激**：broker 限制 500 个 symbol；已有订阅占用部分配额，第二个订阅会使总数超过声明值。
- **步骤**：核心在接纳阶段计算该请求是否符合能力声明；发现超限后拒绝整个订阅，不向集成提交超限请求。
- **预期**：客户端收到说明配额的 typed 拒绝；已有订阅不受影响；核心不把超限请求变成部分接纳。
- **可观察证据**：拒绝结果可枚举且带配额信息；集成没有收到超限订阅；已有订阅的游标和记录继续推进。
- **结论**：已定义。

### Trace 09：Q14 正常回填转实时

- **覆盖项**：Q14
- **依据**：`uta-design.md:143`、`uta-design.md:225`
- **刺激**：客户端订阅带 500 根历史 bar 的回填；能力声明给出历史 bar 支持与 pacing。
- **步骤**：集成按 pacing 分页拉取；核心把回填记录与实时记录送入同一流；完成回填后切换就绪状态。
- **预期**：回填阶段状态为 `backfilling`，之后转为 `live` 且只发生一次；同一流内保持顺序。
- **可观察证据**：客户端看到一次 `backfilling → live`；流记录可按同一 `(Generation, seq)` 观察；分页请求间隔符合已声明 pacing。
- **结论**：已定义。

### Trace 10：Q14 回填与实时边界去重

- **覆盖项**：Q14
- **依据**：`uta-design.md:143`
- **刺激**：回填末页与实时入口包含同一根 bar 的边界记录。
- **步骤**：核心接收回填与实时记录，按同一流处理边界；对边界重复记录去重。

- **结论**：已定义去重结果；重复判定使用的字段和冲突记录形状未定义，若两条边界记录内容不完全相同则列入卡点表。

### Trace 11：Q14 回填中断线

- **覆盖项**：Q14
- **依据**：`uta-design.md:143`、`uta-design.md:224`
- **刺激**：回填尚未结束时集成断线；broker 无可信续传游标。
- **步骤**：核心记录连续性断裂并开启新代数；重连后从头回填；按 pacing 重新请求页面。

- **可观察证据**：订阅者收到新代数及来源缺口；回填首段重新出现；后续就绪通知只有一次；同代数无重复 bar。
- **结论**：已定义。

### Trace 12：额外场景 b——回填中退订再订阅

### Trace 13：Q15 fan-out 的部分失败

- **覆盖项**：Q15
- **依据**：`uta-design.md:144`、`uta-design.md:231`
- **刺激**：无 source 的持仓读解析为三个账户；其中一个 broker 不可用。
- **步骤**：核心按账户用途与身份检查权限；分别向三个集成发送带 deadline 的读；汇总各账户响应。
- **预期**：两个可用账户返回持仓；不可用账户返回 typed `不可用`；三个账户结果相互独立，不合并、不重排；持仓响应作为对账响应留票并进入账户变动流。
- **可观察证据**：客户端收到三个可区分账户结果；不可用结果有 typed 类型；两份成功持仓各带来源与数据时刻；账户变动流有成功持仓对账响应。
- **结论**：已定义。

### Trace 14：Q15 一次性持仓读的正常留票

- **覆盖项**：Q15
- **依据**：`uta-design.md:231`
- **刺激**：客户端对指定账户发起一次性持仓读，集成按能力声明返回持仓响应。
- **步骤**：核心把响应返回客户端，同时将持仓响应作为对账响应帐票写入账户变动流。
- **预期**：客户端收到一次性读结果；该结果与对账响应帐票都保留来源和数据时刻；报价、盘口、搜索、时钟、历史 bar 等其它读不因本规则留票。
- **可观察证据**：客户端得到带来源和数据时刻的持仓结果；账户变动订阅者收到对应对账响应；其它读没有新增帐票。
- **结论**：已定义。

### Trace 15：额外场景 a——持仓响应发现无指令对应的变化

- **覆盖项**：额外场景 a；Q15
- **依据**：`uta-design.md:220`、`uta-design.md:231`
- **刺激**：一次性持仓读返回一项持仓变化，broker 原生 id 与 client key 都无法对应任何本地指令。
- **步骤**：核心先按一次性读规则返回并留存持仓对账响应；指令与帐票模块尝试关联；确认无匹配后记录外部变动。
- **预期**：产生外部变动帐票；该帐票无指令引用并转发给账户变动订阅者；不改变任何指令状态。若存在结果不明且 broker 原生 id 未知，只能标注“存在未定指令”，不能归因；后续不回改已经追加的帐票。
- **可观察证据**：同一读请求有对账响应；另有外部变动帐票且没有指令引用；相关指令状态不变；订阅者收到外部变动。
- **结论**：已定义。

### Trace 19：Q18 策略热变更

- **覆盖项**：Q18

- **刺激**：已有核心持有同一数据目录锁；第二个核心尝试启动并打开同一目录。
- **步骤**：第二个核心检查文件锁与接管 fence；发现持有者仍有效后拒绝启动。
- **预期**：第二个核心退出并说明持有者；单写者不被破坏；已有核心继续持有目录。
- **可观察证据**：第二个核心有拒绝退出码和诊断；目录没有第二写者的记录；原持有者的记录和订阅继续可读。
- **结论**：已定义。

### Trace 25：Q20 持有者死亡后的接管

- **覆盖项**：Q20
- **依据**：`uta-design.md:149`、`uta-design.md:250`
- **刺激**：原核心已死亡，第二个核心再次尝试使用同一数据目录。
- **步骤**：第二个核心确认原持有者失效，取得文件锁与接管 fence，再打开目录。
- **预期**：第二个核心可以接管；不会与仍存活的写者同时写入；重启恢复规则随后适用。
- **可观察证据**：接管核心成功启动并持有目录；新写入只有一个写者；订阅、游标和帐票可重放。
- **结论**：已定义接管结果；原持有者死亡与 fence 判定的精确时序未定义，若两者并发需另行裁决，见卡点表 C5。

### Trace 26：Q21 新版本读取旧目录

- **覆盖项**：Q21
- **依据**：`uta-design.md:150`、`uta-design.md:252`
- **刺激**：N+1 版核心读取 N 版数据目录。
- **步骤**：核心识别目录版本；执行低版本到高版本迁移，写迁移日志并用副本替换。
- **预期**：迁移后数据语义等价；替换完成后新版本可以继续启动；迁移过程有可重放记录。
- **可观察证据**：启动结果成功；订阅、游标、帐票、能力声明和策略重放后等价；迁移日志存在。
- **结论**：已定义。

### Trace 27：Q21 旧版本读取新目录

- **覆盖项**：Q21
- **依据**：`uta-design.md:150`、`uta-design.md:252`
- **刺激**：N 版核心读取高于其支持范围的 N+1 版目录。
- **步骤**：核心在启动前比较存储版本；发现版本过高后停止。
- **预期**：拒绝启动并说明目录版本；不写入、不降级改写目录。
- **可观察证据**：进程有拒绝退出码和诊断；目录内容与启动前一致；没有新增帐票、订阅或迁移记录。
- **结论**：已定义。

### Trace 28：Q21 迁移中途断电

- **覆盖项**：Q21
- **依据**：`uta-design.md:150`、`uta-design.md:252`
- **刺激**：低版本到高版本的迁移在日志写入或副本替换期间断电。
- **步骤**：恢复供电并重新启动；检查目录版本、记录边界和副本。
- **预期**：目录要么是旧版完整，要么是新版完整；不能出现第三种混合版本；启动结果和诊断能说明当前完整版本。
- **可观察证据**：目录可被一个受支持版本完整读取；帐票、订阅表和游标没有半写结构；不存在同时可见的混合字段。
- **结论**：已定义。

### Trace 29：额外场景 c——能力声明缩减后的已有订阅

- **覆盖项**：额外场景 c；Q13/Q14
- **依据**：`uta-design.md:241`、`uta-design.md:238`、`uta-design.md:249`
- **刺激**：已有订阅正在使用某项流能力；集成重新声明，移除该流支持或降低其能力。
- **步骤**：核心校验新的能力声明；识别受影响订阅；追加能力声明记录并处理订阅。
- **预期**：受影响订阅挂起并通知；核心不继续假设已被移除的能力；不受影响订阅继续按原流规则处理。
- **可观察证据**：受影响订阅可见挂起结果和通知；能力声明的新版本可重放；其它订阅没有被连带挂起。
- **结论**：已定义挂起与通知；通知载荷、对外状态字段、游标是否推进、恢复条件和再次声明扩大能力后的重新接续形状未定义，见卡点表 C2。

### Trace 30：额外场景 d——核心重启时集成持有旧会话待发项

- **覆盖项**：额外场景 d；Q4/Q17
- **依据**：`uta-design.md:133`、`uta-design.md:202`、`uta-design.md:251`
- **刺激**：指令已有“已交集成”进度，但没有“调用许可”记录；核心重启时集成进程仍存活，并持有旧会话中的待发项。
- **步骤**：核心重启使旧会话作废；集成丢弃旧会话待发项；核心重放该指令并按 R1 判断。
- **预期**：旧会话待发项不会调用 broker；该指令按可证明未递处理，回到待递或按策略过期；旧会话不能凭待发项继续执行。若恢复后重新派发同一指令，仍须经过新的调用许可流程。
- **可观察证据**：旧待发项对应的 broker 调用记录为 0；没有“调用许可”递送进度；核心重启后指令可观察为待递或按策略过期；旧会话不能提交新的帐票。
- **结论**：核心安全结果已定义；集成丢弃动作是否追加专门帐票、客户端是否收到独立通知及其字段未定义，见卡点表 C3。

### Trace 31：额外场景 e——同一 broker 两账户共享公共行情 feed

- **覆盖项**：额外场景 e；Q13
- **依据**：`uta-design.md:170`、`uta-design.md:238`、`uta-design.md:285`
- **刺激**：同一 broker 的账户 A 与账户 B 各有客户端订阅公共行情；结构上公共行情 feed 每 broker 一个，而账户集成的配额按账户声明。
- **步骤**：分别以两个客户端身份提交公共行情选择器；比较公共 feed 的能力声明、订阅接纳和配额使用。
- **预期**：公共行情的来源是 `PublicFeed(broker)`；订阅仍按客户端身份和选择器保存；超限时明确拒绝，未超限订阅不受影响。
- **可观察证据**：两账户订阅都能标识来源与客户端身份；公共行情记录按同一来源内的 `(Generation, seq)` 观察；超限请求不会被静默接纳。
- **结论**：已定义来源、流内顺序和超限拒绝；共享公共 feed 时配额按账户、按公共 feed、按会话还是按其它边界归属，主文档没有说明，见卡点表 C6。

# 脑裂走查：五条 trace

材料边界：本走查只使用 `uta-design.md` 与 `contracts/01-operations.md`。A、B 表示集成传输会话标签；“尝试号”是递送进度中的尝试号，不把它扩展为新的身份。每一步都只记录文档已经定义的帐票；会话、能力、锁与接管 fence 若不是帐票，则明确写“无”。

## Trace 1：Q2 ③，旧集成 A 晚读合法确认并带 client key 回票

**前置**：指令已经保留并批准，已有 A-02 的“已交集成”进度和 A-03 的调用许可；该调用许可绑定 A 的集成会话号、指令、尝试号、账户和请求摘要。核心在收回票前崩溃，A 仍存活且保留传输缓冲；核心重启后接受新的集成会话 B。这里假定 A 的回票具备可靠 client key 以及 A-04 要求的回票去重键。

**刺激**：B 建立后，A 才从自己的缓冲读到已经落盘且绑定 A 会话的合法许可确认，随后调用 broker；该调用产生带 client key 的回票并试图送回核心。

**每步**：

1. `uta-design.md:131`，“Q2 ③：核心重启建立新会话 B……A 才从缓冲读到……合法确认并调用 broker”与 `uta-design.md:254-256`，“调用许可已落盘、无回票 → 结果不明”。追加帐票：无新增；重放已有帐票后，指令按已有调用许可判为结果不明。
2. `contracts/01-operations.md:34-63`（A-01），“能力已接受”后才允许后续操作；`uta-design.md:240-246`，“会话重建……有许可的进入结果不明”。追加帐票：无；B 的能力声明和会话接纳是版本化记录，不是本步新增的交易帐票。
3. `uta-design.md:213`（R12），“核心不能保证一个仍存活的旧集成实例不会晚读到自己会话的合法确认并调用 broker”。追加帐票：无；调用 broker 本身不产生核心帐票。
4. `contracts/01-operations.md:95-123`（A-03，契约待按 R12 同步）应表达“当前实例丢弃非本会话确认；核心不承诺仍存活的旧集成实例不会晚调用”。追加帐票：无；这是确认接收条件的同步，不改变 R12 对旧实例晚调用的模型结论。
5. `uta-design.md:212-213`，“回票携带 client key 或已知 broker 原生 id → 直接关联”；`contracts/01-operations.md:125-153`（A-04）规定集成向核心提交回票并返回“回票已关联”。追加帐票：若 A-04 进入核心，则为一张关联到同一指令、同一尝试号的回票；它不是 B 的新尝试。
6. A-04 的前置仍是“集成会话已接受”（`contracts/01-operations.md:129-132`）。R12 没有说明核心重启后 A 的旧连接是否仍被接受，也没有说明旧连接不能提交时回票如何转到 B。追加帐票：未定义；不得擅自记成外部变动或关联回票，此传输归属缺口列入 SB-01。

**客户端可观察**：按 R12 且 A-04 回票确实到达核心时，B-11 应能看到同一指令的一条调用许可和一张关联回票，状态由回票决定；客户端不会看到第二张许可。若旧 A 连接不能提交且没有文档定义的接收路径，客户端只能继续看到结果不明，无法从现有契约判断回票是否已经发生。A-03 的契约同步不构成第二条模型路径。

**禁止动作**：B 不得为该指令发第二张调用许可，不得创建新的 broker 尝试，不得因客户端重连或核心重启而再次调用 broker；核心不得把旧会话的回票接收路径默认为 B，也不得在未定义接收路径时静默丢弃或擅自改记为外部变动。

**结论**：R12（`uta-design.md:213`）是本 trace 的模型依据：旧 A 可能晚调用，回票按 R11 关联到同一尝试；A-03 的旧措辞仅是待同步的契约文本，不列为模型矛盾。仍未定义的是旧 A 连接无法提交时的回票接收路径，见卡点 SB-01；同一许可不再许可且不产生第二次 broker 调用有明文依据。

## Trace 2：只有未知 broker 原生 id 的回票、外部变动与对账收敛

**前置**：核心已经重启并接受 B；该指令已有绑定 A 会话的调用许可、没有确定回票，因此处于结果不明。A 确实完成一次 broker 调用，但回票没有 client key，只有核心此前未见过的 broker 原生 id。以下先假定回票带有 broker 事件 id 或四元指纹；没有这两者时适用 A-04 的拒绝分支。

**刺激**：A 提交只有未知 broker 原生 id 的回票；核心尝试把它与结果不明指令关联。

**每步**：

1. `uta-design.md:197-204`（R3），“调用许可已落盘、无回票……结果不明；不明不重发”。追加帐票：无新增；已有许可仍是结果不明边界。
2. `contracts/01-operations.md:125-153`（A-04），“按 broker 原生 id 或可靠 client key 关联；找不到指令 → 外部变动；缺少事件 id 与四元指纹 → 拒绝”。追加帐票：在去重键齐全时为一张外部变动帐票；若去重键缺失则无帐票并返回 typed 拒绝。
3. `uta-design.md:223-225`，“结果不明且 broker 原生 id 未知……仍记外部变动并标‘存在未定指令’”；`contracts/01-operations.md:180-203`（A-06）同样要求“不把变动归因给它”。追加帐票：外部变动帐票带“存在未定指令”标记，不引用该指令，也不改变指令状态。
4. `contracts/01-operations.md:254-280`（A-09），“许可已落盘无确定回票才查询；client key 回读 → 未成交列表 → 成交/持仓对账；不明不发新的调用许可”。追加帐票：查询要求本身无新增帐票；若查询返回持仓、订单列表或账户响应，按 A-05 追加对账响应。
5. A-09 返回“查到回票”时，`contracts/01-operations.md:268-278` 要求核心补回票；配合 A-04 的关联规则，追加帐票：一张新的、关联到该指令的回票（若同时提交可留票的持仓、订单列表或账户响应，另有对账响应帐票）。该回票是新的追加记录，不回写第 3 步的外部变动帐票。
6. A-09 返回可信的“证明未递”时，`contracts/01-operations.md:268-274` 要求核心追加未递记录且不自动重下。追加帐票：一条“未递”递送进度；指令进入文档定义的未递终态。
7. 查询渠道用尽仍无结论时，`uta-design.md:217-221` 要求转人工并等待凭证；`contracts/01-operations.md:569-591`（B-10）规定人工凭证的两种结论。追加帐票：等待期间无新的确定回票；Human 提交后追加一张人工凭证，并按其结论继续或终止。
8. `uta-design.md:225` 与 `contracts/01-operations.md:201` 都规定外部变动不可变、收敛后不回改。若后续回读带回同一 broker 事件的原有事件 id 或同一四元指纹，`uta-design.md:205-206,288-289` 与 A-04 的去重规则又会把它识别为重复；文档没有说明如何同时保留旧外部变动并新增关联回票。追加帐票：该交互未定义。

**客户端可观察**：先能在 B-12 看到带“存在未定指令”的外部变动，在 B-11 看到原指令仍为结果不明。若可信查询补回票，客户端应看到后来追加的关联回票，同时旧外部变动仍在；若证明未递，看到未递结论；若仍无结论，看到结果不明和人工凭证路径。旧外部变动不能被改写成指令回票。至于同一事件键能否产生后来那张关联回票，当前文档没有唯一答案。

**禁止动作**：不得把未知原生 id 的第一张变动直接归因给结果不明指令；不得删除、重写或回填旧外部变动；不得用未声明或不可信的查询答复证明未递；不得在结果不明期间发新许可、创建新 broker 尝试或自动重下。

**结论**：第一张未知 id 变动明确是外部变动并带“存在未定指令”；2.4 能否收敛只有条件式答案：存在声明且可信的查询渠道并返回可关联结果时可以追加新回票，否则转人工。对“先外部、后回读同一事件”的去重键复用与新增关联没有定义，见卡点 SB-02。

## Trace 3：B 会话建立后不得把已有许可误作新尝试

**前置**：同一指令已有批准、A-02“已交集成”和 A-03 已落盘的调用许可；核心崩溃后接受 B；没有确定回票，所以重启判定为结果不明。

**刺激**：B 建立后，核心若把旧的“已交集成”误判为没有递送，于是试图用新尝试号重新派发同一指令。

**每步**：

1. `uta-design.md:254-256`，“调用许可已落盘、无回票 → 结果不明”；`uta-design.md:189-199` 规定状态由已有帐票函数得到。追加帐票：无新增；旧调用许可仍然存在，不能改判为仅“已交集成”。
2. `uta-design.md:240-246` 明确区分会话重建：无许可的旧尝试才在新会话重新派发，有许可的进入结果不明。追加帐票：无；本前置不满足无许可分支，不能追加新的“已交集成”。
3. `uta-design.md:204`（R3），“结果不明期间不创建新的 broker 尝试”；`contracts/01-operations.md:254-280`（A-09）再次规定查询期间“不发新的调用许可”。追加帐票：无；核心只能按查询渠道或人工凭证收敛。
4. `contracts/01-operations.md:111-121`（A-03），“同尝试号已有许可而拒绝”且“同一尝试号永不再许可”。追加帐票：无；B 若重复请求旧尝试号的许可，得到 typed 拒绝，不产生第二张许可。
5. `uta-design.md:196` 的重新派发条件是“已交集成、无调用许可、可证明未递”；本 trace 已有调用许可，因此该条件不成立。追加帐票：无；只有另一种明确没有许可的恢复前置，才可按文档产生新的“已交集成”和新的尝试号。
6. `contracts/01-operations.md:593-613`（B-11），“视图按指令持有的帐票计算”。追加帐票：无；客户端读到的是一条已有许可、结果不明及既有递送进度，不会因 B 会话建立而增加一条新尝试进度。

**客户端可观察**：指令视图保持结果不明；账户变动流不会出现第二张调用许可或新的 broker 尝试。之后客户端只能看到回票、对账响应、未递或人工凭证中的一种收敛路径。文档中直接保证“不重派”的句子是 `uta-design.md:240-246` 的“有许可的进入结果不明”，一般性保证是 `uta-design.md:204` 的 R3。

**禁止动作**：不得把已有调用许可当成许可未落盘；不得因 B 会话建立追加新尝试号、重新派发或请求新的调用许可；不得把结果不明转换为失败后自动重下。

**结论**：该 trace 的“不重新派发”有明确且相互印证的条文：`uta-design.md:240-246` 针对会话重建，`uta-design.md:204` 针对所有结果不明，A-03:111-121 针对许可幂等。没有本 trace 对应的契约卡点。

## Trace 4：Q20 双核心竞争后的集成会话归属

**前置**：旧核心 C-A 曾持有数据目录锁并接受集成会话 A；随后出现 Q20 的双核心竞争，新的核心 C-B 在取得锁并将接管 fence 加一后提供服务。旧核心进程或其集成连接仍存活，集成 A 试图提交回票。

**刺激**：C-B 已成为可服务的持有者后，仍连接旧核心的集成 A 提交 A-04 回票；问题是该回票由谁接收。

**每步**：

1. `uta-design.md:149`（Q20），“第二个核心对同一数据目录启动……拒绝启动”；`uta-design.md:254-256`，“锁不可得拒启；持有者死后 fence+1 落盘后才服务”。追加帐票：无；这是启动与存储接管诊断，不是账户交易帐票。
2. `uta-design.md:255`，“复活的旧持有者写入时 fence 小于存储头 → 被拒并退出”。追加帐票：无；旧核心不能追加回票、对账响应或外部变动。
3. `contracts/01-operations.md:125-153`（A-04）要求“集成 → 核心”，且前置是 A-01 会话已接受；`contracts/01-operations.md:12-13` 说明传输断开不是业务结果。追加帐票：未定义；文档没有说明旧连接的 A-04 是被哪个核心接收、转交或重试，不能自行选成外部变动。
4. 若集成 A 重新连接 C-B 并完成新的 A-01，`contracts/01-operations.md:34-63` 规定新集成会话号重新校验能力，随后 A-04 才有合法前置。追加帐票：无；A-01 的能力接纳是版本化记录。之后若回票关联成功，才追加回票。文档没有规定旧连接中的回票自动迁移到该新会话。
5. `contracts/01-operations.md:640-661`（B-13）只允许客户端观察每账户的“集成会话是否建立”等健康字段；`contracts/01-operations.md:593-613`（B-11）只返回已持久化帐票函数。追加帐票：无；健康读不能代替未定义的回票转交。

**客户端可观察**：C-B 的启动结果和健康读可以显示新的核心是否可服务、集成会话是否重新建立；但在 A 没有通过 C-B 新会话提交前，B-11 不会凭空出现回票。若旧 A-04 被旧核心拒绝且没有重新提交路径，指令仍保持原有结果不明或其他已有状态。谁接收旧连接的回票，当前契约没有唯一答案。

**禁止动作**：旧核心 fence 失效后不得继续写入；C-B 不得把旧 A 会话静默视为自己的会话；不得宣称旧连接的回票已自动转到 C-B；不得为了弥补未定义路由而擅自追加回票、外部变动或新的调用许可。

**结论**：Q20 只完整定义核心锁、接管 fence 和旧持有者写拒绝；没有定义集成会话随核心接管的迁移、旧连接回票的转交或重新提交边界。因此“谁收”是卡点，见 SB-03。

## Trace 5：SDK 不自动重试，但 broker 重复推送同一成交

**前置**：集成会话已由 A-01 接受；集成用于写请求的 SDK 已关闭自动重试；一张正常回票已经或将要通过 A-04 提交。broker 服务端把同一成交再次推送给集成。

**刺激**：集成没有再次发起 broker 写请求，但因重复推送而再次向核心提交同一成交回票。

**每步**：

1. `uta-design.md:202` 与 `contracts/01-operations.md:99-121`（A-03），“SDK/HTTP 客户端必须关闭写请求自动重试”。追加帐票：无；该规则只限制集成对写请求的自动重试，不处理 broker 事件重复推送。
2. 第一次 A-04 回票携带 broker 事件 id，或携带完整四元指纹。`uta-design.md:205-206,288-289` 与 `contracts/01-operations.md:133-149` 要求保留原生 id、状态原值、成交字段和原始负载摘要。追加帐票：一张回票。
3. 第二次推送使用同一 broker 事件 id，或完全相同的 `(broker 原生 id, 状态原值, 累计成交量, broker 时间)`。`uta-design.md:205`（R4）与 A-04 的“重复回票已忽略”生效。追加帐票：无；客户端只会在账户变动流看到第一张回票。
4. 第二次推送表示同一成交，但事件 id 改变，或四元指纹中的状态原值、累计成交量、broker 时间任一改变。文档只规定相同事件 id或相同指纹去重，未定义“同一成交”的另一种识别。追加帐票：未定义；不得把状态单调折叠误当成重复回票去重。
5. 推送既没有事件 id，也没有完整四元指纹时，`contracts/01-operations.md:140-149` 返回“因缺少回票去重键而拒绝”。追加帐票：无；该推送不进入账户变动流。

**客户端可观察**：重复推送使用同一已定义键时，客户端只收到一张回票，指令视图的状态与成交字段只按该回票保真呈现。若同一成交的两次推送使用不同键，契约没有保证只出现一张；客户端可能看到两张追加回票，即使同一指令的状态折叠仍保持单调。无键时客户端看到 typed 拒绝而不是一张回票。

**禁止动作**：不得因重复推送再次调用 broker；不得把 SDK 自动重试规则扩展为事件去重规则；不得凭状态相同、时间相近或成交字段相近自行造出额外去重键；不得以单调折叠抹掉已经追加的回票。

**结论**：R4 对“相同 broker 事件 id”或“相同四元指纹”的重复足够，且缺键时有明确拒绝；它没有定义同一成交却改变事件 id或指纹的情况。因此不能宣称 R4 对所有服务端重复推送都足够；重复逻辑成交的识别边界是卡点 SB-04。

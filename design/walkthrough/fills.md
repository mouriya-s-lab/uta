# 成交回票走查

## 范围与判定方法

本文只依据 `plans/uta-refactor/design/uta-design.md`。每条 trace 都按同一顺序记录：前置 → 刺激 → 每步（主文档行号、关键短语、追加帐票）→ 客户端可观察 → 禁止动作 → 结论。状态回票与成交回票始终分开判断：前者折叠状态，后者保留逐笔明细。

判定先看是否追加帐票，再看指令视图是否改变。帐票不可变且只追加（`uta-design.md:186`）；重复输入若命中主文档规定的去重键，不产生第二张帐票。

## Trace 1：一笔 10 股委托的重复成交与重复状态

**前置**：一笔 10 股委托已进入账户变动路径；broker 原生订单 id 为 `O`。成交 A 的 broker 成交 id 为 `A`，成交 B 的 broker 成交 id 为 `B`。客户端可以读取该账户的账户变动流和指令视图。

**刺激**：broker 依次推送成交 A（3 股 @100，佣金 1）→ 状态 `partially_filled`（累计成交量 3）→ 成交 B（7 股 @101，佣金 2）→ 状态 `filled`（累计成交量 10，平均成交价 100.7）→ 再推送成交 A（成交 id 仍为 `A`，时间戳不同，佣金字段不同）→ 再推送状态 `filled`（时间戳不同；broker 原生订单 id、状态原值和累计成交量不变）。

**每步**：

1. **成交 A**。依据 `uta-design.md:180`“回票·成交（逐笔：broker 成交 id、单笔数量、单笔价格、佣金、broker 时间）”，追加一张 `回票·成交`，保留 `A`、3 股、100、佣金 1 和 broker 时间。依据 `uta-design.md:199`“成交回票不改变状态，只补充逐笔明细”，指令视图不因这张成交回票改变状态。
2. **状态 `partially_filled`**。依据 `uta-design.md:179`“累计成交量、平均成交价等累计字段”和 `uta-design.md:206`“状态回票按 broker 状态偏序折叠”，追加一张 `回票·状态`，保留 broker 原生订单 id、状态原值和累计成交量；指令视图为部分成交，累计成交量为 3。
3. **成交 B**。依据 `uta-design.md:180`，追加一张 `回票·成交`，保留 `B`、7 股、101、佣金 2 和 broker 时间。依据 `uta-design.md:199`，指令视图仍为部分成交，累计成交量仍由状态回票给出。
4. **状态 `filled`**。依据 `uta-design.md:179、206`“累计成交量、平均成交价等累计字段”“状态回票按 broker 状态偏序折叠”，追加一张 `回票·状态`，保留累计成交量 10 和平均成交价 100.7；按状态偏序折叠，指令视图变为成交，累计成交量为 10。
5. **重复成交 A**。依据 `uta-design.md:206`“成交回票逐笔保留、不折叠；去重键 = broker 成交 id”，同一 `A` 不追加第二张 `回票·成交`。依据 `uta-design.md:186`，此前已追加的成交 A 不被覆盖；指令视图不变。佣金字段与第一次不同的冲突处置，主文档没有规定。
6. **重复状态 `filled`**。依据 `uta-design.md:206`“去重键 = broker 事件 id，或指纹（broker 原生 id，状态原值，累计成交量）——不含时间戳”，时间戳变化不改变该指纹，因此不追加第二张 `回票·状态`；指令视图仍为成交、累计成交量 10、平均成交价 100.7。

**客户端可观察**：账户变动流中有四张有效回票：成交 A、状态 `partially_filled`、成交 B、状态 `filled`；重复成交 A 和重复状态 `filled` 都不产生第二张。指令视图最终为成交。消费者按 `uta-design.md:206` 用状态回票的累计字段得到总成交量 10；按成交回票得到两笔明细：A = 3 股 @100、佣金 1，B = 7 股 @101、佣金 2。第二次 A 的不同佣金不能通过第二张帐票观察到；主文档没有定义是否返回冲突、告警或其他说明。

**禁止动作**：不得把成交 A、B 合并成一笔；不得用成交回票覆盖或回写状态视图；不得把时间戳加入状态回票去重键；不得因重复 A 再追加一张成交回票；不得替换已追加的 A 佣金；不得把状态累计成交量 10 与两张成交回票再次相加而得到错误总量。

**结论**：状态回票与成交回票的追加、折叠、去重和客户端总量/明细读取均已定义；同一 broker 成交 id 携带不同佣金时是否需要冲突记录、拒绝或告警未定义，列入 F-01。

## Trace 2：能力声明为“无逐笔成交”

**前置**：该账户的集成能力声明已标明“无逐笔成交”。broker 不提供 broker 成交 id，因此集成只能提交状态回票；客户端订阅账户变动流并读取指令视图。

**刺激**：broker 只推送状态 `partially_filled`（累计成交量 3）和状态 `filled`（累计成交量 10，平均成交价 100.7）。随后集成仍试图提交一张没有 broker 成交 id 的 `回票·成交`。

**每步**：

1. **状态 `partially_filled`**。依据 `uta-design.md:179、206`“累计成交量、平均成交价等累计字段”“状态回票按 broker 状态偏序折叠”，追加一张 `回票·状态`，保留状态原值和累计成交量 3；指令视图为部分成交。
2. **状态 `filled`**。依据 `uta-design.md:179、206`“累计成交量、平均成交价等累计字段”“状态回票按 broker 状态偏序折叠”，追加一张 `回票·状态`，保留状态原值、累计成交量 10 和平均成交价 100.7；按状态偏序折叠，指令视图为成交。
3. **集成提交无 broker 成交 id 的成交回票**。依据 `uta-design.md:206`“broker 不给成交 id 的，集成不得输出成交回票”，这不是允许的成交回票。依据 `uta-design.md:289`“无键 → 该记录被拒（typed），不进流”，该输入不追加 `回票·成交`，也不进入账户变动流。

**客户端可观察**：客户端能看到两张状态回票，指令视图最终为成交，并按状态回票累计字段得到总成交量 10 和平均成交价 100.7。客户端不能得到成交 A、B 各自的数量、价格、佣金或 broker 时间，因为不存在逐笔成交回票；平均成交价不能替代两笔逐笔明细。非法提交的无 id 成交回票得到 typed 拒绝且不进流；主文档没有为该拒绝规定更细的错误变体或额外客户端展示。

**禁止动作**：集成不得在能力声明为“无逐笔成交”时输出成交回票；不得虚构 broker 成交 id；不得从累计成交量或平均成交价反推出 A、B 的逐笔价格和佣金；不得把无 id 的输入静默写入账户变动流。

**结论**：无逐笔成交能力下，状态回票和累计字段路径已定义；无 broker 成交 id 的成交回票按 typed 拒绝且不进流处理。拒绝的更细错误变体和客户端展示未定义，列入 F-02。

## Trace 3：状态乱序，成交回票晚到

**前置**：同一笔 10 股委托的 broker 原生订单 id 为 `O`，成交 A、B 分别有稳定的 broker 成交 id。两张状态回票不是同一事件：`filled` 的状态原值和累计成交量为 10，`partially_filled` 的状态原值和累计成交量为 3，因此两者指纹不同。

**刺激**：broker 先推送状态 `filled`（累计成交量 10，平均成交价 100.7），再推送状态 `partially_filled`（累计成交量 3），最后才推送成交 A（3 股 @100，佣金 1）和成交 B（7 股 @101，佣金 2）。两笔成交回票都晚于对应的状态回票。

**每步**：

1. **先到的状态 `filled`**。依据 `uta-design.md:179、206`“累计成交量、平均成交价等累计字段”“状态回票按 broker 状态偏序折叠”，追加一张 `回票·状态`；指令视图为成交，累计成交量为 10，平均成交价为 100.7。
2. **后到的状态 `partially_filled`**。依据 `uta-design.md:186、206`“帐票不可变、只追加”“迟到的旧状态不覆盖新状态”，该状态与前一张的状态原值和累计成交量不同，不命中前一张的去重键，因此追加一张 `回票·状态`；但它是迟到的旧状态，不能覆盖已折叠的 `filled`，指令视图仍为成交，累计成交量仍为 10。
3. **晚到的成交 A**。依据 `uta-design.md:180、199、206`“逐笔字段”“成交回票不改变状态，只补充逐笔明细”“去重键 = broker 成交 id”，追加一张 `回票·成交`，保留 A 的逐笔字段；不改变已折叠的成交状态。
4. **晚到的成交 B**。依据 `uta-design.md:180、199、206`“逐笔字段”“成交回票不改变状态，只补充逐笔明细”“去重键 = broker 成交 id”，追加一张 `回票·成交`，保留 B 的逐笔字段；指令视图仍为成交。

**客户端可观察**：指令视图的折叠结果是成交、累计成交量 10、平均成交价 100.7；迟到的 `partially_filled` 回票仍是不可变的已追加记录，但不能使视图回退。在本 trace 各步按到达后依次完成追加的前提下，依据 `uta-design.md:39、41、230-234`，这些回票属于账户变动流，并按持久记录顺序转发；消费者看到的顺序是：`filled` 状态 → `partially_filled` 状态 → 成交 A → 成交 B。文档没有按 broker 时间戳重新排序的规则。消费者读取最终状态时看指令视图，读取总量时看状态回票累计字段，读取明细时看随后补到的两张成交回票。

**禁止动作**：不得因 `partially_filled` 晚到而把指令视图从成交退回部分成交；不得丢弃这张不同指纹的状态回票；不得因成交回票晚到而新建状态或改变状态；不得按 broker 时间戳重排已经追加的帐票；不得把账户变动流中的到达顺序误当成状态折叠优先级。

**结论**：状态回票的乱序折叠、成交回票的晚到补充和消费者读取方式均已定义；本 trace 的账户变动流观察顺序以追加顺序为准，不以 broker 时间戳排序。

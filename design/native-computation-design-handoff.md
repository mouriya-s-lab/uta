# 自定义原生计算：设计交接稿

## 0. 定位、状态与证据边界

- **读者**：负责下一轮 UTA 设计整合的设计师与维护者。
- **目的**：把维护者已经说清的自定义计算场景、边界和当前原生方向单独固定下来，使设计师不依赖讨论记录即可继续设计。
- **状态**：这是**已同意的场景/约束 + 当前设计方向**，不是完成的 ABI、运行时、加载器或状态架构。
- **来源**：维护者对本场景的明确要求，以及当前的 [UTA 核心设计](uta-core-design.md) §0.2、§0.3、§5、§5.1、§5.2、§7.0、D6 与相关 spike。
- **证据纪律**：维护者约束标为 `[设计：维护者约束]`；由约束推出、供设计师采用或修订的方向标为 `[设计：推导或建议]`；尚未决定且必须以设计或实验关闭的事项标为 `[spike]`。
- **不在本文做的事**：不实现代码，不改核心正文，不做外部研究，不发明 ABI/API、序列化格式、缓存键、线程模型或调度算法。
- 当前核心 §15 的登记由主线完成；本文只是供后续整合的输入，不等于核心已完成修订。

## 1. 一句话结论

计算是一个**黑盒闭包**：UTA 不需要理解它的内部算法，只需把已注册的读数据和触发信号交给它，并把它产生的值交给程序中已经约定的消费者。`[设计：维护者约束]`

本稿的当前方向是：在与 UTA **同一地址空间**中运行一个可动态编写、替换的小型原生 Rust 计算，让它借用宿主已经准备好的、类型明确的只读窗口/视图；不为每个指标把整个应用重新做一遍。`[设计：推导或建议]`

这两个句子不构成最终 ABI。窗口如何物化、借用多长时间、代码如何编译和装载、失败如何恢复，仍需设计与 spike。

## 2. 问题域与不变的责任边界

| 概念 | 在本场景中的含义 | 核心应否理解内部业务语义 |
|---|---|---|
| 外部来源 | 可有多种来源形态；通过既有入站路径产生记录或向已挂载点发出信号 | 否 |
| 既有入站链路 | 集成提供证据、信封字段和载荷；核心保持位置权威与反向代理职责，不因计算扩展改写协议 | 只理解已登记的锚点与字段 |
| 读 effect | 取得观察数据、推进记录并触发计算；结果仍是可记录的观察值 | 只按注册关系处理 |
| hook | 效应的挂载点；其业务含义由注册方和消费者定义 | 不要求核心理解 |
| computation | 对输入执行的黑盒闭包；本例中只读并输出值 | 不要求核心理解算法 |
| consumer | 已在程序中约定的值消费者，例如负责某订单的 AI 唤醒 | 消费关系由程序/注册关系定义 |

不得借本场景新增一个“指标权威对象”或让核心拥有策略业务语义。观察记录、hook、程序、消费者之间的关联仍沿用核心已有的记录与注册边界。`[设计：维护者约束]`

```mermaid
flowchart LR
  SRC["多种外部来源"] --> RP["既有 reverse proxy / provider"]
  RP --> OBS["观察记录与位置推进"]
  OBS --> HOOK["已注册的读 hook / trigger"]
  HOOK --> VIEW["宿主已准备的 typed read-only 完整窗口视图"]
  VIEW --> CLOSURE["opaque native Rust closure"]
  CLOSURE --> VALUE["indicator / value"]
  VALUE --> CONSUMER["已约定 consumer<br/>示例：对应订单的 AI wake"]
  CONSUMER -->|若产生新的写请求| EFFECT["既有写请求消费路径<br/>单据、STS、IO 壳与日志"]
  EFFECT --> WORLD["外部世界的正常写操作"]
```

图中的 `trigger` 只说明存在触发关系，不选择 edge、level、合并或冷却语义。AI wake 是下游消费，不是计算闭包直接交易，也不是核心直接写 venue。`[设计：维护者约束]`

## 3. 维护者已经收束的约束

1. **黑盒 hook**：UTA 只负责挂载、取数、记录和把值交给已约定消费者；不重写入站 reverse-proxy 协议，不把任意算法搬进核心。`[设计：维护者约束]`
2. **只读指标**：本场景的计算接口提供观察数据并接收计算值，不提供 venue 写入口；这是正常 API 契约，不是对原生代码实际权限的限制。`[设计：维护者约束]`
3. **写边界不变**：若下游 AI 产生外部写请求，正常 API 仍经单据、STS、IO 壳与日志/证据处理，不增设绕过它们的正式写入口；不承诺阻止恶意原生代码自行旁路。`[设计：维护者约束]`
4. **记录渐进、算法不强制渐进**：观察和 effect 的记录位置会逐步推进，但不能因此要求任意闭包都能由 delta 自动归约或自动增量化。`[设计：维护者约束]`
5. **每次触发的完整窗口**：本例要求每次触发都能看到指定输入的完整最新窗口，而不是只看到本次 delta。不能以 delta-only API、静默丢弃中间输入或另建一个免费的 TS 历史缓存替代。`[设计：维护者约束]`
6. **窗口约束有范围**：完整窗口是本场景的可见性契约，不外推成所有 computation 的统一参数或容量承诺。`[设计：维护者约束]`
7. **TS 序列化假设有范围**：本次比较中的 TS 路径按需序列化完整窗口；它不是“所有 JS 运行时都没有二进制 buffer”的断言。`[设计：维护者约束]`
8. 在该 TS 路径中，每次完整窗口交付会重复遍历、编码、解码和分配；一个逻辑 subscription 不会自动消除这些调用成本，也不承诺引擎特定的 zero-copy。`[设计：维护者约束]`
9. **native zero-copy 的精确定义**：仅指同一地址空间内，从宿主已有的 typed read-only window/view 借用到计算调用，不发生每次调用的完整窗口传输。它不覆盖网络、数据库、解码、连续物化等前置成本。`[设计：维护者约束]`
10. 该 zero-copy 不指独立 Rust 进程经 IPC 传递，也不指把宿主 Rust 引用任意伸进 Wasm；连续存储、视图生命周期、保留和并发更新尚未解决。`[设计：维护者约束]`
11. **安全边界**：维护者的明确约束是：“**uta不保证程序无毒，在追求性能的前提下无法保证**”。native 路径不恢复 hostile-code sandbox 承诺；只读类型、native 进程或常规进程形态都不能被写成恶意写入防护。`[设计：维护者约束]`
12. 仍需有普通 API discipline：读数据 → 计算 → emit value → 注册消费者；正常外部写只能走既有 effect path。故障、权限和资源超限的处理要设计，但不能借此重新声称硬隔离。`[设计：维护者约束]`

## 4. 具体场景（数字不是基准）

UTA 持续观察约 1500 条 market stream；一个自定义 computation 选取其中 15 条，使用最近 24 小时的逐秒数据计算 indicator。indicator 达到某个业务阈值后，唤醒与该订单对应的 AI。`[设计：维护者约束]`

- 1500、15、24 小时和逐秒粒度是沟通用场景，不是通用容量上限、默认配置、速率保证或所有策略的必选参数。
- 若某一条流在该窗口内持续保持 1 Hz 覆盖，则该流有 `24 × 60 × 60 = 86,400` 条记录；15 条合计 `1,296,000` 条，前提是覆盖未中断。
- 本计算每次触发都需要这 15 条流的完整最新窗口可见；该要求不能被“只传新增一条”替换。
- 不虚构记录字节大小、p99、吞吐预算或内存预算。
- 阈值后的唤醒具体按边沿还是电平、是否合并或冷却，仍是开放策略，场景文字不暗中选定默认值。

## 5. 当前 native 方向（不是最终架构）

以下是由上述约束推出、交给设计师继续成形的方向：`[设计：推导或建议]`

- 计算作者应能快速地观察结果、修改一个小计算并再次观察，而不是每次指标变化都构建一个完整应用。
- 计算内部保持 opaque；核心只需要稳定的“输入窗口 → 值/失败观察 → 已注册消费者”边界。
- 挂载契约应明确输入流、窗口需求和结果消费者；核心不需要分析闭包源码来推导依赖，也不应默认把全部 1500 条流交给每个计算。具体登记形式仍待设计。
- 宿主负责维护可供读取的观察数据；调用时向同地址空间的 Rust 计算借用类型明确的只读视图。借用只在宿主与计算共同定义的有效期间成立。
- 该方向追求避免每次调用搬运完整窗口，但不把“连续物化”和“没有复制”混为一谈，也不把宿主的所有前置阶段宣称为 zero-copy。
- 动态更新面向小计算单元。source 编译、预编译 artifact、工具链供应、平台 artifact 以及最终用户是否需要本地构建，都是设计选择，不在此稿决定；不得默认终端用户每次都构建完整程序。
- 作者在编码时需要类型明确的窗口、字段、单位和输出约定，而不是猜测宿主对象。类型接口与开发工具本身是工程交付物，TS 绑定也不例外；导出入口数量不等于类型信息丰富程度，更不直接等于优化机会。
- 当前核心 §0.2 已将组合子表示收窄为一个 enum 值和启动/装载期的四个 fold；这不是把原生闭包改造成编译期泛型 AST，或承诺对任意闭包自动派生这四种结果的依据。
- 当前 §5 的闭合值代数仍是核心已有设计中心之一；native computation 是待整合的扩展方向，不是据此 blanket 删除所有 combinator、日志、STS 或 effect 机制。

### 5.1 与现有运行时约束的关系

当前核心 §5.2 对 Wasm 选项保留 macOS / Linux / Windows 三 OS、开箱即用、预算/trap/打包一致性的门槛；不应因本文接受 native 不保证程序无毒，就静默删除这些既有产品/运行时要求。`[设计：维护者约束]`

这条要求只约束未来评估 Wasm 或类似运行时是否可选；它不替 native 预先决定 source 编译还是预编译交付，也不替设计师解决跨平台工具链、ABI 耦合或每平台产物。若平台/构建可用性成为 native 交付条件，仍需单独给出证据。`[spike]`

## 7. 关键场景走查

### 7.1 正常路径

1. provider 沿既有 reverse-proxy 协议接收多源数据，解析锚点与已注册字段，其余载荷仍可不透明转发。
2. 观察记录和位置逐步追加；某个注册的 read hook 根据已决定的触发语义收到信号。
3. 宿主为该次调用提供 15 条输入的最近 24 小时完整窗口视图；窗口内记录不因“本次只新增一条”而消失。
4. native Rust 闭包借用该只读视图，执行自己的算法，输出一个 indicator value 或结构化失败结果；核心不解释算法。
5. 值被追加/暴露给约定 consumer。示例 consumer 检查阈值并唤醒对应订单 AI；是否重复唤醒由未决 trigger policy 决定。
6. AI 若产生外部写请求，该请求进入既有 effect path、STS、IO 壳和日志/证据，不由闭包直写 venue。

### 7.2 缺口、不完整或窗口过期

- provider 断线、记录 gap、窗口未完备或 retention 已越界时，系统不得伪造连续输入，也不得静默当成完整窗口。
- “不调用闭包”“以显式不完整状态观察”“等待完备进度”或其他策略的取舍尚未决定；设计师必须让选择可观察、可重放并与 trigger/backpressure 一致。`[spike]`
- latest/conflated 只在消费者明确接受其 gap 语义时才可能使用；本场景的完整窗口依赖不能默认降级为 latest。`[设计：推导或建议]`

### 7.3 闭包失败、超时或资源超限

- 无有效 value 时，不得把错误伪装成指标值触发正常阈值消费；错误、输入版本和计算版本应能被观察到。错误是否通过独立消费关系唤醒 AI 协助诊断，及具体记录形状，仍待设计。`[设计：推导或建议]`
- 重试、跳过、暂停、限流、人工介入和恢复边界都是 `[spike]`；本文不选策略，也不把宿主权限或只读视图描述成恶意代码隔离。

### 7.4 代码修订与同输入比较

- 作者修改小计算后，需要能区分旧/新 code version，并在相同输入窗口上观察中间值和最终值差异。
- 记录推进是增量的，不代表算法必须增量化；不能为追求实现方便而只保留 delta 或自动假设任意闭包可重算。
- 代码何时生效、旧版本是否继续完成已在途调用、结果如何排序，留给 replacement 设计。`[spike]`

### 7.5 替换、重启与状态

- 若替换发生在调用持有 view、仍有排队触发或存在未完成状态时，生命周期和结果归属必须明确；不得假定旧 view 可立即释放，也不得假定新旧状态自动兼容。
- 重启后的 state reconstruct、从日志重放或迁移的选择需与核心 S4 和保留边界一致；没有实验或契约前，不宣称 live state migration。
- 编译/装载失败或版本不兼容时，旧版本保留、禁用计算或其他 fallback 的选择是 `[spike]`，不得在本文中暗定。

## 8. 范围内的替代比较

| 方向 | 能满足什么 | 代价 / 未决点 |
|---|---|---|
| 闭合 DSL / 程序值树 | 核心可遍历、检查和解释内部计算结构 | 本场景不要求理解任意算法内部；为此维护算子与语言语义并非默认选择，但不因此删除核心自身的组合子 `[设计：推导或建议]` |
| TS 序列化完整窗口 | 易接入既有跨语言形状，保留黑盒 hook | 每次调用有完整遍历与序列化链；类型导出仍需工具；不自动解决观察、reload、state 或 debug `[设计：维护者约束]` |
| native 同地址空间借用 view | 是当前方向：在宿主已建立完整窗口及有效视图的前提下，调用可直接借用而不搬运整个窗口 | ABI、工具链、平台产物、窗口物化与一致性、borrow/retention/并发、错误与替换都未定；借用本身不建立完整窗口 `[设计：推导或建议]` + `[spike]` |
| 独立进程 / IPC 或可选 Wasm 宿主 | 故障域、预算或隔离问题可能更易表达 | 跨边界通常重新引入序列化/复制；不提供本稿 native zero-copy；Wasm 还须满足 §5.2 三 OS 开箱即用条件，不能借此恢复恶意代码承诺 `[spike]` |

比较只针对本场景的计算调用与交付边界，不重写 provider 的独立进程 + 默认 JSON-RPC 契约，也不把任何方向写成已经否决或已经完成。

## 9. 对核心设计的影响边界

已存在、可直接复用的概念关系是：§0.3 的观察侧/效应侧单向边、§5.1 的读/写 effect handler 区分，以及 §7.0 的锚点 + 按字段注册处理器。计算把观察值读入黑盒并把值交给下游，不改变这些关系。`[设计：推导或建议]`

设计师后续至少要复核：

- §0.2 的 enum 值树与四个装载/启动期 fold，明确 native closure 与值树、typed contract 的关系；
- §5 的闭合 `Program`、解释①/②、输入位置推进、状态划分及“算法未必增量”的边界；
- §5.2 的 runtime-isolation 前提，不把 native 无毒保证缺失误写成 Wasm 三 OS 约束消失；
- D6 的 JSON 规范值树假设，决定 native computation 与现有程序表示如何共存，而不是未经设计就宣称 JSON-only 或全面替换；

## 10. 实验与关闭标准

本稿任务中**没有运行任何实验**。以下是设计师应要求的最小证据集，测量值和阈值均待定：`[spike]`

1. **完整窗口原型**：按 1500/15/24 小时/逐秒的场景构造真实 full-window program，确认每次触发可见性、缺口表示和记录保留行为。
2. **调用成本**：测量 native 从宿主已有视图到实际计算结果的分配、额外遍历、端到端延迟及积压，确认没有把整窗复制藏在视图构造阶段。若仍需比较序列化方案，可建立完整窗口交付基线；不要求为比较而实现第二套生产运行时，也不能只凭一个 subscription 推断成本。
3. **迭代成本**：比较 cold build、修改后到可见结果、依赖存在时的 warm rebuild；不得把“Rust 会很快重编译”当作既定事实，也不得要求用户默认构建完整应用。
4. **可观察性**：同一输入窗口运行不同 code version，检查中间值、最终值、输入位置和版本能否对齐与复现。
5. **生命周期**：在输入更新、窗口过期、并发调用和 replacement 同时发生时，观察 view 借用、释放、排队和结果归属；确认不存在悬空借用或静默丢中间输入。

设计可以在以下问题均有可复现实验/契约答案后关闭本 handoff 对应的 spike：完整窗口语义明确；调用成本与积压已有测量并经维护者确认预算；交付路径和平台约束明确；版本、观察、替换、重建与错误可追溯；正常 API 的外部写仍经既有 effect path。若任一观察证明同地址空间借用无法在所需生命周期或负载下成立，应回到替代比较，而不是用 delta-only、无记录缓存或安全口号掩盖。

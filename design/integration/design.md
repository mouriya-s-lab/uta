# 集成（上游适配层）设计

本文设计集成这一侧：集成为什么存在、做什么、不做什么，契约声明部分的书写形式，以及怎样证明一个集成合格。核心↔集成的契约（声明与行为两部分、操作集、推送、义务）由核心设计 §8.1–§8.4 拥有，本文只引用，不重述；核心章节号 `§N.M` 指 `design/core/` 下前缀为 N 的文件。

- **范围**：适配器的职责分解、声明的书写形式、行为义务在实现上的约束、一致性测试的构成、接入一个新 venue 的步骤。
- **不在范围**：先接哪个 venue；某个 venue 的具体映射表与调用序列（那是该集成自己的实现制品）；IDL 与公共 schema 的文件格式（实现阶段制品，§8.1）。
- **状态**：已定。

## 1 为什么有这一层

> 根本约束见 §0.1：值的权威在上游，UTA 只有意图。

总得有一个地方去接触原值：读懂上游协议、在上游落实意图、判定上游的回应对某个意图意味着什么。这件事若发生在 UTA 里，UTA 就要持有原值的拷贝，并承担与原值无尽的对齐。集成把每个上游的全部接触集中到一处，对 UTA 只交出契约值形式的结论，和作为证据的原文。[设计]

```mermaid
flowchart LR
  UP["上游<br/>值的原件、权威"] <-->|"上游协议<br/>只有集成读得懂"| AD["集成（适配器）<br/>上游的唯一消费点"]
  AD -->|"行为：封闭返回值、推送（§8.2、§8.3）"| CORE["UTA 核心<br/>意图及其推进记录"]
  AD -->|"声明：Projection 等（§8.1）"| CORE
  CORE -->|"调用：submit / query_by_key / …"| AD
```

同一接入涉及两种描述，不能混写：

- **怎样和这个上游打交道**：调用编排、鉴权签名、分页、重连、pacing、协议清洗。即使所有上游都提供 OpenAPI，不同的接口设计也会造成完全不同的调用逻辑，所以这一部分只能是代码，每个集成各写一份。
- **这个集成向 UTA 声明什么**：它有哪些作用域、哪些流、各流的载荷 schema、各操作的能力与取证渠道、上游身份怎样对齐到锚点。这一部分是 UTA 契约的声明部分（§8.1），是值。

契约若全部用声明写出，就等于用声明语言写程序；所以声明只覆盖“核心在任何操作之前要读取并 fold 的东西”，其余都是行为，以代码实现、以一致性测试验证（§4）。

## 2 集成做什么

集成的全部职责都是“接触原值”的三种形态。每种形态的输出都是契约值，判定规则由核心拥有，这里只给出落点。

| 形态 | 集成内做的事 | 对核心的输出 | 规则所在 |
|---|---|---|---|
| **消费上游**（读） | 订阅上游推送、清洗、按公共或扩展 schema 写成载荷；上游状态映射到契约词表；提取 venue 身份与位置证据；识别断线与断代 | 观察记录（信封 + 载荷 + 原始负载）、`Gap{origin: Source}`、readiness | §2.1、§2.2、§8.1、§8.3、§8.4 |
| **落实意图**（写） | 把一次 `submit` / `cancel` 变成上游调用序列；把调用方键写进上游的幂等字段；判定上游回应 | `Ack` / `Reject` / `NoResponse`，附 `Evidence` 所需的载荷与原始负载 | §6.5、§8.2、§8.3 |
| **应答取证与读** | 按核心的调用向上游询问；判定上游回答对该键 / 该范围意味着什么 | `Found` / `Absent` / `Unavailable`、`Listing`、`Fills`、`Page`、`Records` | §6.6、§8.2、§8.3 |

实现上的约束 [设计]：

- **判定所需的上游事实写在判定处。** 键的唯一性与可查期限、listing 的滞后、状态枚举的全集（§1.6.1）决定 `Absent` 能否成立、映射是否穷尽。这些事实由集成在自己的实现里持有并使用；核心从不看到它们，只看到判定结果。
- **原始负载是集成所消费的原文。** 走 HTTP/WS 的上游，原文就是响应或消息字节；经 SDK 回调接入的上游（如 IBKR TWS），原文是集成对 SDK 回调对象的无损序列化，以 SDK 暴露的全部字段为界。原始负载只作证据（§2.1），集成不得把应属结论的信息只放在原始负载里。
- **写只发一次。** 一次 `submit` / `cancel` 在上游至多一次写调用；上游 SDK 自带的写重试必须关闭（§8.3）。读可以在集成内部重试，重试结果仍须来自对上游的询问。
- **有公共 schema 的种类必须用公共 schema。** venue 特有内容走扩展 schema 的单独流，程序按身份字段 `Join`（§8.1）。

## 3 集成不做什么

- **不以拷贝回答读。** 读与取证的回答来自本次对上游的询问；为消费推送流维持的状态只用于产出推送记录（§8.3）。集成本身也不得成为上游原值的第二份拷贝。
- **不越过契约。** 不把上游消息格式放进载荷；不输出契约封闭集合之外的返回值；判定不了就取保守值（`NoResponse`、`Unavailable`、`Unmapped(raw)`），不交给 UTA 再判定。
- **不做决策。** 不持有规则状态、不决定是否发写、不重试写、不接触 SQLite（§8.3）。
- **不理解 UTA 的规则。** 集成只需要锚点表、字段注册表与载荷 schema（§2.1）。

## 4 声明的书写形式

声明是契约声明部分（§8.1）的一个值：`Projection`（§2.2，含扩展载荷 schema）、锚点对齐、已注册字段。

- **声明是值，不是描述调用的程序。** 集成可以先调用上游（例如列出账户以得到 `WriteScope`、查询已开通的能力），再构造这个值；交给核心的只是结果值，其中不含调用、时序、时间或状态。[设计]
- **值是权威表示，各语言的构造 API 只是构造糖。** 与值树的规则相同（§2.5）：构造 API 必须产出同一个值，核心按契约 schema 校验它；校验失败按 §8.2 `handshake` 的错误处理（投影不合法 → 拒绝该集成）。[设计]
- **声明随握手给出。** 能力可在握手之后变化，经能力变更推送进入核心（§8.3），不改声明的形式。
- **核心在声明上做的事**：路由（lane 按 `WriteScope`、订阅按 `StreamDecl`）、门（按 `Capability`）、`required_inputs` 比对（§2.5）、取证渠道顺序（§6.6）。声明中出现的每一项都应能对应到其中一处；对应不上的内容不属于声明。

本仓库随 IDL 发布：契约 schema（含 `Projection` 与公共载荷 schema）、一致性测试套件与 fixture 上游。本仓库不提供各语言的适配器框架：契约只有一份，合格与否只由一致性测试裁定；框架是实现便利，以后加入也不改契约。[设计]

## 5 一致性测试

一个集成合格，当且仅当它通过一致性测试。测试以 **fixture 上游**驱动集成：fixture 是可编程的假上游，扮演上游的全部回应方式，测试观察集成对核心输出了什么。

fixture 必须能注入的上游行为：

- 写：业务回执、明确拒绝、超时、断连、5xx、仅传输层确认、回执迟到；
- 读：命中、明确否定、键超出上游保证期限、listing 滞后、分页、不可达；
- 推送：乱序、重复、断线、续传游标可用与不可用、未列举的状态值、venue 专有字段。

测试项：

- 核心验收 §10.5 #22 的每一条（返回值含义、写调用数 ≤ 1、不以拷贝作答、公共 schema、`Unmapped(raw)`、原始负载与 `session_epoch`）；
- 推送义务：断线后上报 `Gap{origin: Source}`；readiness 进入 `Live` 时声明 `live_from`；续传与否按 §8.2 `handshake` 的 epoch 规则；`attribution` 按 §5.3 填写；
- 声明：声明值通过契约 schema 校验；写操作的 `CapabilityProof` 所声明的每条取证渠道，在 fixture 上都能按 §8.2 的返回值集合应答。

每个集成上线前必须通过全部测试项；这也是 C2 关闭事件“每个集成上线时其 P1 声明完整”的检查点。

## 6 接入一个新 venue

1. 从该 venue 的一手文档核实能力：推送流、调用方幂等键及其唯一性与保留期、按键回读、续传游标、配额（§1.6.1 的一行）。
2. 写声明：作用域与锚点对齐、流与载荷 schema（先用公共 schema，容纳不下的进扩展 schema）、每个 `(scope, OperationKind)` 的能力与取证渠道。
3. 写行为：三种形态的调用序列与判定；状态映射表按该 venue 列举输入枚举，未列举的输出 `Unmapped(raw)`。
4. 让 fixture 上游复现第 1 步核实到的每一项能力与限制，通过一致性测试。

新 venue 只加处理器与扩展 schema，不改锚点、不改核心（§8.3 扩展三轴）。

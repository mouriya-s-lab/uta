# 长连接端点

## 0 定位

- **层级与元素**：L3 component，解释层程序里的“长连接端点”组件：外部客户程序（包括 Alice）与解释层之间的双向长连接。
- **上级文档**：[design.md §4.1 组件与部署](design.md#41-组件与部署)（解释层部分的 L1 与容器视图；端点落在哪个进程也在那里）。
- **本文决定什么**：一条连接上的请求与推送；推送从哪里来；续传令牌与确认；订阅选项；订单与审批的推送；读取令牌在连接上怎样兑现。
- **读者**：实现长连接端点的人；外部客户程序的作者（经本仓库发布的消息协议 schema）。审批者：无（K3）。
- **状态**：已定。
- **非目标**：
  - 核心↔解释层的订阅组、会话与一次性读的规格：[subscription.md §4.1 核心↔解释层：订阅组与 rewind_cursor](../core/core-process/subscription.md#41-核心解释层订阅组与-rewind_cursor)、[session-entry.md §3 模型](../core/core-process/session-entry.md#3-模型)、[one-shot-read.md §4.2 核心↔解释层：read](../core/core-process/one-shot-read.md#42-核心解释层readtargets-deadline--vectargetresult)。本文只引用。
  - 请求与推送的对外说法、读取令牌的内容与认定：[translation.md](translation.md)。
  - 消息字段的序列化形状与传输：实现阶段制品。

证据标签与编号前缀的约定见 [README.md §0.4 阅读约定](../README.md#04-阅读约定)。

## 1 分配给本组件的需求与它面对的域

### 1.1 上级分配的需求

需求编号见 [design.md §1.3 分配给解释层的需求](design.md#13-分配给解释层的需求)。本组件承担：

| 需求 | 本组件承担的部分 |
|---|---|
| Q29、C5（依 H5） | 端点不持有状态；客户凭续传令牌重连，投递从核心持久化的已确认 cursor 之后续（§3、§4.3） |
| C6 | 断连期间的投递损失以缺失通知给出（§4.3） |
| Q2、Q9 | 待审事项、结果未知与已确认的推送经执行事实订阅到达，重连不丢（§4.2、§4.5） |
| C11、Q19（依 H7） | 非本 OS 用户的连接拒绝；以下游自报的 actor 握手，请求体里的身份不进核心会话（§3、§4.1） |

### 1.2 本组件直接面对的域

- **外部客户程序**：独立生命周期，随时断开、崩溃、重启；它自己保存续传令牌与读取令牌，重连时交回。
- **OS 传输**：对端凭据的粒度是 OS 用户（H7）；本机非本用户的进程不可信，本用户的进程视为用户本人。
- **核心会话**：以握手建立，只在核心实例的内存里；会话不拥有订阅、单据或在途读（[session-entry.md §3 模型](../core/core-process/session-entry.md#3-模型)）。

## 3 模型

- **一条连接一个核心会话**：端点为每条连接以下游自报的 actor 握手开一个核心会话；连接断即会话结束，核心不为此写记录。
- **不持有状态**：订阅、确认进度、单据都在核心（[design.md §3.1 解释层不持有状态](design.md#31-解释层不持有状态)）。端点崩溃或重启，对客户就是一次断连；端点自己没有要恢复的东西。
- **续传令牌不是第二份进度源头**：它是客户保存的、对核心侧确认进度的不透明编码；续投的起点只由核心持久化的已确认 cursor 决定。
- **不变量**：
  1. 端点不以请求体里的身份开会话或发请求；核心会话的 actor 只取连接建立时下游自报的那一个。
  2. 端点对下游说出的每个状态与结果都经翻译（[translation.md](translation.md)），连接上不出现核心概念。

## 4 结构与接口

**拥有**：与外部客户程序的双向连接；推送的组装；续传令牌；把客户的确认转为核心的确认。
**隐藏**：传输与消息的序列化形状。
**假设**：一条连接一个核心会话；连接断即会话结束。

### 4.1 连接与请求

- 外部客户程序（包括 Alice）与解释层保持一条双向长连接：同一连接上发请求（与一次性命令同一组操作），收推送（订单状态、成交、行情、策略程序具名输出的当前值、待审事项、结果未知通知、连接状态变化）。推流靠它。
- 非本 OS 用户的连接拒绝，不开核心会话（H7；身份与授权的整体安排见 [design.md §4.4 身份与发布物](design.md#44-身份与发布物)）。
- 请求怎样解析到核心的目标、结果怎样翻成对外说法，与一次性命令相同：[translation.md §4.1 请求的解析：此刻能不能](translation.md#41-请求的解析此刻能不能)、[translation.md §4.3 状态与结果的翻译](translation.md#43-状态与结果的翻译)。

### 4.2 推送从哪里来

- 待审事项、结果未知、“已确认发生 / 未发生”与“已放弃跟踪，结果未知”来自解释层对各来源执行事实的订阅（[subscription.md §3.1 订阅与项](../core/core-process/subscription.md#31-订阅与项)），与行情推送一样持久、可续传，重连不丢。推送的是事项的出现、决定与关闭；某待审事项此刻是否已偏离（市场变了），不单独推送，解释层在呈现该事项时读取单据的当前状态（[read-model.md §4.2 读模型集合](../core/core-process/read-model.md#42-读模型集合)），放行与否仍由核心当时的门判定。
- 账户、可读数据与能力变化时（来源重新连接、能力变更），解释层经同一订阅得知并重读声明，对下游的账户列表与“此刻能不能”随之更新。
- 策略程序具名输出的推送语义（每条带完整值、从现在开始不补发、值未改变不重复推送）见 [translation.md §4.2 策略程序的具名输出](translation.md#42-策略程序的具名输出)。

### 4.3 续传与确认

- **续传令牌**：不透明，编码核心侧的确认进度。客户保存，重连时交回；解释层不保存，续投的起点由核心决定（§3）。
- **确认**：客户表示“已处理”，解释层转为核心的确认（确认 = 已处理，[subscription.md §3.2 cursor 与确认](../core/core-process/subscription.md#32-cursor-与确认)）。未确认的区间重连后可能重复收到。确认越过一条缺失通知所标的区段，即确认了这次损失，该通知不再给出。
- **缺失通知**：订阅上的投递缺口按 [translation.md §4.3 状态与结果的翻译](translation.md#43-状态与结果的翻译) 的 `Gap{origin: Delivery}` 一行翻成缺失通知；它在每次重连时先于后续推送给出，客户确认后消去。

### 4.4 订阅选项

- 从现在开始 / 从令牌续 / 只要最新（可能合并；客户处理不及时暂停推送、跳过一段；两者都以缺失通知标出）/ 逐条有序（客户处理不及时只放慢推送，不暂停、不跳过；落后到保留范围之外的段仍以缺失通知给出），分别落到核心的 `from` 与两种订阅消费方式（`latest`、`ordered`，[delivery.md §3.1 三种消费方式（投递侧）](../core/core-process/delivery.md#31-三种消费方式投递侧)、[subscription.md §4.1 核心↔解释层：订阅组与 rewind_cursor](../core/core-process/subscription.md#41-核心解释层订阅组与-rewind_cursor)）。
- 一个订阅可含多项数据（可跨来源，也可含策略程序的具名输出），每项各自生效或被拒；逐条有序只在同一项数据内成立，不同数据之间不保证先后（[delivery.md §3.2 投递的单位与次序](../core/core-process/delivery.md#32-投递的单位与次序)）。策略程序的具名输出从现在开始订阅时不补发已经记下的值（[translation.md §4.2 策略程序的具名输出](translation.md#42-策略程序的具名输出)）。
- 订阅没有“等齐再给”：按来源证据等齐只是策略程序的输入方式，核心的订阅不带等待点。需要多项数据到齐再计算的客户在自己一侧处理：按时间截止的，声明自己的等待窗口（例如到某时刻再等一段后用已收到的数据），窗口之后才到的数据照常收到，不当作完整。

### 4.5 订单与审批的推送

解释层对执行事实的订阅只用逐条有序，可从最早开始，没有缺失；新接入的客户要历史时，从最早开始重放即可得到 UTA 的全部请求、审批与执行过程记录（[subscription.md §3.1 订阅与项](../core/core-process/subscription.md#31-订阅与项)）。订阅一个账户之后，该账户此后的全部请求都在同一订阅里，不需重订。上游的订单状态与成交是观察记录，走观察订阅，按其缺失与保留规则给出（[observation-journal.md §2.4 保留：边界与删除规则](../core/core-process/observation-journal.md#24-保留边界与删除规则)）。

### 4.6 读取令牌的兑现

客户凭读取令牌在连接上订阅这次读取所读的数据，从令牌所记的起点开始；端点把到来的结论按 [translation.md §4.4 读取令牌](translation.md#44-读取令牌) 的认定交给客户，其余的不交。服务重启与实例变化时的处置也在那里。
